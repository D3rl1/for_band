# 11 · 日志与留痕

## 11.1 这个板块解决什么

> **"谁在什么时候改了什么"这个问题，事后必须能答上来。**

给几十个真人用的系统，迟早会遇到"这次考勤怎么变成这样了""我的录音怎么没了"这类问题。
答不上来就只能互相猜疑；答得上来，绝大多数争议当场就解决了。

---

## 11.2 三类日志，用途不同，**不要混在一起**

| 类型 | 记什么 | 谁能看 | 保留 |
|---|---|---|---|
| **访问日志** | 请求路径、状态码、耗时、操作人 | 管理员 | 30 天 |
| **操作日志（业务留痕）** | **谁 · 何时 · 对什么 · 做了什么 · 改前 → 改后** | 管理员 / 团长 | **长期** |
| **错误日志** | 异常堆栈、上下文 | 管理员 | 30 天 |

### `operation_log` 表

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `operator_id` | 操作人（**代签时这是关键信息**） |
| `action` | 动作类型（见 §11.3） |
| `target_type` / `target_id` | 操作对象 |
| `before` / `after` | 改前 / 改后的值（JSON，只存变化的关键字段） |
| `ip` | 来源 IP |
| `created_at` | |

索引：`idx_operator_id`、`idx_target`、`idx_created_at`

## 11.3 必须留痕的动作

| 类别 | 具体动作 |
|---|---|
| **账号** | 建号 · 停用 · 改角色 · 改声部 · **重置密码** · 导出账号表 |
| **考勤** | **代签** · 改签到状态 · **审批请假** |
| **活动** | 建 / 改 / **取消**活动 · **团长改声部课内容** |
| **曲目与演出** | 改曲目 · 改演出档案 · 删附件 / 照片 |
| **录音** | 删录音 |
| **数据** | 导出考勤表 · 导出全量数据 |
| **系统** | 备份执行 · 备份失败 |

## 11.4 两条铁律

### 1. 密码与 token 绝不入日志

包括**错误日志的异常信息里也不能带**。
⚠️ 常见坑：异常堆栈会把方法入参打出来，而登录接口的入参里就有密码。
**登录 / 改密码相关的逻辑要显式检查日志输出。**

### 2. 操作日志**只增不改不删**

留痕如果能被修改，就等于没有留痕。
应用层**不提供任何删除或修改 `operation_log` 的接口**。

## 11.5 与 H2 的关系（声部课修改留痕）

用户在需求里明确要求过一条：

> "团长可以修改声部长安排的声部课的内容，但**要标注一下团长修改了的痕迹**，
> 不然声部长完全不知情也不好。"

这条需求分两层实现：

| 层 | 期 1 做吗 | 内容 |
|---|---|---|
| **界面层（H2）** | ✅ | `event.updated_by` + `updated_at`；**当修改人 ≠ 创建人时，界面显式标注「已被 XXX 修改于 …」** |
| **完整差异（本文件）** | 期 1 不做 | `operation_log` 里记录逐次修改的 `before` / `after` |

> **H2 是操作日志在界面上的投影。** 期 1 先做界面那层（成本低、声部长立刻有感），
> 完整的逐次差异等操作日志体系建起来后自然就有了。

---

## 11.6 实现建议

- 用 **AOP 切面 + 自定义注解** `@OpLog(action = ...)` 统一记录，
  不要让每个 Service 手写一遍（写一百遍就会漏九十九遍）
- 访问日志可直接用 Spring Boot 的 access log 或轻量 Filter
- 日志轮转：logback 按天切分 + 保留 30 天（见 `12-部署与备份.md`）
