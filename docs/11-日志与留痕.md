# 11 · 日志与留痕

## 11.1 这个板块解决什么

> **"谁在什么时候改了什么"这个问题，事后必须能答上来。**

给几十个真人用的系统，迟早会遇到"这次考勤怎么变成这样了""我的录音怎么没了"这类问题。
答不上来就只能互相猜疑；答得上来，绝大多数争议当场就解决了。

---

## 11.2 三类日志，用途不同，**不要混在一起**

| 类型 | 记什么 | 谁能看 | 保留 |
|---|---|---|---|
| **访问日志** | 请求路径、状态码、耗时、操作人 | 管理员 | 30 天 |
| **操作日志（业务留痕）** | **谁 · 何时 · 对什么 · 做了什么 · 改前 → 改后** | 管理员 / 团长 | **长期** |
| **错误日志** | 异常堆栈、上下文 | 管理员 | 30 天 |

### `operation_log` 表

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `operator_id` | 操作人（**代签时这是关键信息**） |
| `action` | 动作类型（见 §11.3） |
| `target_type` / `target_id` | 操作对象 |
| `before` / `after` | 改前 / 改后的值（JSON，只存变化的关键字段） |
| `ip` | 来源 IP |
| `created_at` | |

索引：`idx_operator_id`、`idx_target`、`idx_created_at`

## 11.3 必须留痕的动作

| 类别 | 具体动作 |
|---|---|
| **账号** | 建号 · 停用 · 改角色 · 改声部 · **重置密码** · **踢下线** · 导出账号表 |
| **考勤** | **代签** · 改签到状态 · **请假批准覆盖已有签到** · **审批请假** |
| **活动** | 建 / 改 / **取消**活动 · **团长改声部课内容** |
| **曲目与演出** | 改曲目 · 改演出档案 · 删附件 / 照片 |
| **录音** | 删录音 |
| **数据** | 导出考勤表 · 导出全量数据 ⏸ 暂缓（随部署） |
| **系统** | 备份执行 · 备份失败 🚧 待实现（#12）· **管理员应急重置密码** |
| **专场策展** | 开专场时间点 · 设为/取消专场 · 加入策展图 · 调整策展顺序 · 改策展文案 · 移出策展图 |
| **声部留言** | 上任声部长留言（写与改共用） |

> ⚠️ **上面带标记的三个动作，现在代码里都还没有**（`导出全量数据` 随部署暂缓；
> `备份执行` / `备份失败` / `应急重置密码` 的规格已定案、代码未写）。
> **这是"规格里有、代码里没有"，不是本文档漏记**——标记含义见 `docs/00` §0.9，进度看 `交接单.md`。
>
> **`备份执行` / `备份失败` 的落地形态**（`docs/12` §12.5「⚡ 备份成败怎么让应用知道」）：
> 两个 action 由**备份脚本 best-effort 写入**（脚本本来就有库凭据）；
> ⚠️ **库不可用时写不进去是正常的**，那种情况**以状态文件的 `ok=false` 为凭据**。

> **「管理员应急重置密码」（`ADMIN_PASSWORD_EMERGENCY_RESET`）是 2026-09-24 补的**：
> 应急重置脚本要作废目标账号的全部 token（`SECURITY.md` F7 第 3 条），
> 而这条动作原先没有 action 串。**只在服务器上执行，不经过任何 API。**

> **「专场策展」这组 6 个 action 串是 2026-09-28 补的**（来自 `#73`，功能见 `docs/17`）：
> `SHOWCASE_CREATE`（开专场时间点）、`SHOWCASE_TOGGLE`（设为/取消专场）、
> `SHOWCASE_PHOTO_ADD`（加入策展图）、`SHOWCASE_PHOTO_ORDER`（调整策展顺序）、
> `SHOWCASE_PHOTO_NOTE`（改策展文案）、`SHOWCASE_PHOTO_DELETE`（移出策展图）。
> 6 个串都挂了 `@OpLog`、并在 `logs.html` 的 `actionLabels` 里配了中文名；
> 规格侧定：**新起「专场策展」一行类别**登记（未并进「曲目与演出」）。
> ⚠️ **闸门管不到这一项**（`spec_check.py` R10 只管错误码表）——**只有人看**。

> **「声部留言」的 `SECTION_NOTE_WRITE` 是 2026-09-30 补的**（来自 `#111`，功能见 `docs/03` §3.5）：
> **写与改共用这一个串**（它是"留痕"，不区分新增 / 修改），中文名「写上任声部长留言」。
> 规格侧定：**新起「声部留言」一行类别**登记。

> **「踢下线」是 2026-09-23 补进来的**——`01` §1.3 新增了
> `POST /api/admin/members/{id}/revoke-sessions`（作废某人全部 token、但**不动账号状态**），
> 属**账号级动作**，与"停用"同类。实现当时已经写了 `@OpLog`，是**规格漏了**这条。

> **明确不进这张清单的**：「**处理反馈**」（`15`）。理由——`feedback` 表自带
> `handled_by` / `handled_at`，**本身就是留痕**；再进操作日志是同一件事记两遍。
> 判断标准：**被操作的对象自己已经记了"谁在何时处理的"，就不必重复记**。
>
> **同样不进清单的：「改自己的资料」**（头像 / 简介 / 联系方式 / 生日，`03` §3.4）。
> 理由：这是**本人对自己资料的编辑**，不是"对他人数据的管理动作"——留痕要回答的是
> "**谁动了不属于他的东西**"，而这个动作天然不涉及。**（管理员替别人改，走的是
> `PUT /api/admin/members/{id}`，那条本身就在「账号」一行的"改角色/改声部"同类里。）**
> 写在这里是为了**免得后人看着"改了数据却没留痕"顺手补上**。

> ⚠️ **「请假批准覆盖已有签到」为什么要单列出来**（2026-09-23 补）：它**既不完全等于"审批请假"、
> 也不等于"改签到状态"**——所以**不显式写就必然被漏**（本轮评审就是这么漏的：实现里那条
> `PRESENT → LEAVE` 的改写**没有任何留痕**，等审批人批完，签到的痕迹就没了）。
>
> ⚠️ **「改签到状态」与「覆盖签到」的留痕必须写全 `before` → `after`**：
> `§11.2` 的字段定义本来就要求两个都给（`before` = 改前值、`after` = 改后值），
> **但实现当时把 `ATTENDANCE_SET_STATUS` 的 `before` 传成了 `null`**——只记了"改成了什么"，
> 答不上"改之前是什么"，而这正是留痕存在的理由。**这两个字段一起写才算留痕，写一半不算。**
>
> ⚠️ **2026-10-18 起「覆盖」的 `before` 不再只有 `PRESENT`**：考勤状态扩为四值
> （`PRESENT` / `PARTIAL` / `LEAVE` / `ABSENT`，见 `05` §5.2），所以
> `ATTENDANCE_OVERRIDE_BY_LEAVE` 的 `before.status` 可能是 **`PRESENT` / `PARTIAL` / `ABSENT`**
> 中的任意一个，`after.status` 恒为 `LEAVE`。**不新增 action**，原 action 名保留不动；
> 覆盖逻辑仍是"任何非 `LEAVE` 的已有行 → `LEAVE`"，实现时**不要只放行 `PRESENT`**。
>
> 📌 **团员乐器（`member.instrument`）的变更本轮不进 `snapshotOf`**（2026-10-18 明确不做）：
> `PUT /api/admin/members/{id}` 的快照仍只记 `role` / `sectionId` / `status` / `joinedAt`。
> 写在这里是免得后人把"改了乐器却没留痕"当成漏项顺手扩大范围。

## 11.4 两条铁律

### 1. 密码与 token 绝不入日志

包括**错误日志的异常信息里也不能带**。
⚠️ 常见坑：异常堆栈会把方法入参打出来，而登录接口的入参里就有密码。
**登录 / 改密码相关的逻辑要显式检查日志输出。**

### 2. 操作日志**只增不改不删**

留痕如果能被修改，就等于没有留痕。
应用层**不提供任何删除或修改 `operation_log` 的接口**。

## 11.5 与 H2 的关系（声部课修改留痕）

用户在需求里明确要求过一条：

> "团长可以修改声部长安排的声部课的内容，但**要标注一下团长修改了的痕迹**，
> 不然声部长完全不知情也不好。"

这条需求分两层实现：

| 层 | 期 1 做吗 | 内容 |
|---|---|---|
| **界面层（H2）** | ✅ | `event.updated_by` + `updated_at`；**当修改人 ≠ 创建人时，界面显式标注「已被 XXX 修改于 …」** |
| **完整差异（本文件）** | 期 1 不做 | `operation_log` 里记录逐次修改的 `before` / `after` |

> **H2 是操作日志在界面上的投影。** 期 1 先做界面那层（成本低、声部长立刻有感），
> 完整的逐次差异等操作日志体系建起来后自然就有了。

## 11.6 实现建议

- 用 **AOP 切面 + 自定义注解** `@OpLog(action = ...)` 统一记录，
  不要让每个 Service 手写一遍（写一百遍就会漏九十九遍）
- 访问日志可直接用 Spring Boot 的 access log 或轻量 Filter
- 日志轮转：logback 按天切分 + 保留 30 天（见 `12-部署与备份.md`）
