# 07 · 演出

## 7.1 这个板块解决什么

记录乐团演出的完整档案：演了什么、谁上的台、曲目顺序与指挥、录像在哪、照片与复盘。

**这份档案本身就记着"某年某场谁上过台"**——2026-09-24 起这也是"谁上过台"这件事的**唯一落点**：
期 6 历届成员板块已取消（`09` 整份 ❌ 不做），演出节目单承担了它原来的意义。

## 7.3 接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/concerts` | 登录 | 演出列表（分页，含历史） |
| GET | `/api/concerts/{id}` | 登录 | 详情（曲目单 + 参演名单 + 照片 + 复盘） |
| POST / PUT | `/api/concerts` `/api/concerts/{id}` | 管理员 / 团长 / 指挥 | 新建 / 修改 |
| PUT | `/api/concerts/{id}/program` | 管理员 / 团长 / 指挥 | 设置曲目单（顺序 + 指挥） |
| PUT | `/api/concerts/{id}/cast` | 管理员 / 团长 / 指挥 | 设置参演人员名单 |
| POST | `/api/concerts/{id}/photos` | **登录（全员）** | 上传照片 |
| DELETE | `/api/concerts/{id}/photos/{pid}` | 上传者本人 / 管理员 | 删除照片 |
| GET | `/api/concerts/{id}/program.html` | 登录 | **可打印节目单**（见 §7.4） |

> ⚠️ **「我们的专场」专页自己的接口不在本表**——它们归 `17-我们的专场.md` §17.3
> （专页是**展示板块**，与演出档案的运维接口不是一回事）。本表只管演出档案本身。

## 7.4 业务规则与边界

### 演出**不做签到考勤**

演出不是排练，现场忙着上台不可能点签到。

**改为记录「参演人员名单」**（`concert_cast`）：提前定好、事后可核对。
这份名单记的就是"某年某场谁上过台"本身。

> **荣誉团员可以被列入参演名单**（2026-09-23 定）：现实里"毕业了回团参演"很常见。
> 三条限制：**不计考勤**（`05` 已写）、**不能自己报名 / 修改名单**（名单由管理员 / 团长 / 指挥设置，`PUT /api/concerts/{id}/cast` 的权限不变）、
> **不能签到**（演出本来就不签到）。他们在节目单里照常出现。
>
> ⚠️ **2026-09-24 更正**：这两处原文写着"这份名单是 `09-历届成员.md` 的核心数据"。
> 期 6 历届成员**用户 2026-09-23 已取消**，`09` 整份转为设计存档 → 该说法已作废（`09` 引我们的数据，
> 不是我们为 `09` 服务）。已改写。

### 录像只存链接，**不托管视频文件**

视频体积大、吃存储，还会把"每周拉回本地"的备份从几十 MB 拖成几个 GB。
发到 B 站或网盘，这里只留地址。

### 曲目单

- 曲目**从曲目库选择**，不自由填写——否则曲目库就失去了意义
- **指挥放在曲目行上**（`concert_piece.conductor`）：协奏曲请外聘指挥、某首由学生指挥，都能表达

### 节目单导出　✅ **已结案（2026-09-24）**

生成一张**可打印的 HTML 页**（`GET /api/concerts/{id}/program.html`），用于现场分发或发群。

> 它原本是暂定项 **T6**，当时用户标注的理由是"有时候是我们单独做海报的"——
> 那只影响**将来要不要另出海报**，不影响本功能，所以已结案（见 `docs/00` §0.6 的 T6 行）。

### 照片

- **团员都能上传**——演出当天拍照的往往是普通团员，限制上传只会让照片永远集不起来
- **⚠️ 照片必须在前端压缩后上传**：用 canvas 缩到**长边 1920 / 质量 80%**。
  手机直出原图一张好几 MB，不压缩的话磁盘和每周备份都会被拖垮。
  这类问题往往半年后才被发现，所以从一开始就做。
- **⚠️ 下载鉴权（2026-09-26 补写）**：`GET /api/files/{id}` 对演出照片的判定是
  **「登录即可，含荣誉团员」**——与曲目附件**相反**（那条对荣誉团员一律 403）。
  👉 规格出处是 §7.5 的可见性（全团可见）与 `02` §2.3 荣誉团员表；
  **`08` §8.5 说的"三处共用一套机制"从来不包括"共用同一条权限"**。
  ⚠️ 实现上这条规则**必须覆盖三个引用点**：① `concert_photo.file_id`、② `concert.poster_file_id`、
  ③ `showcase_photo.file_id`（`17`）。**漏掉任何一个，那些图就只有上传者本人看得到**
  ——② ③ 漏掉就是"专页的图对全团是空的"。这条规则曾经整个漏掉，见 `交接单` `#70`。

### 专场（`is_showcase`）　2026-09-26 新增

**「专场」不是一个新实体，就是一场被标记了的演出**——因此节目单、参演名单、复盘全部现成，
「我们的专场」时间线（`17`）点进一个节点，将来还能直接带出"这场演了什么、谁上过台"。

- **只有管理员能"开一个新时间点"**（= 新建一场 `is_showcase = 1` 的演出，`02` §2.3）。
  理由：它是**门面**，不是日常运营。
- ⚠️ **专场建完之后，它那条档案照常由 管理员 / 团长 / 指挥 维护**
  （名称 / 日期 / 地点 / 曲目单 / 参演名单，走本板块既有的接口）。**收窄的是"能开几个新节点"，不是"能不能改"**。
- **专页只取 `is_showcase = 1` 的演出**；其余演出照旧出现在演出列表里，只是不上时间线。
- ⚠️ **专页上展示哪些图、什么顺序、配什么字**，由管理员**单独策展**（表 `showcase_photo`，规则见 `17`）——
  **与本节这个"全员晒图"是两件事**。两边的图可以是同一张 `file`，不重复占磁盘。

### 演出照片的**帖子化**（点赞 / 评论）　**批 2——本轮只定规格，不实现** 🚧 待实现（#75）

把每场演出的照片墙做成"帖子"的样子，让人能回应。**这一节只是先把规格定下来，避免以后忘掉。**

- **一条帖子 = 一个上传者在该场演出下的照片集**（不是每张照片一条，也不是整场一条）。
  表现为：**上传者的头像 + 姓名**在整组照片上方，点赞与评论挂在**这一组**上。
  ⚠️ 头像渲染**走现成的 `paintAvatar` 唯一入口**（`14` §14.6.4），**别写第二套**。
- **上传规则一个字不变**：本节上面那几条照旧（全员可传、前端压缩）。
- **点赞与评论对全角色开放**（含团长 / 指挥，`02` §2.3）；⚠️ **荣誉团员只能看，不能点赞也不能评论**
  （`02` §2.3 荣誉团员表的防腐条款：点赞与评论是"动作 + 发言"，不是只读）。
- **表**（三张，定义见 `13`）：
  - `concert_post`（`concert_id` + `member_id`，**`UNIQUE(concert_id, member_id)`**）——一条帖子一行；
  - `concert_post_like`（**`UNIQUE(post_id, liker_id)`**）——去重**靠唯一键、不靠代码判重**（照 `profile_visit` 的先例，代码判重挡不住并发）；
  - `concert_post_comment`——**平铺按时间、不做父子嵌套**（照 `recording_comment` 的先例）。
- ⚠️ **边界：一律照 `08` §8.4「点评」的既有口径，不新造概念。**
  写这条之前**先读那一节**——评论的删除权、要不要"已读/未读"之类的状态，
  在录音点评那里都已经定过（**包括"不做已点评/未点评标记"那条及其理由**）。
- **本功能不做**：@ 提及、通知 / 提醒（`T12` 本来就没实现）、把帖子塞进个人主页。
  ⚠️⚠️ **这条边界必须写进 `00` §0.6 的 `T18` 行**（那份文件写着"个人页的社交互动（留言/点赞/@）❌ 不做"，
  理由是"等于给系统加一整个社交模块"）——**不写，下一个人会拿 T18 把这一节删掉**。
- **空帖子**：某人把自己在这场演出的照片全删光之后，这条帖子的照片数为 0 ⇒ **前端不渲染它**，
  但**数据库那行不自动删**（沿本项目"绝不自动删除任何人的东西"的一贯口径，见 `08` §8.4）。

### 彩排 / 走台

**彩排不由本板块承载**，而是作为一种活动类型 `event.kind = DRESS_REHEARSAL`
放在 `04-排练与声部课.md` 里——这样它能复用已有的**签到**和**内容**能力，不新增结构。

### 可见性

**全团可见，含历史演出。**
**荣誉团员照常能看**（`02` §2.3：含节目单 / 参演名单 / **照片** / 复盘）。
⚠️ 这里的"能看"**包括"能下载"**——`GET /api/files/{id}` 对演出照片的判定同此口径（见上面「照片」那节）。
**「我们的专场」专页也是同一个权限**（它就是演出档案换一种呈现方式），见 `17`。
