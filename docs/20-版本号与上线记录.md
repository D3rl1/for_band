# 20 · 版本号与上线记录（人话版）

> **关联**：`12` §12.6 增量上线（jar 备份与回滚口径）、`交接单.md` §六 线上发布回执。
> **用途**：给版本号定一个轻量规则，让「版本号 → 提交 → 回滚点」能对上。
> 本文是约定说明，不占 `交接单.md` 的待办编号。

---

## 20.1 这份文档解决什么问题

一句话：**出问题时，能说清「线上跑的是哪一版、怎么退回去」**。

版本号不是做完了给自己发的奖状。它只服务三件事：

1. **指认**：大家说的是同一份东西，不是「我记得是上周那版」。
2. **承诺**：这次改动分量多大，别人要不要提前准备。
3. **记录**：半年后回看，版本号能对上一段历史。

所以版本号的价值不在数字本身，而在它后面拴着的那条链：**名字 → 提交 → 服务器上的 jar**。断在哪一环，出事时都要多花时间。

---

## 20.2 四个词的大白话

**pom.xml**：Java 项目不直接手搓能跑的程序，而是把代码交给 Maven（一个打包工具）打成一个大盒子（jar），服务器上跑的就是这个盒子。`pom.xml` 是交给它的清单：项目叫什么、这盒东西编号多少、要装哪些外来零件。里面的 `<version>` 就是盒子上贴的编号。

**SNAPSHOT**：草稿上盖的「未定稿」章。Maven 看到 SNAPSHOT，会理解成「这东西还在改，别人要用就每次重新拿最新的」，所以不缓存；正式编号（比如 `0.4.0`）则被当成定稿。

**git tag**：git 每次保存代码（commit）相当于给整个项目存一次档，每次存档有一串自动生成的编号（如 `d09319c`），能精确找回当时的样子，但人记不住。tag 就是给某次存档**起个人名**，比如 `v0.1`。以后说「回到 v0.1」就等于「打开那个存档」。

**数据库迁移**：数据库是存放团员、考勤、请假、演出数据的仓库。仓库的「货架结构」会变，比如请假表要新增「原因」这一列。迁移就是「把旧结构改成新结构的那一步操作」。迁移工具（Flyway 一类）会给每一步编号，并记住仓库已经做到第几号。我们目前没上这类工具，只有一份整脚本 `sql/schema.sql` 手动重跑。

---

## 20.3 我们现在的样子

- **编号没改过**：`pom.xml` 还是建骨架时的 `0.0.1-SNAPSHOT`，之后加的功能、上线的包都沿用这个编号。等于一本书改了多次，封面还印着「第一版初稿」。
- **存档没有名字**：仓库里没有 git tag，所有提交只能靠一串自动编号指认。
- **没有版本台账**：没有「第几版改了什么」的清单。`work_log.md` 是流水账，给团员的更新告示是公告，都不能回答「这次和上次差了什么」。
- **上线记录靠提交号**：§六 记的是「某天换上了某个提交」，只有当时的当事人看得懂。
- **回滚靠日期命名**：出问题时把服务器上的 jar 换回某天备份的那个。一天发两次、或者隔了一个月，就不容易分清哪个备份对应哪次上线。
- **数据库结构没有编号**：结构改造靠整脚本重来，没有「已经改到第几步」的记录。

这些不是故障，只是**编号还没有承担「指认」的作用**。

### 安卓客户端版本（独立于后端 `v主.次`）

安卓安装包有自己的一套号：**`versionCode`（整数，只许单调递增）+ `versionName`（给人看的）**。
**这两样与后端的 `v主.次` 无关**——后端发 `v0.5` 不代表 App 要叫 0.5；反过来 App 升了版本，后端版本号也不必动。

| 规则 | 内容 |
|---|---|
| **升级判据** | 安卓系统只比 **`versionCode`**；新包必须**严格大于**已装的。改 `versionName` 不触发升级 |
| **签名** | 所有可以覆盖安装的包必须用**同一把签名密钥**；换了密钥只能卸载重装（`android/keys/` 在 `.gitignore`，不入库） |
| **三份文件必须一致** | `android/version.properties`（源）→ `android/dist/version.json` 与服务器上的 `static/app/version.json`（部署产物）。由 `android/build.sh --publish` 一次生成，**不许手改其中一份** |
| **固定路径** | 安装包永远叫 **`/app/band.apk`**；`version.json` 给站内「检查更新」用 |
| **入库口径** | `static/app/*.apk`、`static/app/version.json`、`android/build|dist|keys` 全部**在 `.gitignore`**，**是部署产物、不进仓库**（含真实 IP） |

**版本台账**

| 日期 | `versionName` | `versionCode` | 说明 |
|---|---|---|---|
| 2026-10-23 | 1.0 | 2 | 首个对外安装包；备注「服务器已更换，请安装此版本以继续使用」 |

## 20.4 我们的版本号规则

版本号形如 **`v主.次`**，从 `v0.1` 起，不用三段式。

**次号 +1**（如 `v0.1 → v0.2`）：普通更新。

- 加页面、改样式、修 bug；
- 新增功能，但不改变已有数据的含义；
- 团员不需要重新学怎么操作。

**主号 +1**（如 `v0.1 → v1.0`）：会让旧数据或旧页面出问题的改动。

- 数据库字段增删，或字段含义改变；
- 权限口径改变（谁能看什么、谁能改什么变了）；
- 需要团员重新登录、重新提交、或按新方式操作。

主号 +1 要**在发布前**提前通知团员，不能发完再说。

几条配套约定：

- 版本号由这次发布的人在上线前定，不事后补。
- 同一个版本号只指一次发布，用过就不要再指给别的提交。
- `pom.xml` 里的 `0.0.1-SNAPSHOT` **暂不改**：它只决定 jar 文件名，不参与对外沟通；对外的版本一律以 git tag 和 §六 记录为准。等哪天要对外发布正式包，再一起改。
- 对团员说话可以用日期（「10 月 12 日那版」），版本号是给我们自己对账用的。

## 20.5 每次上线的三个动作

三个动作都复用现有流程，不新增工具，也不改 §六 的表格列。

### 动作一：起号，写进 §六

在 `交接单.md` §六「内容」列的开头写上版本号，例如：

```text
v0.1｜新增演出照片页
```

历史行保持原样，不回头补号。

### 动作二：给部署的那次提交打标签

标签要指向**真正部署到服务器的那次提交**，不一定是当前最新提交。部署前先确认提交号，然后在本机项目目录执行：

```bash
git tag v0.1 <提交号>
```

如果线上部署的就是当前最新提交，可以省略提交号：

```bash
git tag v0.1
```

标签默认只留在本机，要同步到远端再执行：

```bash
git push --tags
```

### 动作三：留回滚点，并和标签对上

沿用 `12` §12.6 增量上线的第 2 步，换 jar 前备份旧包：

```bash
cp /opt/band/band.jar /opt/band/band.jar.bak-20261022
```

然后在 §六「包 / 回滚点」列写清三样东西：包文件名、备份路径、tag 名。例如：

```text
for-band-0.0.1-SNAPSHOT.jar；回滚点 /opt/band/band.jar.bak-20261022；tag v0.1
```

这样一行记录就能回答三个问题：发的是哪个包、旧包在哪、对应哪次存档。

## 20.6 回滚时怎么用

先分清两件事：

- **代码回滚**：`git checkout v0.1` 只是把本机代码切回那次存档，**不会动服务器**。
- **线上回滚**：仍按 `12` §12.6「只回 jar、不回库」：停服务，把备份 jar 换回去，再起服务。

操作前先看 §六 那一行，确认 **tag 名和 jar 备份文件名指的是同一次上线**。两者对不上时，以实际部署的包为准，并把记录补正。

**数据库不回滚**：新增的表和列会留在库里；回旧 jar 时旧代码不用这些新东西，通常没有影响。但被收紧的约束（比如某列改成不允许为空）不会跟着退回去。这正是主号 +1 要提前通知的原因。

---

## 20.7 什么时候再升级这套做法

现在的做法是手动的：一条命令、一行记录。出现下面任意一条，再考虑完整方案（三段式版本号 + 数据库迁移工具）：

1. 有别的系统要调用我们的接口，需要「大号不变就不许破坏」的承诺；
2. 数据库改动频繁到「重跑整脚本」已经记不清改到哪一步；
3. 多人同时开发、发布，手动打标签容易漏。

没出现之前，保持轻量做法。工具不是越早引入越好，是疼到那个程度再引入。

## 20.8 常见问题

**1.0 是不是「终于做完了」？**
不是。1.0 是「我承诺以后按规矩改」。功能做没做完，看 `交接单.md`，不看版本号。

**SNAPSHOT 为什么可以留着？**
它只影响 Maven 怎么把包提供给别的项目。我们只有一台服务器直接跑 jar，不靠 Maven 仓库分发，所以留着不碍事。

**跟团员说版本号还是说日期？**
说日期。「10 月 12 日那版」比「v0.2」好懂。版本号给我们自己对账用。

**忘了打标签怎么办？**
补打，指向当时真正部署的提交：`git tag v0.1 <提交号>`。补打之后不要再把这个号指给别的提交。

**一天发两次怎么办？**
两个版本号，两次都记录，各自对应自己的提交和 jar 备份。不要用同一个号覆盖一天里的两次发布。

## 20.9 一页速查

**上线前**

- [ ] 定号：这次是次号 +1，还是主号 +1？
- [ ] 主号 +1 时，提前通知团员。
- [ ] 确认这次要部署的提交号。

**上线时**

- [ ] 停服务，备份旧 jar（`12` §12.6）。
- [ ] 按顺序：换 jar、喂 `sql/schema.sql`、起服务。
- [ ] 打标签：`git tag v0.1 <提交号>`
- [ ] 推标签：`git push --tags`
- [ ] 在 §六 记一行：版本号、内容、提交、包与回滚点、结果。

**回滚时**

- [ ] 先看 §六 那一行，确认 tag 与 jar 备份对得上。
- [ ] 停服务，换回旧 jar，起服务。
- [ ] 数据库不回滚，按 `12` §12.6 的口径处理。
