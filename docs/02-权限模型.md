# 02 · 权限模型

## 2.1 这个板块解决什么

定义**谁能在系统里做什么**，并保证越权访问被稳定拦住。这是全库最容易被漏、也最危险的一块。

---

## 2.2 六级角色

| 角色 | 人数 | 定位 |
|---|---|---|
| `ADMIN` 管理员 | **仅 1 个**（系统账号） | 管**系统**：配置、部署、备份、操作日志；账号相关的全部操作；能重置任何密码 |
| `LEADER` 团长 | 约 3 个 | 管**乐团**：全部业务数据（活动 / 考勤 / 曲目 / 演出 / 录音） |
| `CONDUCTOR` 指挥 | 1~2 个 | **⚠️ 暂定（T1）**：只管排练与曲目，不碰账号与系统。**亦不参与考勤**（不签到、不算出勤——指挥是外聘 / 老师，**不是团员**），但**能看全团考勤与统计**（见下）|
| `SECTION_LEADER` 声部长 | 每声部 1 个 | 管**本声部**：安排声部课、看本声部考勤、听本声部录音并点评 |
| `MEMBER` 团员 | 其余 | 看自己相关、签到、上传自己的录音 |
| `HONORARY` 荣誉团员 | 若干（已毕业） | **只读**：给**因毕业离团**的人保留一个能登录、能查看的身份。**权限 = 团员权限的只读子集**（"**只减不增**"）——见 §2.3 末尾 |

### 两条结构性边界

1. **团长不能建 / 停用团长。** 否则三个团长可以互相踢号，出了矛盾就是僵局。
   管理员是唯一的"元权限"持有者。
2. **管理员账号是独立的系统账号**（`is_system = true`），不属于任何团员，不出现在名单与考勤里。
   详见 `01-认证与账号.md`。

> **「改问题状态」只给管理员（2026-10-26 用户拍板）**：**团长也 ❌**。
> 公开栏的状态是给全团看的"官方口径"，只由系统管理员维护，避免多个号各改一套。
> 落点上 `@RequireRole(Role.ADMIN)` 就够（与 `AdminFeedbackController` 同款），
> **不要**为了这一格去写"ADMIN 或 LEADER"的判定。
>
> **「专场」与上面第 59 行「演出档案增删改」的关系（2026-09-26 补，`17`）**：新增的
> 「专页策展」**收窄到只管理员**，而「演出档案增删改」仍是 管理员 / 团长 / 指挥。两者**不矛盾**——管的是两件事：
> **「开一个新时间点」（= 新建一场专场演出）只给管理员**，因为它是**门面**、不是日常运营；
> 而**专场建完之后，它那条档案（名称 / 日期 / 地点 / 曲目单 / 参演名单）照常由那三个角色维护**。
> 收窄的是"能开几个新节点"，**不是**"能不能改"。
> ⚠️ **别顺手把第 59 行也收窄**——那会挡住团长日常维护演出，属于误伤。
>
> **「签到（自己）」那一行 2026-09-23 改了两格**（原为五个角色全 ✅）：
> **管理员 `✅→❌`**——他是 `is_system` 的**系统账号**，`13` 不变式 3 与 `05` §5.4 都写着
> "**不参与考勤与出勤统计**"，代码里应到名单也硬过滤 `is_system`，所以原来那个 ✅ 是**不可达的**
> （规格自己打自己，已修）。
> **指挥 `✅→❌`**——**指挥是外聘 / 老师，不是团员**，不按团员口径记考勤。
> ⚠️ 这不是"指挥不该来"，而是"**他不用签到、也不算出勤率**"；
> **他的查看权一点没减**（「看某场考勤明细 / 看出勤率统计」两行照旧是全团）——
> 他得知道大家来没来，好安排排练。
>
> → 于是一句总口径：**不参与考勤的人有三类**——`is_system` 的管理员、`role = CONDUCTOR` 的指挥、
> 以及 `status ≠ ACTIVE` 的人（休团 / 退团 / 毕业，**含荣誉团员**）。这三类**不进应到名单**
> （⇒ 不能签到、不进分母），但**查看权各自另算**（指挥与管理员都能看全团）。
> 落地细节（含"分母为 0 显示 `—`"）见 `05` §5.4。

**休团权限补充（2026-11-04 用户拍板）**：`PAUSED` 表示免除本人出勤和录音作业要求，**可登录且保留本表原角色全部非出勤权限**，不改为只读、不降为荣誉团员、不因休团卸任。曲谱查看 / 下载、自愿录音上传（不计作业应录 / 未交）、问题讨论、个人资料、活动 / 演出报名及角色管理 / 审批等仍按原角色与声部范围；生日通告亦不因休团排除。休团不进录音作业应录名单，不计未交 / 部分交 / 欠交或催交；自愿上传不恢复作业义务，历史录音保留。以休团者为考勤对象的本人签到 / 他人代签 / 休团期间活动请假不产生考勤记录，历史查看保留；休团的声部长 / 团长仍可审批他人请假。`LEFT` / 普通 `GRADUATED` 与荣誉有效期的登录限制继续有效。
>
> **代签那一行是 2026-09-23 收窄的**（原为 声部长 ✅ 本声部）：代签的真实用途是**修正数据**
> （补录、改错），**没有正常场景需要"声部长替团员按一下"**（用户原话："不然谁会想着给别人代签？"）。
> 这条理由比角色清单更重要——**以后加角色时照它判断**。规则细节（含"有生效中请假的人不出现代签"、
> "窗口只管本人签到、代签不受限"）见 `05` §5.3。
>
> **审批请假的边界（与 `docs/05` §5.5 同一口径，别写成两套）**：
> 「审批请假（排练）」那一行的"双签"指 **声部长 + 团长**；**声部长自己请假**时那一方改由**团长直接签**；
> **团长自己请假**时由**另一位可登录的现任团长（含休团团长）**签，无其他合资格团长时退回管理员签。休团只免本人出勤，不卸任、不收回审批权（2026-11-04 改定）。
> 管理员对两类请假**始终可签**（兜底）。
>
> **「建 / 改声部课」那一行的团长格 2026-10-30 改了**（原先只有"可改，须留痕"，即**可改不可建**）：
> 用户拍板——"**团长布置声部课的权限可以给，毕竟一团之长，声部长如果没法直接布置的话还有后手**"。
> 团长**建**声部课**不限本声部**（他本来就没有声部），且**建与改都要留痕**（机制见 `04` §4.5）。
> ⚠️ 实现时 `checkSameSection` **只对声部长调用**——创建路径原来对所有人都查同声部，
> 只把 `LEADER` 加进白名单会被 `NOT_YOUR_SECTION` 直接挡掉。细则见 `04` §4.6。
> 🚧 待实现（#241）
>
> **纪念头像两行是 2026-11-16 加的（#266，已落地）**：**发放 / 撤回只有管理员**——团长能看团员资料，
> **不等于**能发东西；**使用**这一行对所有角色一视同仁，**只看本人有没有未撤回的发放记录**，
> 与角色高低无关（管理员没收到也不能选）。写入头像的闸门在 `MeProfileService.validateAvatar(avatar, memberId)`，
> 传的必须是**目标成员**的 id；发放关系永久有效，见 §2.4。
>
> **录音那两行是 2026-09-23 改的**（起因：`docs/archive/移交事项-2026-09-23.md` #50 / #51 —— 本表与 `08` 两处打架，实现方各按一边做，提请规格侧统一）：
> **「删除录音」收窄为「本人 / 本声部长 / 管理员」**——**团长、指挥由 ✅ 改 ❌**。
> 他们**照旧能"听全部"**（上一行没动），但**删除是不可逆动作，收窄到与录音直接相关的三方**；
> 口径以 `08` §8.4「删除权限」为准，本表原先给团长 / 指挥的 ✅ 是**未同步的旧值**。
> **录音作业那两行（「录音管理视图」/「布置·修改本周录音作业」，2026-10-26 追认补）**：声部长的"本声部"限定同样靠 `checkSameSection`，
> **只对声部长调用**——它仅豁免 ADMIN，对指挥 / 团长无差别套用会把"指挥没有声部"误判成 `30003`；
> ADMIN / LEADER / CONDUCTOR 可管任意声部。细则见 `08` §8.3。
>
> **「录音留言点评」团员那格由 ❌ 改「✅ 仅自己」**——即**团员能在自己的录音下回复追问、但点评不到别人的**。
> ⚠️ 这一格**不是放宽**：`08` §8.4 早就写着"**双向**"（声部长留言后团员要能回复，否则他会转去微信），
> 那个 ❌ 若按字面实现，会把这条功能**直接做废**。

### 荣誉团员（第 6 个角色）：**团员权限的只读子集**

## 2.4 实现要求

### 权限判定集中在一处

**所有权限判定集中在 `PermissionService`，绝不散落成 `if (role == ADMIN)`。**

理由：角色定义**用户明确说"之后还会改动"**（见 `00-总览` 的 T1）。
散着写的话，改一次角色要翻遍几十个文件，必然漏。

期 1 用「**角色枚举 + 集中判定**」即可；若日后角色变动真的频繁，
再升级为数据库可配置的权限表（**规模到了再升层**，不提前设计）。

### 默认拒绝 + 白名单 🚧 待实现（#223）

**没有显式声明权限的接口一律拒绝。** 反过来写黑名单的话，漏保护一个 POST 就是漏洞。

建议做法：自定义注解 `@RequireRole(...)` + 拦截器统一校验；未标注的接口默认拒绝。

### 问题讨论的权限落点（`15`，2026-10-26）

**能复用现成机制的，不新造判定函数。**

| 动作 | 落点 |
|---|---|
| 看问题 / 回帖 / 回帖时间线 | `@RequireRole`（登录即可）；**荣誉团员也能看**，不调 `checkNotHonorary` |
| 发问题 / 回帖 / 「我也遇到」/ 编辑自己的内容 | `@RequireRole` + `permissionService.checkNotHonorary(currentUser)` |
| 编辑**别人**的问题 / 回帖 | 比对 `member_id`；非本人 → `30002`（`NOT_SELF`） |
| **改问题状态** | **`@RequireRole(Role.ADMIN)`，只放管理员**；团长 / 指挥 / 声部长 / 团员一律 403 `30001` |
| 查看历史反馈（归档，只读） | `@RequireRole(Role.ADMIN)` |

> **不要**为"改状态"写 `checkCanChangeIssueStatus()`：`@RequireRole` 已经能表达"只放 ADMIN"
> （与 `AdminFeedbackController` 同款）；`PermissionService` 里那个 `checkNotHonorary()` 存在的唯一原因是
> **注解表达不了"排除某个角色"**，而这里不需要排除——是纯白名单。

### 越权防护（**本项目最大的真实风险**）

给几十个真人用的系统，最容易出的不是被黑客攻破，而是：

> **团员 A 看到了不该看的数据，或改到了别人的记录。**

**每条接口都过三个问题：**

1. 未登录能不能访问？
2. 普通团员能不能访问管理层接口？
3. **团员能不能操作"别人的"记录？**（水平越权）

**高危样板**：`PUT /api/attendance/{id}`、`DELETE /api/recordings/{id}`、
`GET /api/recordings/{id}` 这类**按 id 取/改数据**的接口——
**必须先确认这条记录属于当前用户、或当前用户具备该范围权限**。
这是新手最常漏的一处。

### 验收标准

**每个接口至少一条越权测试用例**：

- 用团员 token 打管理员接口 → 期望 **403**
- 用 A 的 token 改 B 的记录 → 期望 **403 或 404**
- 未带 token 访问受保护接口 → 期望 **401**

### 定向发放纪念头像（2026-11-16 拍板口径，已落地 #266）

**定性（2026-11-16 用户补充）**：本条属于**权限模型**议题，不是装扮渲染功能——核心是“哪张头像、发给哪些人、谁有资格用”的**发放关系**，为后续向特定人群发放头像做结构与权限上的准备；`docs/14` 的界面提案只是这套资格的外在表现，不能倒过来当作需求主体。与「全员可选、全站显示」的秋日头像框（本人自由选择、不涉及资格发放）是两条互不相干的线。

**用户已明确的新需求**：今后制作有纪念意义的头像时，希望只发给一部分人，并询问权限如何设置。当前 `AvatarCatalog.isAllowed()` / `MeProfileService.validateAvatar()` 仅验证头像是否在共享清单中（后者 `:67`），没有按成员发放使用资格。**2026-11-16 用户对推荐方案逐项回复“都按推荐”**，下表即已拍板口径；结构方案已于同日获用户批准并落地，见本节末「落地记录」。

**已拍板口径**：把“能否编辑个人资料”和“能否使用某张纪念头像”分开判断，按头像与具体成员之间的使用资格授权；沿用现有角色，不为每次纪念活动新增角色。

| 项 | 已定行为（2026-11-16） |
|---|---|
| 普通头像与限定头像 | 原有公共头像继续共享；新纪念头像可设为“指定成员可用”。动态 / 静态只描述素材形态，与发放范围独立——不把全部动态头像自动变成限定 |
| 发放与管理者 | **仅管理员**（`Role.ADMIN`）可发放 / 撤回；从成员名单勾选具体人，可批量发放，记录操作者、时间与纪念批次 / 理由。团长不因能查看团员资料而获得发放权 |
| 领取后的使用 | 发放只授予使用资格，不自动替换本人当前头像；本人按原编辑权限自行选择。**只要发出去就永久可用，不因之后身份变化而失效**（用户原话：“不管他最后怎么样了”）：离团、转声部、改角色、荣誉团员到期、账号停用都不清除资格；停用期间无法登录自然用不了，但记录保留，恢复后仍可用。资格不能随角色 / 声部 / 状态自动删除，也不设到期日 |
| 展示与选择 | 未获授予者自己的网格**不出现**该项（不是“显示但锁住”，不给解锁 / 领取按钮）；获得者在既有静态 / 动态区域看到并可选，标“纪念限定”。其他人看其名片 / 名册仍正常显示已佩戴头像——限制的是使用资格，不是隐藏已佩戴形象 |
| 误发撤回 | 允许撤回，但**只用于纠正发错人**，不是“到期收回”：撤回须填理由并留痕；撤回后该成员不能再选；若正佩戴则统一回退姓名首字并留痕。永久性指不因身份变化失效，不排除误发纠错 |

**正式设计时必须守的边界**：仅在前端隐藏选项不构成限制，所有头像写入路径都需后端核验“头像存在且为公共，或目标成员已获授权”；管理员代改别人头像时核验的是**目标成员**资格，不能借管理员本人身份绕过发放。接收者资料编辑资格仍按现有权限判断，不能凭拿到头像越过荣誉只读 / 账号边界。个人可用列表需反映本人资格，公开渲染不能因查看者未获该头像而把拥有者头像抹掉；清单缓存与切账号时不能串用资格。授权关系按成员身份持久保存（不塞进公开素材清单），且**不因成员离团 / 停用 / 角色变化而删除**；不改 `avatar` 仍存受控 id 的约定。

**界面展开（同日补充，按已拍板口径调整）**：入口 / 发放面板 / 记录、获赠者头像选择区与未获赠者显示见 `docs/14` §14.6.4「纪念头像定向发放：界面提案」。发放不自动替换当前头像；布局仍属建议，口径以本节为准。

**落地记录（#266，2026-11-16）**：用户批准结构（授权关系表 + 清单 `"scope": "grant"` 标记），编号 266。
- **表**：`avatar_grant`（`docs/13` §13.3㉛）；DDL 在 `sql/schema.sql`，需在 `band` / `band_test` 各跑一次。
- **接口**：`POST /api/admin/avatar-grants`（整批发放，一张限定头像 → 一批成员，全天候仅管理员）、
  `DELETE /api/admin/avatar-grants/{memberId}/{avatarId}?reason=`（撤回，理由必填）、
  `GET /api/admin/avatar-grants?avatarId=&batch=`（含已撤回行）；本人资格 `GET /api/me/avatar-grants`（每条 `{avatarId, batch}`，不带管理端字段）。
- **校验**：`MeProfileService.validateAvatar(avatar, memberId)` 两道闸门（在清单里 ∧ 公共或目标成员有未撤回资格）；
  管理员代改（`AccountLifecycleService`）传**目标成员** id。
- **留痕**：发放 / 撤回各一个 action 串（`AVATAR_GRANT` / `AVATAR_GRANT_REVOKE`，`docs/11` §11.3）。
- **反例覆盖**：`AvatarGrantTests` 覆盖未获授予者直接提交、非管理员发放、越权撤回、管理员代改目标校验、
  重复发放不新增行、撤回后不能再选、撤回佩戴回退、离团后资格仍在、重新发放激活同一行、发放记录保留已撤回行、
  撤回理由超 200 字 422、本人资格响应带 `batch` 且不外泄管理端字段。
- **不随状态删除**：没有任何代码路径在离团 / 停用 / 改角色时删除 `avatar_grant` 行；不设到期日。
