# 02 · 权限模型

## 2.1 这个板块解决什么

定义**谁能在系统里做什么**，并保证越权访问被稳定拦住。这是全库最容易被漏、也最危险的一块。

---

## 2.2 六级角色

| 角色 | 人数 | 定位 |
|---|---|---|
| `ADMIN` 管理员 | **仅 1 个**（系统账号） | 管**系统**：配置、部署、备份、操作日志；账号相关的全部操作；能重置任何密码 |
| `LEADER` 团长 | 约 3 个 | 管**乐团**：全部业务数据（活动 / 考勤 / 曲目 / 演出 / 录音） |
| `CONDUCTOR` 指挥 | 1~2 个 | **⚠️ 暂定（T1）**：只管排练与曲目，不碰账号与系统。**亦不参与考勤**（不签到、不算出勤——指挥是外聘 / 老师，**不是团员**），但**能看全团考勤与统计**（见下）|
| `SECTION_LEADER` 声部长 | 每声部 1 个 | 管**本声部**：安排声部课、看本声部考勤、听本声部录音并点评 |
| `MEMBER` 团员 | 其余 | 看自己相关、签到、上传自己的录音 |
| `HONORARY` 荣誉团员 | 若干（已毕业） | **只读**：给**因毕业离团**的人保留一个能登录、能查看的身份。**权限 = 团员权限的只读子集**（"**只减不增**"）——见 §2.3 末尾 |

### 两条结构性边界

1. **团长不能建 / 停用团长。** 否则三个团长可以互相踢号，出了矛盾就是僵局。
   管理员是唯一的"元权限"持有者。
2. **管理员账号是独立的系统账号**（`is_system = true`），不属于任何团员，不出现在名单与考勤里。
   详见 `01-认证与账号.md`。

> **「签到（自己）」那一行 2026-09-23 改了两格**（原为五个角色全 ✅）：
> **管理员 `✅→❌`**——他是 `is_system` 的**系统账号**，`13` 不变式 3 与 `05` §5.4 都写着
> "**不参与考勤与出勤统计**"，代码里应到名单也硬过滤 `is_system`，所以原来那个 ✅ 是**不可达的**
> （规格自己打自己，已修）。
> **指挥 `✅→❌`**——**指挥是外聘 / 老师，不是团员**，不按团员口径记考勤。
> ⚠️ 这不是"指挥不该来"，而是"**他不用签到、也不算出勤率**"；
> **他的查看权一点没减**（「看某场考勤明细 / 看出勤率统计」两行照旧是全团）——
> 他得知道大家来没来，好安排排练。
>
> → 于是一句总口径：**不参与考勤的人有三类**——`is_system` 的管理员、`role = CONDUCTOR` 的指挥、
> 以及 `status ≠ ACTIVE` 的人（休团 / 退团 / 毕业，**含荣誉团员**）。这三类**不进应到名单**
> （⇒ 不能签到、不进分母），但**查看权各自另算**（指挥与管理员都能看全团）。
> 落地细节（含"分母为 0 显示 `—`"）见 `05` §5.4。
>
> **代签那一行是 2026-09-23 收窄的**（原为 声部长 ✅ 本声部）：代签的真实用途是**修正数据**
> （补录、改错），**没有正常场景需要"声部长替团员按一下"**（用户原话："不然谁会想着给别人代签？"）。
> 这条理由比角色清单更重要——**以后加角色时照它判断**。规则细节（含"有生效中请假的人不出现代签"、
> "窗口只管本人签到、代签不受限"）见 `05` §5.4。
>
> **审批请假的边界（与 `docs/05` §5.5 同一口径，别写成两套）**：
> 「审批请假（排练）」那一行的"双签"指 **声部长 + 团长**；**声部长自己请假**时那一方改由**团长直接签**；
> **团长自己请假**时由**另一位在团团长**签，**只有一位在团团长时退回管理员签**（2026-09-23 改）。
> 管理员对两类请假**始终可签**（兜底）。
>
> **录音那两行是 2026-09-23 改的**（起因：`移交事项-2026-09-23.md` #50 / #51 —— 本表与 `08` 两处打架，实现方各按一边做，提请规格侧统一）：
> **「删除录音」收窄为「本人 / 本声部长 / 管理员」**——**团长、指挥由 ✅ 改 ❌**。
> 他们**照旧能"听全部"**（上一行没动），但**删除是不可逆动作，收窄到与录音直接相关的三方**；
> 口径以 `08` §8.4「删除权限」为准，本表原先给团长 / 指挥的 ✅ 是**未同步的旧值**。
> **「录音留言点评」团员那格由 ❌ 改「✅ 仅自己」**——即**团员能在自己的录音下回复追问、但点评不到别人的**。
> ⚠️ 这一格**不是放宽**：`08` §8.4 早就写着"**双向**"（声部长留言后团员要能回复，否则他会转去微信），
> 那个 ❌ 若按字面实现，会把这条功能**直接做废**。

### 荣誉团员（第 6 个角色）：**团员权限的只读子集**

**不在上表逐行列**——它的口径只有一条：**能从团员那列拿掉的都拿掉，绝不新增**（"**只减不增**"）。

> ⚠️ **可见范围：一律照「团员」那一列，不照管理层那一列。**
> 典型就是活动可见性——团员只看「全团活动 + **本声部**声部课」，荣誉团员也一样（`04` §4.4）。
> 实现时**别写成 `role ≠ MEMBER`**：那样等于把新角色当管理层，
> 他会**看到全部 7 个声部的声部课**（2026-09-23 评审真踩过）。

| 能力 | 荣誉团员 | 依据 |
|---|---|---|
| 登录（看内容） | ✅ **可以登录**（对 `01` §1.4「非在团禁止登录」的**有意例外**） | 受 `member.honorary_until` 约束：**为空或已过期即不可登录** |
| 看活动安排（列表 / 详情） | ✅ | 相当于"回忆里当年有什么活动" |
| **签到** / 提交请假 / 撤回请假 | ❌ | 已离团，这些动作无意义 |
| 看名册（姓名 + 声部 + 乐器） | ✅ 全团可见 | **手机号仍然只有管理员 / 团长 / 指挥可见**（这条不改） |
| 看**别人的**出勤统计 / 请假数 | ❌ | 属"别人的数据" |
| 看**自己的**历史考勤与请假 | ✅ 仅自己 | 自己的记录，保留 |
| **看更新公告** | ✅ **可以看** | **对"只减不增"的有意例外**（理由见下）；纯只读信息 |
| **提交反馈** | ❌ | 属"新增动作"，按**防腐条款**默认不给 |
| **改自己的资料**（头像 / 简介 / 联系方式 / 生日） | ❌ | 按**防腐条款**默认不给。**要开就得在这一节单独加一行并写理由**（比如"他们也该有个头像好回忆往事"）——像上面「看更新公告」那条例外一样办理 |
| 看曲目**元数据**（曲名 / 演出曲目单） | ✅ | |
| **看/取曲目附件（谱子、音频）** | ❌ **一律不可** | 用户明确："账号只是为了追忆往事，**跟谱子扯不上关系**"（见 `06`） |
| 看演出档案（节目单 / 参演名单 / 照片 / 复盘） | ✅ | 照片沿用现有规则（登录可见） |
| 听录音 | ✅ **仅自己发过的** | 与团员同一规则（`08`） |
| 上传 / 修改 / 删除任何内容 | ❌ 一律不可 | |
| 导出（考勤 / 账号 / 节目单） | ❌ 一律不可 | |
| 个人栏：改密码 / 登录设备 / 退出 | ✅ **可用** | 属**账号自管**，不是业务修改；不给他们就没法管自己的账号 |
| 被列入演出名单 / 节目单 | ✅ **可以参演** | 但**不计考勤、不能签到、不能自己报名**（`07`） |

> **⚠️ 一条"防腐"条款（以后新增权限时必须遵守）**：
> **任何新功能、新权限，默认都不给荣誉团员。**要给，必须**在这一节单独加一行并说明理由**——
> 因为他的定位是"只读的过去"，而不是"权限稍小的团员"。
>
> **已按此条款开出的例外（就一条）**：
> **看更新公告**（`15`）——它是**纯只读信息**，正好落在"只读的过去"这个定位里；
> 而且不给的话，「进系统会看到更新」这件事会在新老角色之间不一致，**反而制造两类体验**。
> 提反馈则**没给**（那是"动作"，不是"只读"）。**以后要再开口子，照这两条对照着判断。**

## 2.4 实现要求

### 权限判定集中在一处

**所有权限判定集中在 `PermissionService`，绝不散落成 `if (role == ADMIN)`。**

理由：角色定义**用户明确说"之后还会改动"**（见 `00-总览` 的 T1）。
散着写的话，改一次角色要翻遍几十个文件，必然漏。

期 1 用「**角色枚举 + 集中判定**」即可；若日后角色变动真的频繁，
再升级为数据库可配置的权限表（**规模到了再升层**，不提前设计）。

### 默认拒绝 + 白名单

**没有显式声明权限的接口一律拒绝。** 反过来写黑名单的话，漏保护一个 POST 就是漏洞。

建议做法：自定义注解 `@RequireRole(...)` + 拦截器统一校验；未标注的接口默认拒绝。

### 越权防护（**本项目最大的真实风险**）

给几十个真人用的系统，最容易出的不是被黑客攻破，而是：

> **团员 A 看到了不该看的数据，或改到了别人的记录。**

**每条接口都过三个问题：**

1. 未登录能不能访问？
2. 普通团员能不能访问管理层接口？
3. **团员能不能操作"别人的"记录？**（水平越权）

**高危样板**：`PUT /api/attendance/{id}`、`DELETE /api/recordings/{id}`、
`GET /api/recordings/{id}` 这类**按 id 取/改数据**的接口——
**必须先确认这条记录属于当前用户、或当前用户具备该范围权限**。
这是新手最常漏的一处。

### 验收标准

**每个接口至少一条越权测试用例**：

- 用团员 token 打管理员接口 → 期望 **403**
- 用 A 的 token 改 B 的记录 → 期望 **403 或 404**
- 未带 token 访问受保护接口 → 期望 **401**

## 2.5 待定项

- **T1 指挥权限**：现为"只管排练与曲目，不碰账号"，用户明说会改。
- **T8 账号操作权限**：现为全部收归管理员（团长不建号 / 不改角色 / 不重置密码）。
  若团长日常建号的需求变强，可能下放给团长。

> ⚠️ **T8 的边界必须说清楚（2026-09-23 补，这条已经被误用过一次）**：
> **T8 管的是"账号级"动作**——建号 / 停用 / 改角色 / 改声部 / 重置密码 / 踢下线，
> 也就是**身份与权限**。
> **它不挡"本人自己的资料字段"**：`avatar` / `intro` / `contact` / `birthday`（以及 `alumni_message`）
> **本人可以写**，见上表新增的那一行。
>
> **为什么专门写这一段**：`14` §14.6.4 的「不做的」里曾用 T8 当理由否掉过"编辑资料按钮"——
> 原话是"账号操作全部收归管理员（T8），本人改不了姓名/声部/角色——**摆一个编辑按钮是假的**"。
> **那个推理是错的**：T8 挡的是**姓名/声部/角色**，不等于"本人不能写自己的任何字段"；
> 而项目里**早就有先例**——`09` §9.3 的 `PUT /api/alumni/{memberId}/message`（毕业寄语）
> 权限写的就是「**本人 / 管理员**」。**别再把 T8 当成"本人一概不可写"的依据。**
