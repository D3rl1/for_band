# 05 · 签到与考勤

## 5.1 这个板块解决什么

让团员点一下就能签到，让管理层看到谁到了谁没到，并且**请假走正规流程、有据可查**。

> **2026-10-18 变更**：`attendance.status` 从两种扩为四种（`PRESENT` / `PARTIAL` / `LEAVE` / `ABSENT`）。
> `PARTIAL`（遗憾离场）计入出勤、不单列；`ABSENT`（缺勤）只用于改判已有行，无记录仍靠推导。见 `DECISIONS.md` D33。

---

## 5.2 数据模型

### `attendance`（考勤记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `event_id` | bigint | 关联 `event`（排练 / 声部课 / 彩排通用） |
| `member_id` | bigint | |
| `status` | varchar(12) | **四种值**：`PRESENT` 出勤 / `PARTIAL` 遗憾离场 / `LEAVE` 已批准请假 / `ABSENT` 缺勤（2026-10-18 扩） |
| `marked_at` | datetime | 签到时间点（**这就是全部事实**） |
| `marked_by` | bigint | 操作人。**本人签时 = `member_id`；代签时为操作人** |

**唯一约束：`UNIQUE(event_id, member_id)`**

> 这个唯一索引一物两用：**既防重复签到，又保证签到的幂等性**。

**缺勤默认不存，靠推导**：应到名单里没有 `attendance` 记录的人 = 缺勤。

> 为什么这样设计：避免"管理员忘记录入"被误算成缺勤——这种事一旦发生就说不清。
> 附带好处：见 §5.5 的"逾期未批自动算缺勤"，**不需要写任何额外逻辑**。

**`ABSENT` 是唯一例外，而且只用于人工改判（2026-10-18）**：

- 人**已经有** `attendance` 行（比如当时误签成了 `PRESENT`），管理员/团长事后把这一行改成 `ABSENT`；
- **无记录的人仍然没有行**，不给补一条 `ABSENT`——补录只走 §5.3「代签」，缺勤仍由“应到无记录”推导；
- 统计的缺勤数用 `应到 − 出勤 − 请假` 算，`ABSENT` 行天然落进这个减法，**不会和推导缺勤双算**。

四种值的语义：

| 值 | 中文 | 什么时候出现 |
|---|---|---|
| `PRESENT` | 出勤 | 本人签到或代签 |
| `PARTIAL` | 遗憾离场 | 来过但中途先走，或晚到；由管理员 / 团长在 §5.6 改判 |
| `LEAVE` | 请假 | 请假批准后写入（§5.5） |
| `ABSENT` | 缺勤 | 已有签到行被管理员 / 团长事后改判为没来 |

> **`PARTIAL` 计入出勤**（出勤率分子与所有「出勤」计数都含它），**不单列次数**；明细行仍显示「遗憾离场」。
> 理由见 `DECISIONS.md` D33。

## 5.3 签到规则

| 项 | 规则 |
|---|---|
| **方式** | **点「签到」→ 弹层确认 → 才提交**（2026-09-23 改，见下方留痕） |
| **窗口** | **开始前 30 分钟开放，结束后 2 小时关闭** |
| **迟到** | **只记录签到时间点，页面不出现"迟到"二字**——怎么解读交给人 |
| **幂等** | 重复提交返回 `40002 已签到`（**HTTP 409**，语义见 `10-接口规范与错误码.md`），**不报错、不产生第二条记录、也不覆盖原状态**——已存在 `ABSENT` / `PARTIAL` / `LEAVE` 行时同样如此 |
| **取消的场次** | 不可签到；已有的签到记录保留但统计排除 |

> **被改判成 `ABSENT` / `PARTIAL` 后，本人不能再自己签回来**：唯一键里已经有一行，`checkIn` 只会返回 `40002 已签到`，且**不改写原状态**。要改回 `PRESENT` 只能由管理员 / 团长走 `PUT /api/attendance/{id}`。这与“只改已有行”的口径一致。

> **变更留痕（2026-09-23）**：「方式」**原为「一键点签到」**，附的理由是**用户原话**
> "这本来就是个君子协定，现实靠人工核查人数"。
> **现改为「点 → 弹层确认 → 才提交」**。**为什么改**：**防误点**——签到是**一按就落库**的，
> 而团员自己**撤不掉**（`PUT /api/attendance/{id}` 是管理员/团长权限），点错一次就得找人改。
> **代价（如实记下）**：签到是**高频动作**（每次排练一次），从此每次都多一次点击。
> 这是**有意识接受的摩擦**，与"别用起来烦"的一般偏好相反，但**误签一次的麻烦更大**。
> **窗口与判罚的口径不变**（见本节末尾"为什么不做倒计时"）。
> **印章与提示音仍在"成功"路径上**（弹层确认之后才播），不要挂在点击上（`14` §14.6.4）。

### 代签

**口径（2026-09-23 改）：代签是"数据修正口"，不是协作功能。**

> 📌 **引用别名（2026-09-24 补）**：不少地方——**包括代码注释**——把本节写成 **`05` §5.4「代签」**。
> **代签的权威位置就是本节（§5.3）**，§5.4 是「考勤统计」。见到「§5.4 代签」即指本节对应的那几行。
> 代码注释里那批待改，见 `交接单.md` `#35`。

| 项 | 规则 |
|---|---|
| **谁能代签** | **管理员 / 团长**（见 `02` §2.3）。**2026-09-23 起声部长不再能代签** |
| **为什么收窄** | 代签的真实用途是**修正数据**（补录、改错）——**没有正常场景需要"声部长替团员按一下"**（用户原话："不然谁会想着给别人代签？"）。这条理由比角色清单更重要：**以后加角色时照它判断** |
| **接口** | `POST /api/events/{id}/attendance` + body `{"memberId": N}`——**与"本人签到"同一个端点**（见 §5.6）|
| **不受签到窗口限制** | **窗口只约束"本人签到"**，代签**不受限**。否则补录历史场次会被 `40003 当前不在签到时间内` 挡死。依据：窗口是**可用性规则**（给团员点按钮用的），**不是数据完整性闸门** |
| **必须有确认步骤** | 代签按钮**先弹层确认**，且**层里要写明"为 某某 签到"**（防点错行）——代签改的是**别人的数据**，比误签自己更该拦 |
| **有请假的人不出现代签** | 某人在这场比赛上有**生效中的请假**（`PENDING` / `APPROVED`）时，**不出现「代签」选项**，后端也**必须拒**（**返回 `40008`**，见 `10` §10.5；前端藏按钮只是体验，不是闸门，见 `SECURITY.md` C2）。**已驳回 / 已撤回的不算**——他该来，要能补签 |
| **留痕** | `marked_by` 记操作人（不记的话"谁替谁签的"永远查不清），并写一条操作日志 `ATTENDANCE_MARK_FOR`；代签记录在后台可查询 |

> **为什么"申请中的请假"也算**：已批准的请假会写一条 `attendance(status = LEAVE)`（§5.2），
> 所以那种人天然不会出现代签按钮；**但申请中的还没有 `attendance` 行**——若不额外拦，
> 同一个人就会**既有待批请假、又有一条出勤**，等审批批下来时把出勤**静默改写成请假**（无任何提示）。
> 这就是这条规则存在的理由：**先把请假走完（撤回或驳回），再代签**。

**补录历史场次（上线迁移走的就是这条路）**：`03` §3.4 与 `13` 不变式 14 定了
"**补录活动必须同时补录考勤**"。做法 = 先补 `event`、再**逐人代签**把当天来了的人录进去；
没补到的人记缺勤。**应到名单只含当前 `ACTIVE` 的人**——所以补录的历史场次里
**不会出现当年在团、现已离团的人**（这是**刻意的**：考勤只服务现役的人，见 §5.4）。

### 为什么不做倒计时、不做超时判罚

签到窗口是**可用性规则**（让大家知道什么时候能点），不是判罚机制。
**客观事实（几点签的）交给系统算，是否算迟到这个人情判断留给人。**

这与作者在其它自用工具上的一贯偏好一致：**别让系统用时间给人定性**。
详见 `DECISIONS.md` D17。

## 5.4 考勤统计

### 应到场次的计算（**个人视角**）

| 对象 | 应到 = |
|---|---|
| 排练 / 彩排 | 全团按 `event.date` 回溯为 `ACTIVE` 的成员（休团活动日不计；退团 / 毕业沿用原规则） |
| 声部课 | **按 `event.date` 在 `member_role_history` 回溯出的"当时属于该声部"的人**（且那天处于 `ACTIVE`）——**不是按当前的 `section_id`** |
| 已取消的场次 | **整场不计入**（分子分母都不计） |

> ⚠️ **两类人不进应到名单**（2026-09-23 补）：
> **`is_system` 的管理员**（系统账号，`13` 不变式 3）与
> **`role = CONDUCTOR` 的指挥**（外聘 / 老师，**不是团员**）。
> 他们**不签到、不进分母**，但**查看权不受影响**——指挥与管理员照旧能看全团考勤与统计（`02` §2.3）。
> 再加上 `status ≠ ACTIVE` 的人（休团 / 退团 / 毕业，**含荣誉团员**），
> 这三类就是**全部"不参与考勤"的人**。

> ⚠️ **前端入口必须同口径（2026-10-30 补，`交接单` #240）**：活动详情页的「签到 / 请假」入口、
> 以及「我的出勤」页的撤回请假入口，**按"是否进应到名单"隐藏**，不是按"是不是荣誉团员"隐藏。
> 这三类人里管理员、指挥、有效荣誉团员与 **`PAUSED` 休团成员均可登录**；
> ⇒ 前端除 **`ADMIN` / `CONDUCTOR` / `HONORARY`** 三个角色外，必须判断 **`me.status === 'PAUSED'`**。后端同样校验最新状态，不能只藏按钮。与 #240 共用判据，不另外复制一份。
> 漏判的后果不是"少一个按钮"，而是**点了必失败**：指挥点签到吃 422 `10001`（不在应到名单）、
> 点请假吃 403 `30001`（`checkAttendeeAction`），管理员账号同样中招。
> ⚠️ 判据**只写一处**（`band-core.js` 的 `BAND.noAttend(me)`），各页禁止再各列一份角色数组——
> 2026-10-30 查出来的缺口正是**同一条规则抄了三份、只对了一份**（`event-detail.html` 漏、`my-attendance.html` 与 `band-profile.js` 各对一半）。
> 🚧 待实现（#240）

**出勤率按个人视角计算：**

**休团区间（2026-11-04 用户拍板，T2 定案）**：休团期间的排练 / 彩排 / 声部课均不计本人应到与出勤分母，不自动生成缺勤，也不要求本人签到 / 代签 / 请假；恢复后只恢复此后的出勤要求，不能把休团期间重新算作缺勤。休团前已有的考勤记录与历史统计应保留，不能因当前 `PAUSED` 把其全部历史应到清零。查看考勤及管理 / 审批他人的权限仍按原角色。本人遗留请假保留记录，不能在休团期间活动生成新的 `LEAVE` 记录或计数；非应到者的记录不得混入单场汇总。

**实施边界**：原 `ExpectedRosterResolver` 只按现状态筛选，不能表达多次休团 / 恢复；#249 改为下述状态历史回溯。现有 `member_role_history` 不能冒充状态历史，`left_at` 不能挪作休团起点；旧数据无依据不猜休团日期。2026-11-05 用户已授权独立状态历史表、上海操作当日生效和同日最终状态；模型见 `13` §13.3㉚，其余结构扩展仍须先拍板，不能通过「全部历史清零」或「恢复后补算休团期」规避。新记录起的区间已有实现与测试，旧日期缺失部分仍不得宣称已恢复真实历史。

**#249 历史区间方案（2026-11-05，用户拍板）**：独立 `member_status_history` 存状态切换事实，列为 `id`、`member_id`、`before_status`、`after_status`、`effective_date`、`changed_at`、`operator_id`，索引 `(member_id, effective_date, id)`；状态更新与历史写入同一事务并锁定该成员，不能借角色历史或操作日志代替。模型已登记 `13` §13.3㉚；先同步规格，再改建表脚本与代码。

- **业务日与同日切换（已拍板）**：采用 `Asia/Shanghai`，从操作当日 00:00 生效，以活动日期判断；休团日免到，恢复日重新应到。同一日多次切换以最后一条为该日状态（保留所有事实），意味着日内已签到后休团会使当天记录保留但退出计数。用户明确选择当日生效。
- **旧数据（待核实）**：上线前的休团起止日无法从当前状态或 `left_at` 推断。已有考勤 / 录音及请假记录原样保留；需用户确认旧休团区间后补入真实日期，不能默认全历史休团或全历史在团。新建成员按填写的入团日期建立 ACTIVE 基线；旧成员首条事实以前只沿用首条 before_status 的原口径，避免切换造成额外回写，不把它称作已核实区间。未补齐前不能声明单场 / 个人 / 声部 / 导出历史区间统计完成，也不能用虚构日期迁移。 🚧 待实现（#249；旧区间待用户核实，真实日期回填尚未完成）
- **遗留请假（沿用本节已定规则）**：保留请求与审批记录，审批他人仍按角色；最终审批写考勤前按活动日区间重新校验。休团日活动不写入或覆盖 `attendance(LEAVE)`；已存在的非应到考勤保留原记录但退出所有汇总。恢复后仍以活动日判断，不能让恢复后的审批补写休团日考勤。
- **统一验收**：上海跨日边界、同日反复切换、多轮休团 / 恢复、休团前记录保留、休团日既有记录退出计数、恢复不追补、遗留请假审批与撤回、旧区间补录；同一场在单场 / 个人 / 声部 / 导出中的分子分母一致。实施与真实测试证据见 #249 回执；旧数据缺失日期仍须单独核实。

```
分母 = 该成员「joined_at ~ left_at」区间内、他应到的场次数
分子 = 他处于 PRESENT 或 PARTIAL 的场次数   # 遗憾离场计入出勤
请假次数 = 他处于 LEAVE 的场次数（单独统计）
缺勤 = max(分母 − 分子 − 请假次数, 0)       # 无记录与 ABSENT 都落在这里
```

**守恒式（四处必须同口径，2026-10-18 定）**：

```
present = count(PRESENT) + count(PARTIAL)
leave   = count(LEAVE)
absent  = max(expected - present - leave, 0)
rate    = expected == 0 ? — : present / expected
```

> ⚠️ **`PARTIAL` 只在这一个地方“变形”**：统计上算进 `present`，**不单列次数**；
> 明细行仍按原值显示「遗憾离场」。不要给 `PARTIAL` 加第五个数字。

> ⚠️ **`ABSENT` 既不算出勤、也不算请假**：它只是替“推导缺勤”占了一个明确的行。
> 若把它算进请假，个人页的请假次数会虚增，出勤率与请假次数的配对解释就失真了。

必须同一口径的计数点（实现时逐个核对）：

- `AttendanceService.eventAttendance`（单场明细汇总）
- `AttendanceService.sessions`（历次场次，每行五个数）
- `AttendanceService.aggregate`（全员 / 声部汇总）
- `AttendanceStatsService` 的个人汇总与 `personalKindSummary`
- `AttendanceCsvExporter` 的逐行状态

> ⚠️ **分母为 0 时展示 `—`，不是 `0%`**（2026-09-23 补）：指挥、荣誉团员这类"天然不进应到"的人，
> 分母就是 0。而现在的算法是 `expected == 0 ? 0 : present / expected`——**会显示成"0%"**，
> 一个从没缺勤的人看到 0% 只会以为系统坏了。**0/0 本身无意义，就显示 `—`。**
> （这条**同时修掉一个既有问题**：荣誉团员现在看自己的出勤率就是 0%。）

> ⚠️ **为什么不能用"当前在团成员"当应到**：某人退团后，他过去所有场次都不再算应到，
> 但他那时的签到记录还在 → **出勤率会算出超过 100%**。

> ⚠️ **补录历史活动时，必须同时补录考勤**（`13` 不变式 14）。分母是从 `event` 表现算的，
> **只补活动、不补考勤 → 分母凭空变大、分子还是 0 → 老团员出勤率暴跌**。
> 这是上面那条的**镜像坑**：那边分母变小（算出 >100%），这边分母变大（算出畸低）。
> 补录的做法见 §5.3「代签」末尾。

> ⚠️ **声部课的应到必须回溯"当时声部"**。团员**可以换声部**（见 `03-团员与声部.md`，
> 且 `11` 要求留痕），而 `member.section_id` 只有**当前值**。若按当前声部算历史声部课：
> **旧声部少算一人、新声部多算一人——两边都错**。
> 解法就是用 `member_role_history`（不变式 8 本来就要求"变更角色时必须写"），
> 按 `event.date` 落在哪段 `from_date ~ to_date` 区间判定当时属于哪个声部。
> 见 `13-数据模型总表.md` 不变式 7。
> 这是写规格阶段自审抓出来的问题，必须用 `left_at` 划边界。

### 统计口径

| 项 | 规则 |
|---|---|
| **排练出勤率 与 声部课出勤率** | **分开算，两个数字并列**（性质不同，合并会失真） |
| **请假计法** | **计入分母**：出勤率 = 出席 / 应到；**另外单列请假次数** |
| **遗憾离场（`PARTIAL`，2026-10-18）** | **计入出勤**（分子 + 所有「出勤」计数），**不单列次数**；明细行显示「遗憾离场」 |
| **缺勤（`ABSENT`，2026-10-18）** | 已有行的人工改判；统计上计入缺勤（`expected − present − leave`），**不算请假** |
| **排行** | **不做公开排行** |
| **可见性** | 自己 + 团长 / 指挥（全团）+ 声部长（本声部）|
| **荣誉团员**（2026-09-23） | **不计考勤**（已离团 → 应到名单天然不含他们，无需额外排除）；**不能签到、不能提交/撤回请假**；但**能看自己的历史考勤与请假记录**（仅自己）。他们的出勤**不参与任何统计分母** |
| **导出** | 管理员 / 团长可导出。**格式 = CSV（UTF-8 带 BOM）**，Excel 可直接双击打开——见 `10-接口规范与错误码.md` §导出格式。**逐行状态四值显式映射**：`PRESENT`→出勤、`PARTIAL`→遗憾离场、`LEAVE`→请假、`ABSENT`→缺勤；无记录→缺勤。**不得留 `else → 出勤` 的兜底**——未知值不能算成出勤 |

### ⚠️ 硬性展示规则

> **出勤率与请假次数必须成对展示，任何界面都不许单独出现其中一个。**

原因：请假计入分母，所以"请假 8 次、出勤率 78%"的人，**只看出勤率会被当成"老不来"**。
两个数字绑在一起，才读得出真实情况。

### 三种统计视图

1. **个人**：自己的出勤率 + 请假次数（分开看排练与声部课）
2. **单场**：某场活动的明细（谁到了、谁请假、谁缺勤）
3. **汇总**：声部 / 全团（按角色限定范围）

## 5.5 请假流程

### 双人审批（**排练**）

**排练的请假需要两人都批**：**声部长 + 团长**。

**声部课的请假只由声部长一方审批。**

### 为什么不用单一 `status` 字段

单一状态字段**无法表达"谁批了、谁还没批"**。因此**每条申请生成若干"待签"记录**：

| 活动类型 | 生成几条 `leave_approval` |
|---|---|
| 排练 / 彩排 | **2 条**（`SECTION_LEADER`、`LEADER`） |
| 声部课 | **1 条**（`SECTION_LEADER`） |

**判定规则**：

- **任一方 `REJECTED` → 整单驳回**（`REJECTED`）
- **全部 `APPROVED` → 整单通过**（`APPROVED`）
- 否则 `PENDING`

**通过后的动作**：写一条 `attendance(status = LEAVE, marked_by = 最终审批人)`；若已有考勤行，则改写为 `LEAVE`。
→ 好处：**统计只读一张表**，不用每次去 JOIN 申请单，同时也留了痕。

⚠️ **但"这个人在这场已经有考勤记录"怎么办？**（2026-09-23 补——原先规格没说，实现就自己拍成了**静默覆盖**；2026-10-18 泛化到四种状态）

- **口径：以请假为准**——把那条已有的 `attendance` **从任意非 `LEAVE` 状态**改写成 `LEAVE`（`PRESENT` / `PARTIAL` / `ABSENT` 都适用）。
  （他提前报了不来，以申请单为准。**但不许悄悄改写。**）
- **绝不许静默**（用户定的原话：**"要留痕，不能说直接静默了"**）。必须做**两件事，缺一不可**：

  | # | 做什么 | 为什么不能省 |
  |---|---|---|
  | ① | **留痕**：写一条操作日志——**谁批的、把哪个人的哪条考勤从什么状态改成了 `LEAVE`**；且 **`before`（改前的实际值：`PRESENT` / `PARTIAL` / `ABSENT`）与 `after`（`LEAVE`）都要写全**，不能只写改后 | `docs/11` 的定位就是"谁在什么时候改了什么，**事后必须能答上来**"——只写一半，答不上"改前是什么" |
  | ② | **当场提示**：批准成功后**在响应里告诉审批人**（如"张三已有考勤记录，其考勤已改为请假"），界面据此弹一句 | **`11` §11.2 里操作日志只有管理员 / 团长能看，而声部长也能审批**——只做①的话，**声部长批准那一刻什么都看不见**，那还是静默 |

> **为什么 ② 不是"锦上添花"**：只留痕 = "**事后**查得到"，而用户要的是"**别静默**"。
> 这两件事在**声部长审批**的场景下正好分叉——**他有权限批准，却没权限查日志**。
> 所以判据是"**审批的人当场看得见**"，不是"系统里记下来了"。

### 边界情况（**必须实现**）

| 场景 | 处理 |
|---|---|
| **声部长自己请假** | 他不能审自己，那一方改由**团长直接签** |
| **团长自己请假** | 由**另一位可登录的现任团长（含休团团长）**签；无其他合资格团长时退回管理员（2026-11-04 更新，#249 已实现） |
| **撤回** | **三个条件同时满足才可撤**：① `status === PENDING`；② **未逾期**（`!overdue`）；③ **活动未开始**（`LeaveService.ensureEventNotStarted` 的口径）。再排除 `HONORARY` / `CONDUCTOR` / 系统账号及休团期间活动（`PermissionService.checkAttendeeAction`，休团新增校验见 #249）。⚠️ 旧页面只要 `PENDING` 就给撤回钮，**逾期或已开始的活动点下去必被服务端拒**——前端必须按这三条收窄，别让用户白点一次。 |
| **逾期未批**（活动已结束仍 PENDING） | **自动视为"未请假"，即缺勤**；后台把这些申请**标红提醒审批人** |

> **变更留痕（2026-09-23）**：「团长自己请假」**原为"由管理员签"**，现改为
> 「**另一位在团团长签；只有一位在团团长时退回管理员**」。理由：团长之间互相审更顺，不必惊动管理员；
> **但必须保留管理员兜底**——否则"团里只有一位团长（或另一位不在）"时**没人能签，申请会卡死**。
> 实现落点：`PermissionService.canDecideApproval` 的 `LEADER` 行判定**现在是一刀切拒绝其他团长**
> （`requesterRole == LEADER → false`），要改成：**decider 是可登录的现任 `LEADER`（含休团）且不是申请人本人** → 可签；
> **并加兜底**：**没有其他可登录的现任 `LEADER` 时，仅 `ADMIN` 可签**。ADMIN 恒可签的兜底**保持不动**。
> **这次动的是权限判定 → 按 `AGENTS.md` 的硬规矩，实现方必须同时补集成测试**（用例见本节末尾）。

> ✅ **逾期未批无需写额外逻辑**：缺勤本来就是"没有记录"推导出来的。
> 审批一直不批 → 申请停在 `PENDING` → 那条 `LEAVE` 记录永远不会写入 → **有到场记录就按 `PRESENT` / `PARTIAL` 算，没有记录才自动计为缺勤**。
> 后台只需列出"活动已结束但仍 `PENDING`"的申请。

### 申请时的两个动作（**别做成一个东西**）

- **取消**：在**表单里**点「取消」→ 关掉表单，**不产生任何申请**（点错了、改主意了都能退）；
- **撤回**：**提交之后**想收回 → 在「我的出勤」页的请假段里点「撤回」（**必须同时满足上表三条件**：`PENDING` + 未逾期 + 活动未开始；荣誉团员 / 指挥 / 系统账号及休团期间活动不出现撤回入口），
  接口是 `POST /api/leave-requests/{id}/cancel`。

> 这两个动作**不是一回事**：取消 = 什么都没发生；撤回 = 已经产生过申请、再把它作废。
> 界面文案也要能让团员一眼分清（"取消"只出现在表单里；"撤回"只出现在已提交的申请上）。

### 请假理由**必填**

`reason` **不能为空**——审批人（声部长 / 团长）要靠它判断批不批。
数据库层是 **`NOT NULL`**（见 `13` §13.3⑦），**前端也要校验非空**（两边都做：前端给即时反馈，后端是真闸门）。

### 这次改动要配的测试（**硬要求**，依据 `AGENTS.md`「动权限必须配测试」）

1. **另一位可登录的现任团长（含休团）能签**团长的请假；
2. **申请人自己不能签自己的**那条待签行；
3. **没有其他可登录的现任团长时**：无资格的"团长"签不动，**管理员能签**；
4. **理由为空提交被拒**（后端必须拒，前端校验只是体验）。

### 期 1 排期建议

请假审批流 = 申请单 + 审批 + 状态机 + 两个界面，**会明显拉长工期**。

**建议排在期 1 的后半段**：先把签到跑起来让团员真用，再做请假。它只是锦上添花，
不该挡住第一次上线。

| `type` | string | `CHECKIN` / `LEAVE` / `RECORDING`（`RECORDING` 期 5 落地后并入，**现在不会出现**）|
| `time` | string | 业务时间，ISO 8601。签到取 `attendance.marked_at`、请假取 `leave_request.applied_at` |
| `eventId` | number | 供客户端跳活动详情 |
| `title` | string \| null | 活动标题（活动若已不在则为 null）|
| `note` | string | 展示文案：`出勤` / `遗憾离场` / `请假 · 待审批` / `请假 · 已批准` / `请假 · 已驳回` / `请假 · 已撤销` |

**排序与截断**：按 `time` **倒序**，取前 `limit` 条（默认 5、上限 20；`limit ≤ 0` 按默认值处理）。

> ⚠️ **签到那一类只取 `attendance.status` 为 `PRESENT` 或 `PARTIAL` 的行**（2026-10-18 扩）。
> `PARTIAL` 的 `note` 写「遗憾离场」，流水里**不按“出勤”展示**，但它属于“本人到场”的事件，应该出现在流水里。
> `ABSENT` **必须排除**——它是事后修正值，不是签到事件，捞进来会让人以为自己那天来过。
> `LEAVE` 行是"请假被批准"的**后果**，与 `leave_request` 重复——**请假一律以申请单为准**。若把 `LEAVE` 行也捞进来，
> 同一次请假会在流水里**出现两次**（一次"请假 · 已批准"、一次"出勤"），看起来像发生了两件事。
> **"出勤"这个词只属于 `PRESENT`。** 这条写进规格的原因：不写的话，后人"补全"时很容易顺手把状态全都取上。

### `/api/leave-requests` 的可见范围（**默认拒绝 + 白名单**，2026-09-23 定）

`scope` 取值：`mine`（我提交的，**默认值**）/ `needsMe`（有我能签的待签行）/ `all`（角色范围内的全部）。

**枚举"谁能看到别人的请假单"，其余一律只能看自己：**

| 角色 | 能看到 |
|---|---|
| 管理员 / 团长 | 全部 |
| 声部长 | **本声部成员 + 自己**的 |
| **其他所有角色**（团员 / 指挥 / **荣誉团员** / **以及以后新增的任何角色**）| **只能看自己，无论 `scope` 传什么** |

> ⚠️ **写这条的原因（2026-09-23 评审抓到的越权）**：实现当时写的是"**列举谁不能看**"——
> `role == MEMBER || role == CONDUCTOR` 才强制只看自己；于是新加的**荣誉团员**
> 默认落进**无过滤**那一支，只要传 `?scope=all` 就能拿到**全团所有人的请假申请**
> （含 `reason` 自由文本）。`scope` 默认是 `mine`，所以默认看不出来；
> 而那个角色的越权测试也只测了 `mine`——**测试全绿，洞还在**。
>
> **口径必须是"默认拒绝 + 白名单"**（与 `02` §2.4 同一条原则）：**列举"谁能看"，
> 不列举"谁不能看"**，否则**每加一个新角色都要重犯一次**。
> `04` §4.4 的活动可见性是同一个坑的另一面（那边是"看到太多"）。

### 并发与幂等（**必须处理**）

- **两人同时点签到** → 数据库抛唯一约束冲突。
  **必须捕获并返回 `40002 已签到`（HTTP 409），不能返回 500**——否则 App 上会弹一个看不懂的错误。
  （状态码以 `10-接口规范与错误码.md` 为准；前端把 409 + `40002` 当**成功**处理。）
- 重复提交请假 → 同一个人对同一场活动**只允许一条有效的 `leave_request`**。
