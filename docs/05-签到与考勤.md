# 05 · 签到与考勤

## 5.1 这个板块解决什么

让团员点一下就能签到，让管理层看到谁到了谁没到，并且**请假走正规流程、有据可查**。

---

## 5.2 数据模型

### `attendance`（考勤记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `event_id` | bigint | 关联 `event`（排练 / 声部课 / 彩排通用） |
| `member_id` | bigint | |
| `status` | varchar | **只存两种**：`PRESENT` 已签 / `LEAVE` 已批准请假 |
| `marked_at` | datetime | 签到时间点（**这就是全部事实**） |
| `marked_by` | bigint | 操作人。**本人签时 = `member_id`；代签时为操作人** |

**唯一约束：`UNIQUE(event_id, member_id)`**

> 这个唯一索引一物两用：**既防重复签到，又保证签到的幂等性**。

**缺勤不存，靠推导**：应到名单里没有 `attendance` 记录的人 = 缺勤。

> 为什么这样设计：避免"管理员忘记录入"被误算成缺勤——这种事一旦发生就说不清。
> 附带好处：见 §5.5 的"逾期未批自动算缺勤"，**不需要写任何额外逻辑**。

### `leave_request`（请假申请）

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `event_id` | 针对哪场活动 |
| `member_id` | 申请人 |
| `reason` | 理由 |
| `status` | `PENDING` / `APPROVED` / `REJECTED` / `CANCELED`（申请人撤回） |
| `applied_at` | 提交时间 |

### `leave_approval`（待签记录）

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `leave_request_id` | |
| `required_role` | `SECTION_LEADER` / `LEADER`——**这一方需要谁来签** |
| `approver_id` | 实际签署人（未签时 NULL） |
| `decision` | `PENDING` / `APPROVED` / `REJECTED` |
| `decided_at` | |
| `note` | 审批意见 |

## 5.3 签到规则

| 项 | 规则 |
|---|---|
| **方式** | **一键点签到**（用户原话："这本来就是个君子协定"，现实靠人工核查人数） |
| **窗口** | **开始前 30 分钟开放，结束后 2 小时关闭** |
| **迟到** | **只记录签到时间点，页面不出现"迟到"二字**——怎么解读交给人 |
| **幂等** | 重复提交返回 `40002 已签到`（**HTTP 409**，语义见 `10-接口规范与错误码.md`），**不报错、不产生第二条记录** |
| **取消的场次** | 不可签到；已有的签到记录保留但统计排除 |

### 代签

声部长 / 管理员 / 团长可以代签（权限见 `02-权限模型.md`）。

**代签必须留痕**（`marked_by`）：不记的话"谁替谁签的"永远查不清。
代签记录在后台应可查询。

### 为什么不做倒计时、不做超时判罚

签到窗口是**可用性规则**（让大家知道什么时候能点），不是判罚机制。
**客观事实（几点签的）交给系统算，是否算迟到这个人情判断留给人。**

这与作者在其它自用工具上的一贯偏好一致：**别让系统用时间给人定性**。
详见 `DECISIONS.md` D17。

## 5.4 考勤统计

### 应到场次的计算（**个人视角**）

| 对象 | 应到 = |
|---|---|
| 排练 / 彩排 | 全团 `status = ACTIVE` 的成员（休团 / 退团 / 毕业不计） |
| 声部课 | **按 `event.date` 在 `member_role_history` 回溯出的"当时属于该声部"的人**（且那天处于 `ACTIVE`）——**不是按当前的 `section_id`** |
| 已取消的场次 | **整场不计入**（分子分母都不计） |

**出勤率按个人视角计算：**

```
分母 = 该成员「joined_at ~ left_at」区间内、他应到的场次数
分子 = 他签到（PRESENT）的场次数
请假次数 = 他处于 LEAVE 的场次数（单独统计）
```

> ⚠️ **为什么不能用"当前在团成员"当应到**：某人退团后，他过去所有场次都不再算应到，
> 但他那时的签到记录还在 → **出勤率会算出超过 100%**。

> ⚠️ **声部课的应到必须回溯"当时声部"**。团员**可以换声部**（见 `03-团员与声部.md`，
> 且 `11` 要求留痕），而 `member.section_id` 只有**当前值**。若按当前声部算历史声部课：
> **旧声部少算一人、新声部多算一人——两边都错**。
> 解法就是用 `member_role_history`（不变式 8 本来就要求"变更角色时必须写"），
> 按 `event.date` 落在哪段 `from_date ~ to_date` 区间判定当时属于哪个声部。
> 见 `13-数据模型总表.md` 不变式 7。
> 这是写规格阶段自审抓出来的问题，必须用 `left_at` 划边界。

### 统计口径

| 项 | 规则 |
|---|---|
| **排练出勤率 与 声部课出勤率** | **分开算，两个数字并列**（性质不同，合并会失真） |
| **请假计法** | **计入分母**：出勤率 = 出席 / 应到；**另外单列请假次数** |
| **排行** | **不做公开排行** |
| **可见性** | 自己 + 团长 / 指挥（全团）+ 声部长（本声部）|
| **导出** | 管理员 / 团长可导出。**格式 = CSV（UTF-8 带 BOM）**，Excel 可直接双击打开——见 `10-接口规范与错误码.md` §导出格式 |

### ⚠️ 硬性展示规则

> **出勤率与请假次数必须成对展示，任何界面都不许单独出现其中一个。**

原因：请假计入分母，所以"请假 8 次、出勤率 78%"的人，**只看出勤率会被当成"老不来"**。
两个数字绑在一起，才读得出真实情况。

### 三种统计视图

1. **个人**：自己的出勤率 + 请假次数（分开看排练与声部课）
2. **单场**：某场活动的明细（谁到了、谁请假、谁缺勤）
3. **汇总**：声部 / 全团（按角色限定范围）

## 5.5 请假流程

### 双人审批（**排练**）

**排练的请假需要两人都批**：**声部长 + 团长**。

**声部课的请假只由声部长一方审批。**

### 为什么不用单一 `status` 字段

单一状态字段**无法表达"谁批了、谁还没批"**。因此**每条申请生成若干"待签"记录**：

| 活动类型 | 生成几条 `leave_approval` |
|---|---|
| 排练 / 彩排 | **2 条**（`SECTION_LEADER`、`LEADER`） |
| 声部课 | **1 条**（`SECTION_LEADER`） |

**判定规则**：

- **任一方 `REJECTED` → 整单驳回**（`REJECTED`）
- **全部 `APPROVED` → 整单通过**（`APPROVED`）
- 否则 `PENDING`

**通过后的动作**：写一条 `attendance(status = LEAVE, marked_by = 最终审批人)`。
→ 好处：**统计只读一张表**，不用每次去 JOIN 申请单，同时也留了痕。

### 边界情况（**必须实现**）

| 场景 | 处理 |
|---|---|
| **声部长自己请假** | 他不能审自己，那一方改由**团长直接签** |
| **团长自己请假** | 由**管理员**签 |
| **撤回** | **活动开始前可以撤回**；**开始后不可**（否则可用来逃避缺勤） |
| **逾期未批**（活动已结束仍 PENDING） | **自动视为"未请假"，即缺勤**；后台把这些申请**标红提醒审批人** |

> ✅ **逾期未批无需写额外逻辑**：缺勤本来就是"没有记录"推导出来的。
> 审批一直不批 → 申请停在 `PENDING` → 那条 `LEAVE` 记录永远不会写入 → 该成员自动计为缺勤。
> 后台只需列出"活动已结束但仍 `PENDING`"的申请。

### 期 1 排期建议

请假审批流 = 申请单 + 审批 + 状态机 + 两个界面，**会明显拉长工期**。

**建议排在期 1 的后半段**：先把签到跑起来让团员真用，再做请假。它只是锦上添花，
不该挡住第一次上线。

## 5.6 接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/events/{id}/attendance` | 登录 | **签到（幂等）**。重复提交返回"已签到" |
| GET | `/api/events/{id}/attendance` | 见 §5.4 | 某场考勤明细 |
| PUT | `/api/attendance/{id}` | 管理员 / 团长 | 改签到状态（如事后补录） |
| GET | `/api/members/{id}/attendance-summary` | 见 §5.4 | 个人出勤率与请假次数 |
| GET | `/api/me/recent-activity` | 登录（**只能取本人**） | **新增（2026-09-23）**：「个人栏」的"最近流水"——把 **签到 / 请假 / 录音** 三类按时间倒序**合并**成一条流，`?limit=5`（上限 20）。服务端合成，前端不用拼三次；**只回本人数据、不接受 `memberId` 参数**（避免越权） |
| GET | `/api/attendance/export` | 管理员 / 团长 | 导出考勤表 Excel |
| POST | `/api/events/{id}/leave-requests` | 登录 | 提交请假申请 |
| POST | `/api/leave-requests/{id}/cancel` | 申请人 | 撤回（**活动开始后不可**） |
| GET | `/api/leave-requests` | 见 `02` | 待我审批的 / 我提交的 |
| POST | `/api/leave-approvals/{id}/decide` | 见 §5.5 | 审批（`{decision, note}`） |

### 并发与幂等（**必须处理**）

- **两人同时点签到** → 数据库抛唯一约束冲突。
  **必须捕获并返回 `40002 已签到`（HTTP 409），不能返回 500**——否则 App 上会弹一个看不懂的错误。
  （状态码以 `10-接口规范与错误码.md` 为准；前端把 409 + `40002` 当**成功**处理。）
- 重复提交请假 → 同一个人对同一场活动**只允许一条有效的 `leave_request`**。
