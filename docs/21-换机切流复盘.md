## 21.4 五个阶段的「放行闸门」

每个阶段只问一句：**满足什么才允许进入下一步。**

### 阶段 1：准备（新机可独立工作）

- 新机能起 jar；数据库能连；`/api/health` 200。
- 证书能签发、能自动续期（彩排通过）。
- 备份脚本能跑通，产物可解压。
- 磁盘余量足够放「库 + 上传包 + 旧包」。
- **不过怎么办**：任何一项不通过都不进切流；继续在旧机跑。

### 阶段 2：冻结与导出（数据不再变化）

- 旧应用已停，确认没有进程还在写库/写文件。
- 导出全库 + 打包上传目录，**记录导出时刻**。
- 三类指纹当场记下：行数据、文件清单、整包。
- **不过怎么办**：若导出失败或文件不完整，直接重启旧应用，回到阶段 1，不要带病往下走。

### 阶段 3：搬运（包完好）

- 源机、本机、目标机三处的整包 `sha256` 一致。
- 目标机解包成功，文件数/总大小与源机一致。
- **不过怎么办**：重传，不要"先导入再说"。

### 阶段 4：导入与校验（数据真的搬全了）

- 表数一致（24）。
- 行数据指纹一致。
- 上传清单指纹 + 文件数一致（23）。
- 上传目录属主为 `band:band`，应用可读写。
- 服务 `active`，本机与公网 `health` 200，HTTPS 可打开。
- **不过怎么办**：停新应用，保留现场；按回滚口径处理（见 `12`）。

### 阶段 5：收尾（用户侧真的能用）

- 真机五项验收：登录、上传后刷新仍在、新 APK 能装能传、PWA 重加 + 离线页、大文件上传耗时。
- 旧机自启已关（`systemctl is-enabled band` = `disabled`），数据与旧包保留。
- 备份保留期按决策落地并实跑一次。
- 文档、回执、群通知全部到位。
- **不过怎么办**：任何一项失败都算"未完成"，旧机**不许拆**。

## 21.5 判据为什么这么设

### 为什么比「行数据指纹」，不比整包的 `sha256`

两次 `mysqldump` 的整包哈希**几乎必然不同**：不同小版本的 MySQL（如 8.0 与 8.4）会在 dump 里写入不同的版本注释行。整包一比，差异来自工具而不是数据，反而掩盖真问题。

正确口径：只对**行数据**求指纹，导出时排除三类与数据无关的内容——**建表语句**（结构用"表数"单独核）、**触发器**、**注释**（尤其是 `/*!…*/` 这类版本条件注释）。两机执行同一条命令，指纹相同才算数据一致。命令原文见 [`12`](12-部署与备份.md) 的判据表。

### 为什么上传要「清单指纹 + 文件数」两样

只看总大小会漏掉"同名覆盖"和"少几个文件但大小凑巧接近"。

正确口径：把每个文件的**相对路径**（不是绝对路径，两台机器的安装目录不同）与**字节数**配对，排序后整体求哈希，等于把"有哪些文件、各多大"压成一个值；**文件数**再单独报一次，防止"少一个空文件"这类边界。命令原文见 [`12`](12-部署与备份.md) 的判据表。

### 「三处一致」是什么意思

**源机 → 传输包 → 目标机**。只有传输包与目标机一致，不能证明源机当初打的就是全的；只有源机与包一致，不能证明包在路上没坏。三处都报同一个 `sha256`，才算搬全。

### 服务面判据不能替代数据面判据

`/api/health` 200 只证明"进程活着、能响应"。空库也能返回 200。所以**数据面（指纹/表数/文件数）与服务面（active/health/HTTPS）必须分开过**，最后再加一层**人工验收**（登录、上传、读取），三层都过才算完成。

### 证书为什么要单独列一条

这是 **IP 证书**，有效期只有约 6 天，全靠 certbot timer 续。切换当天的"HTTPS 能打开"不代表一周后还能打开——所以必须在切流前做一次 `--dry-run --run-deploy-hooks`，切流后看一眼 `notAfter`。

## 21.6 关键决策与代价

### 不做旧网址 302 跳转

- **决定**：旧网址直接停用（应用停掉，返回 502），不做跳转。
- **理由**：旧网址本来就是测试网址；已提前通知团员换新网址，再挂跳转反而让"换网址"这件事永远收不了尾。
- **代价**：谁还收藏着旧地址，会看到一个 502。可接受。
- **未来什么时候才需要**：如果下次换机**没有提前通知用户**，或者旧地址已对外发布过，才需要跳转。
- **如果做，用 302 不用 301**：IP 证书会换，301 会被浏览器长期缓存，等于把用户永久钉在一个会过期的地址上。

### 备份保留期 14 天 → 3 天

- **决定**（用户拍板）：本地只留 3 天。
- **理由**：磁盘小；长期累积的旧备份价值低。
- **代价**：超过 3 天才发现的数据损坏，本地无备份可回。**异地周备份因此成为主要安全网**——而它目前还没有被验证在跑（见 §21.9）。
- **稳态占用**：约 `KEEP_DAYS × 上传包大小 ≈ 3 × 35MB ≈ 105MB`；库那份只有 19K/天。
- **实现要点**：清理用 `band-*` 通配，同时覆盖 `band-db-*` 与 `band-uploads-*`；`-mtime +3` 会保留 4 份（含当天），属正常。

### 换到 2 核 2G

- **决定**：新机 2 核 2G / 4M（比旧机 4G 小）。
- **能跑的前提是三处调优同时到位**：swap、MySQL 缓冲池调小、JVM `-Xms256m -Xmx512m -XX:MaxMetaspaceSize=192m`。
- **代价**：备份、统计这类重查询会比 4G 机器慢。**能跑 ≠ 宽裕**；人数或录音量再上一个台阶时，优先加内存，而不是先加核。

### 旧机留作回滚窗口

- 停应用，但**不删包、不删数据、不改配置**。
- 回滚 = 把新机数据搬回 + `enable` + `start`，不需要重装。
- 旧机到期自然下线；在此之前旧网址 502 是预期状态。

### 新 APK 必须重新分发

旧 APK 里**写死了旧服务器地址**，换 IP 后旧包无法更新、无法连服务器。新包 `versionCode=2`（覆盖安装要求版本号递增），已打进 jar 并放在 `/app/band.apk`。

**发完之后必须核对「三份版本文件一致」**：`android/version.properties`（源）、`android/dist/version.json`、
服务器上的 `static/app/version.json`。只改其中一份的典型症状：**页面提示有新版、下载到的却是旧包**，
或反过来（有新包但站内永远提示已是最新）。三份都由 `android/build.sh --publish` 一次生成，别手改。
规则与台账见 `20` §20.3「安卓客户端版本」。

## 21.7 十条注意点（正确做法版）

格式：**触发条件 → 正确做法 → 怎么自查**。

### 1. 远程命令里带 `sudo` 和 `;`

- **触发**：`sudo cmd1; cmd2` 这种一行里串了两条命令。
- **正确**：`sudo` 只作用于**紧随其后的一条命令**；第二条要提权就写成 `sudo cmd1; sudo cmd2`。
- **自查**：第二条报 `Permission denied` 而第一条成功，就是权限没跨过分号。

### 2. 改配置文件里带缩进的行

- **触发**：用 `sed -i` 按行首锚点替换，而目标行前面有空格。
- **正确**：先用 `sed -n '5p' 文件` 看原文；替换模式不要依赖行首锚点，或把缩进算进去；替换后再用 `sed -n` 打印同一行确认。
- **自查**：`sed` 成功退出且**不报错**，不等于改到了——必须回读那一行。

### 3. 把大文件写到 `/tmp`

- **触发**：在 `/tmp` 里生成别人（或旧进程）已经存在的同名文件。
- **正确**：换写到 `/data` 或应用自己的目录；`/tmp` 有 sticky bit，且 `fs.protected_regular=2` 会阻止 root 覆盖他人文件。
- **自查**：写入报"Permission denied"但目标是 root 自己的进程时，优先怀疑这不是权限位问题。

### 4. 备份清理的匹配范围

- **触发**：写 `find … -delete` 清理旧备份。
- **正确**：先用 `-print` 跑一遍看清单，再加 `-delete`；通配要同时覆盖数据库与上传两类产物。
- **自查**：清理后 `ls -lh` 目录，确认两类都只剩预期份数。

### 5. 换 origin（IP/域名）的连带影响

- **触发**：服务地址从 A 换成 B。
- **正确**：把四类东西一起处理——① 浏览器登录态（localStorage 按 origin 隔离，所有人要重新登录）；② Service Worker / PWA（也按 origin 注册，要重新"添加到主屏幕"）；③ 写死地址的客户端（APK 必须发新版本）；④ 证书（按新地址签发）。
- **自查**：用**全新浏览器**（无缓存、无旧登录态）打开新地址完整走一遍。

### 6. 有效期很短的证书

- **触发**：使用 IP 证书（LE 的 IP 证书约 6 天）。
- **正确**：必须有 timer 自动续期，切流前跑一次 `certbot renew --dry-run --run-deploy-hooks`。
- **自查**：`openssl` 或 certbot 看 `notAfter`；站点"昨天还好、今天打不开"时先查证书。

### 7. 用普通用户看 root 的目录

- **触发**：`ls /var/backups/...` 报 `Permission denied`。
- **正确**：看目录内容需要 `r`，进入/遍历需要 `x`；root 的 700 目录普通用户两者都没有。用 `sudo ls` 或先 `stat -c "%U %a %n"` 看权限。
- **自查**：`stat` 的第三个字段是权限位，`700` 表示只有属主可读写进入。

### 8. 停服务时看到 `failed` / 退出码 143

- **触发**：`systemctl stop` 后状态里出现 143 或 `failed`。
- **正确**：`143 = 128 + 15`，即收到 SIGTERM，是被要求停止的正常结果，不是崩溃。判断服务状态看 `is-active` / `is-enabled`，不要只看 stop 的退出记录。
- **自查**：`systemctl is-active band` 应为 `inactive`；`journalctl -u band` 末尾应有正常的停机日志。

### 9. 覆盖安装安卓包

- **触发**：要把新 APK 装到已装旧版的手机上。
- **正确**：`versionCode` 必须**严格递增**，签名保持一致；否则系统会拒绝覆盖。
- **自查**：装完看"应用信息"里的版本号；旧包若还写着旧地址，表现为"能打开但连不上"。
  再查**三份版本文件**（`android/version.properties`、`android/dist/version.json`、`static/app/version.json`）
  的 `versionCode` 是否同为最新、`/app/band.apk` 是否就是这一版；不一致时站内「检查更新」会说谎。

### 10. 文档里的数字

- **触发**：换机/调优后同步文档。
- **正确**：一律用**实测值**回填（配置、堆上限、保留期、表数、文件数），不要沿用上一台机器的值；保留原来的判断时，把"当时判断"与"实测结论"分开写。
- **自查**：改完 `grep` 旧值（如 `-Xmx768m`、`KEEP_DAYS=14`），确认没有残留。

## 21.9 遗留与风险

| 项 | 现状 | 影响 |
|---|---|---|
| 真机五项验收 | **未回**（登录/上传/新 APK/PWA/大文件计时） | 数据面已验证，但"用户真的能用"没有闭环 |
| 异地备份 | 文档写了"每周拉回本机、留 8 周"，**未验证在跑** | 本地只留 3 天，这是目前最大的安全网缺口 |
| 旧机下线 | 保留作回滚窗口，到期自然下线 | 到期前旧网址 502 属预期；到期后需确认不再需要回滚 |
| 证书续期 | 只有 timer，没有主动告警 | 续期若失败，最迟约 6 天后站点不可用；排障先看 `notAfter` |
| 停机窗口 | 未计时 | 下次应记录，才能判断"低峰窗口够不够" |
| `android/build.sh` | 用法示例里写着旧 IP；文件**未跟踪也未忽略** | 将来按 `.gitignore` 的意图提交 android 源码时，会把真实 IP 带进公开仓；提交前应改成 `<IP>` |
