# 12 · 部署与备份

> **部署权只属于仓库 owner**（2026-11-02 起）：GitHub 上的 PR 合并 ≠ 上线；CI 没有部署 job，也没有服务器密钥。部署仍按本文件手动执行。

## 12.1 这个板块解决什么

让服务能跑起来、数据**不丢**。
对这个项目来说，**"数据丢了"的概率比"被攻击"高得多**——所以备份是这一块的重心。

## 12.2 两个阶段

### 阶段一：本机（**现在这个阶段**）

```bash
mvn spring-boot:run
```

- 本机 MySQL 8.0
- **不做容器化**（Docker 对本项目是没必要的复杂度，见 `DECISIONS.md`）
- 手机浏览器访问 `http://<本机局域网 IP>:8080` 验证移动端效果

**本机开发库（期 0 已建立，2026-09-21）**：

- 库名 **`band`**（utf8mb4），应用账号 **`band_app`@`localhost`** 仅授权 `band.*`，
  应用不用 root 连库（见 §12.4）。密码放在 `application-local.yml`（已 gitignore，
  新机器需手工重建此文件）
- **应用账号只给 DML**（`SELECT, INSERT, UPDATE, DELETE`）——`SECURITY.md` F4 要求"应用不用 root 连库"：

  ```sql
  CREATE USER 'band_app'@'localhost' IDENTIFIED BY '<见 application-local.yml>';
  GRANT SELECT, INSERT, UPDATE, DELETE ON band.* TO 'band_app'@'localhost';
  ```

- 建表 / 补列脚本 **`sql/schema.sql`**（表结构以 `docs/13` 为唯一权威）。
  ⚠️ **这个脚本用管理员账号跑，不是 `band_app`**：
  它含 `CREATE TABLE` 与**守护式 `CREATE PROCEDURE`**（MySQL 8 不支持 `ADD COLUMN IF NOT EXISTS`，
  用 `information_schema` + 过程实现"可重复执行"，见 `13` §13.5），
  这些需要 **DDL 权限**（`CREATE` / `ALTER` / `CREATE ROUTINE` / `ALTER ROUTINE`），
  而按 F4 收紧后的 `band_app` **没有**这些权限——拿它跑会直接报权限不足。

  ```bash
  mysql -uroot -p band < sql/schema.sql     # 用管理员账号
  ```

  （**"应用账号权限收紧"与"建表脚本能跑"这两件事的边界必须写清楚**：
   这条以前没写，结果 `sql/schema.sql` 改成带过程的写法之后，
   文档里那条 `mysql -uband_app ...` 就成了一个跑不通的命令。）
- 首次启动时应用自动写入 **7 个初始声部**（打击声部 / 提琴声部 / 胡琴声部 / 吹管声部 /
  古扬声部 / 阮声部 / 琵琶声部），逻辑幂等，表非空则跳过
  （⚠️ 因此**改了声部名单后，已有库不会自动更新**——需清空 `section` 表再重启，
  或直接改数据。见 `docs/03` §3.2）

> ⚠️ **校园网的两个已知坑**（来自作者另一个项目的踩坑记录）：
> ① 校园网客户端会劫持流量，未认证前请求会撞死本机端口（报 `WinError 10061`，那是本机拦截不是超时）；
> ② 代理（如 `127.0.0.1:7890`）不稳时会影响联网操作。
>
> **对策很具体**：**Maven 配置阿里云镜像**、npm 用国内源，
> 别让"拉依赖"这一步就在校园网里卡死。

> 代价是备份 / 统计这类重查询会比 4G 机器慢。**上面"2G 偏紧"的原判断保留**——能跑 ≠ 宽裕，

> ⚠️ **下单前必须确认的一件事（这不是小事，可能白花钱）**：
> 国内云对"**没有备案的站点**"会不会拦 80/443，**官方口径是矛盾的**——
> 腾讯云官方文档写的是拦**域名**（未提纯 IP），阿里云 FAQ 却说"无论用 IP 还是域名、未备案前均不允许开通网站访问"；
> 社区实测是"**纯 IP + 非标端口**一般长期可用，**纯 IP + 80/443** 有被扫到后阻断的报告"。
> → **下单前找客服确认，或者先买最短周期实测**（别直接付一年）。
> 若确实被拦，可选的退路：先用非标端口顶（不合规、仍有风险）、或换香港节点、或走域名 + 备案。

#### 「先买最短周期」具体验哪三件（2026-09-23 定）

买**月付**（几十块）就行，**买完一小时内**按顺序验；**三件全过再转年付**。

| # | 验什么 | 怎么验 | 不过怎么办 |
|---|---|---|---|
| 1 | **80 / 443 会不会被云厂商拦** | 起个 Nginx 只配 80，从**手机流量**访问 `http://<IP>` | 换香港节点，或走域名 + 备案 |
| 2 | **LE 的 IP 证书能不能签出来** | 按 §12.2.1 步骤 2 先跑 `--staging`（**不消耗正式额度**） | 同上——80 被拦则 `http-01` 必然失败 |
| 3 | **手机能不能正常打开** | **用流量**（别用校园网 WiFi）开 `https://<IP>`，确认**有锁头**、能登录 | 查证书链 / 手机时间 / 系统版本 |

> ⚠️ 第 3 条**必须用流量验**：校园网可能被中间设备干扰（见本文件开头"校园网的两个已知坑"），
> 测出来的问题**不一定是服务器的问题**。
> 三条全过 = 这条路线成立；任何一条不过 = **只亏一个月**。

> ✅ **2026-09-23 首次上线时这三条全过**（腾讯云轻量 2 核 4G / 广州 / Ubuntu）：
> 80/443 未被拦、LE 的 IP 证书一次签出（`openssl s_client` 返回 `Verify return code: 0`，全链下发）、
> 手机流量下有锁头能登录。**完整验证过程与踩坑记在 `work_log.md`**——本节只留上面那张
> **可重复执行的判据表**，将来换服务器照它重跑一遍即可。

⚠️ **用 IP（不走域名）有一条已知代价**：**纯 IP 站点会被部分国产浏览器额外提示**——
**夸克报"安全警示"**（它自家安全中心的拦截，**与证书无关**）、**微信提示"这是 IP 地址"**；
**证书本身没问题**（Chrome / 手机自带浏览器均正常显示锁头）。
这条对"**团员多从微信群点进来**"有影响，详见 `SECURITY.md` G3。

#### 12.2.1 上 HTTPS：用 Let's Encrypt 的 **IP 地址证书**

**不需要域名、不需要备案**：Let's Encrypt 自 2026-01-15 起为 **IP 地址**签发证书。
将来若办了域名，再换成域名证书（同一个 Nginx 换证书路径 + 加 `server_name`，其余不变）。

**前置条件**：

- **固定的公网 IP** —— 买服务器时自带，**不需要额外租**；买**包月 / 包年**套餐即可
  （别选按量付费的临时 IP）。**证书绑的就是它，IP 一变证书当场作废。**
  这只与买服务器有关，**与域名 / 备案无关**。
- **80 端口对公网开放** —— webroot 验证走 `http-01`，Let's Encrypt 会回来访问
  `http://<IP>/.well-known/acme-challenge/…`。
- **certbot ≥ 5.4**（webroot 支持 IP 地址的版本；`--ip-address` 是 5.3 新增，
  `--preferred-profile` 是 4.0 新增）。

**步骤**：

1. **Nginx 先只配 80 端口**，并在其中留出 ACME 验证目录：
   `location /.well-known/acme-challenge/ { root /var/www/certbot; }`。
   ⚠️ **不要一上来就配 443** —— 443 段要引用证书文件，而证书还没签出来，Nginx 会起不来。
   **顺序必须是：先起 80 → 签证书 → 再加 443 段。**
2. **先用 staging 试跑**（不消耗正式额度、先把流程验证通）：
   ```bash
   certbot certonly --staging --preferred-profile shortlived \
     --webroot --webroot-path /var/www/certbot \
     --ip-address <你的公网IP>
   ```
   ⚠️ **不许加 `--nginx`** —— nginx / apache 插件**尚不支持 IP 地址**，只能用 `--webroot`
   （或 `--standalone`，但那要求先停掉占用 80 端口的 web server）。
3. 通了之后**去掉 `--staging`** 再跑一次，拿正式证书。
4. **手工**在 Nginx 里指向证书（`certbot` 目前**只签发、不安装**）：
   `/etc/letsencrypt/live/<IP>/fullchain.pem` 与 `privkey.pem`；然后补上 443 段
   （反代到本机 `8080`）与 80 → 443 跳转，`nginx -s reload`，
   浏览器开 `https://<IP>` 确认有锁头。
5. **配 deploy hook**，让每次自动续期后 Nginx 重载：
   往 `/etc/letsencrypt/renewal-hooks/deploy/` 放脚本执行 `nginx -s reload`。
6. **配「续期失败」告警**（**这条不能省**）：
   IP 证书只有 6 天有效期，一年要成功续期约 60 次；失败若没人察觉，
   6 天后团员打开看到的是"不安全"警告页，而作者最后才知道。
   可用作者已有的 Telegram 机器人推送，或退化为邮件。
7. **上线前必须真的跑通一次**：staging 签发成功 → 正式签发成功 → **手工触发一次续期**
   → 确认它自动重载了 Nginx。**"配置写好了"不等于"跑通了"。**

**一个容易混淆的点**：**不能用 `--nginx` 插件 ≠ 不用 Nginx。**
插件只是 certbot"顺手帮你改 Nginx 配置"的便利功能，它不支持 IP 证书，所以那两行 `ssl_certificate`
要手工写。**Nginx 本身照旧干这五件事**：

- **反向代理**：对外 443 → 本机 `8080`（Java 应用本身照旧跑 HTTP，不需要改）
- **TLS 加解密**：证书由 Nginx 加载并使用
- **80 → 443 跳转**、静态文件、限流、访问日志
- **转发真实客户端 IP**（一行配置的事，漏了会**静默失真**）：反代之后应用拿到的
  `getRemoteAddr()` 是 `127.0.0.1`——**"我的登录设备"里显示的 IP 会退化成 `127.0.0.1 *`**，
  按 IP 的登录限流也会被拉平成同一条。所以 Nginx 要送 `X-Real-IP` / `X-Forwarded-For`，
  应用侧只在**确实处于反代之后**时才信任这两个头——**无条件信任等于让客户端自己填 IP**。
- **webroot 模式下应答 ACME 的验证请求**——所以 Nginx 是签发环节的必经之路

#### 12.2.2 将来换成域名证书

办到域名后：Nginx 加 `server_name` + 把证书指向域名证书即可，反代与其它配置都不用动。
（域名路线的前置条件与坑：能备案的服务器须**大陆节点 + 累计订阅 ≥ 3 个月 + 有公网带宽**；

## 12.5 备份（**这一节最重要**）

### 三层

| 层 | 做法 | 频率 | 保留 |
|---|---|---|---|
| 服务器本地 | `mysqldump --single-transaction` 全库 | **每日凌晨** | **3 天**（2026-10-23 由 14 天下调，见下） |
| **异地** | **拉回作者本机** | 每周 | 8 周 |
| 兜底导出 | 管理员在后台点"导出全量数据"（JSON） | 按需 | 自己存 |

> **2026-10-23 保留期由 14 天改为 3 天（用户决定）**：理由是磁盘不大，长期累积的旧备份价值低。
> 代价是**恢复窗口从两周缩短到三天**——超过三天才发现的数据损坏/误删将无本地备份可回。
> 脚本侧对应 `/opt/band/backup.sh` 的 `KEEP_DAYS=3`；`-mtime +3` 实际会留 4 份（第 0~3 天）。
> ⚠️ 因此**第二层「每周拉回本机、留 8 周」成为主要安全网**，在该层真正跑起来之前，
> 不要把本机那份当作已有保障。

**文件目录也要一起备份**——录音和照片不在数据库里。

⚠️ **备的必须就是 §12.6 第 4 步配的那一个目录**（口径：`/data/band/uploads/`）。
**这两处只要是两个路径，就会安静地错**：备份脚本备一个空目录也照样"成功"，
而真正落盘的那个目录**从来没进过备份**——**不会有任何报错**（2026-09-24 查出的口径缺口，见 `交接单.md` `#47`）。

> ⚠️ **第 3 层「导出全量数据（JSON）」⏸ 随部署暂缓**（`docs/archive/移交事项-2026-09-23.md` #62）：
> **导出哪些表、什么结构，规格没定**，现在做等于实现方自己拍。

### ⚡ 备份成败怎么让应用知道（**2026-09-24 定案——原先这里是规格空白**）

**背景**：备份做成了**服务器脚本**；`docs/11` §11.3 要求 `备份执行` / `备份失败` 留痕、
下面硬要求 3 又要求后台显示"上次成功备份时间"——但**应用怎么知道脚本成没成，原先没定**，
所以应用侧一行都没实现（`GET /api/admin/storage` 是**存储用量**，与备份无关）。
现在定死，实现方不必自己拍：

**① 通道 = 状态文件，不是回调 API。**

脚本结束时写 `/opt/band/backup-status.json`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ok` | bool | 本次是否成功 |
| `last_attempt_at` | string | 本次开始时间（ISO 8601，带时区） |
| `last_success_at` | string \| null | **最近一次成功**的时间；本次失败时**保留上次的值**（不清空） |
| `message` | string | 失败原因，截断到 200 字 |

- **必须原子写**（先写 `.tmp` 再 `mv`）——否则应用会读到半截 JSON。
- **不选"脚本回调应用 API"**：那要新开一个**免登录的写入口**，为了一件只读的状态显示多一个攻击面。
- 脚本顺带**记账**：`stdout` 追加到 `/opt/band/backup.log`。
- ⚠️ **状态以文件为准，不以数据库为准**——"库挂了"正是最常见的备份失败原因，
  那种情况下失败信息**必须还写得下**（写库就写不进去了）。

**② 应用侧只读这个文件**，提供一个端点：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/admin/backup-status` | **仅管理员** | 读上面的状态文件并原样返回，另附 `stale_hours`（距上次成功的小时数；无成功记录时为 `null`）＋ `known`（文件读不出来时为 `false`，其余字段全 `null`） |

- ⚠️ **文件不存在 / 读不出来 / JSON 坏了 → 返回"未知"状态，绝不抛 500**——状态读取本身不能变成新故障。
- ⚠️ **应用绝不发起备份、也不写这个文件**（职责单一：脚本写、应用读）。

**③ 页面落点**：`logs.html`（`14` §14.5）顶部，与存储用量同一行区域。
显示「上次成功备份：<时间>」；`last_success_at` 为空、或 **>48 小时** → **标红**。

**④ 留痕**：`docs/11` §11.3 的 `备份执行` / `备份失败` 两个 action **由备份脚本 best-effort 写入**
（脚本本来就有库凭据——跑 `mysqldump` 要用）。⚠️ **库不可用时写不进去是正常的**——
此时**状态文件的 `ok=false` 才是指证据**。别为了让留痕完整去掩盖"库挂了"这件事。

### 三条硬要求

#### 1. **必须做「删库 → 从备份恢复」演练**

在一台临时库上把备份恢复出来，抽查 3 条数据能对上。

> **没演练过的备份等于没有备份。** 这是最容易自欺的一步——
> 备份命令天天成功执行，但恢复时才发现备份文件是空的或者结构不对，这种事非常常见。

**演练频率**：上线前一次；之后每季度一次。

**演练之后要留下痕迹**（2026-09-24 补，否则"每季度一次"会悄悄变成"从没做过"）：
1. `work_log.md` 记一行（日期 ｜ 从哪份备份恢复、比对了几条 ｜ 结论）；
2. 在 `交接单.md` 开一条并**当场结掉**（`✅`），作为"这一季做了"的凭据；
3. 若演练**失败**：那不是记录问题，是**事故**——按 `AGENTS.md` 进 `debug_log.md` 六段式，
   并且**在修好之前不要再声称"备份可用"**。

#### 2. **备份文件本身当作机密保管**

它包含 `member.initial_password` 明文（未激活账号的初始密码，见 `01-认证与账号.md`）。
**备份文件泄露 = 未激活账号的初始密码泄露。**

→ 备份目录权限收紧；异地传输走加密通道。

#### 3. **备份失败必须可见**

`logs.html` 顶部显示 **"上次成功备份时间"**，超过 **48 小时**标红。

**怎么实现见上面「⚡ 备份成败怎么让应用知道」那一节**（2026-09-24 定案：
脚本写状态文件 → 应用 `GET /api/admin/backup-status` 只读 → 页面标红）。

> 通知渠道由作者自行安排，**系统只负责把这个状态显示出来**，
> 不要做成"失败了但谁也不知道"。
> ⚠️ 这句是**静默失败**的典型防线（本项目 `PHILOSOPHY` 式的一条硬口味：失败要出声）——
> 备份脚本就算天天"成功执行"，只要没人看得见结果，它跟没跑是一样的。

## 12.6 第一天上线的逐步手册

> **这一节和下面的 §12.7 检查清单是一对**：这里说"**怎么做**"，清单说"**做完了没**"。
> 前提：你已经按 §12.2 选了服务器（见那节的「买什么服务器」）。

**0）上服务器之前，先在本机把这套跑通一遍**（`mvn package` 出 jar、`java -jar` 起得来、`/api/health` 通）。

**运维端点（供 systemd / Nginx / 巡检脚本用，2026-09-24 登记）**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查。**无需登录**（运维用）；只回服务存活状态，**不含任何业务数据**。`refresh.sh` 与 `restart.sh` 都靠轮询它判断服务起没起来。🚧 **待实现（#222）**：现实现还返回 `sectionCount`（查库计数），需收回到 `status` / `db` |

   **别把"第一次跑通"留到服务器上**——本地能复现的问题，在服务器上排查要慢十倍。

1. **SSH 安全基线**（照 `SECURITY.md` F 节做：密钥登录、禁密码登录、改默认端口、防火墙只开必要端口）。
   本机部署私钥放 **`~/.ssh/band-deploy`**（见 §12.3），登录用 `ssh -i ~/.ssh/band-deploy ubuntu@<IP>`。
2. **装运行时**：JDK 17 与 MySQL 8。MySQL **只监听 `127.0.0.1`**（`SECURITY.md` F3），**不要暴露公网**。
3. **建库与建表**：建库 `band` + 低权限账号 `band_app`，执行 `sql/schema.sql`（脚本可重复执行）。
4. **传 jar 与配置**：jar 放 `/opt/band/`；**数据库密码只放在服务器本地的 `application-local.yml`**（不进 git，见 §12.3）。
   **同一个文件里把落盘目录也定死**（⚠️ 这行是全项目**唯一**的口径，且必须与 §12.5 的备份目录**是同一个**）：

   ```yaml
   band.storage.dir: /data/band/uploads
   ```

   ⚠️ **漏了这行不会报错**——它会退回 `application.yml:20` 的默认值 `${user.home}/band-uploads`，
   于是**录音落在服务账号的家目录里、而备份脚本备的是 `/data/band/uploads/`**，两边永远对不上，
   而且**任何地方都不会报错**（2026-09-24 查出，见 `交接单.md` `#47`）。

   **4b）文件票据密钥（2026-10-07 落地，规格见 `08` §8.5）**
   手机看谱子走**签名 URL**，签名密钥也放进**同一个** `application-local.yml`（**不进 git**）：

   ```yaml
   band.file-ticket.secret: '<32 字节以上随机串>'
   ```

   生成：`openssl rand -base64 32`。**配好之后必须重启服务才生效**。

   ⚠️ **不配也能跑，但只是兜底**：应用会用**本次启动的临时随机密钥**（绝不退回写死的默认值），
   代价是**一重启，之前发出去的查看 / 下载链接全变 401**。前端每次打开都重新取票，**会自愈**；
   但生产不该依赖这一点——否则每次部署后第一次点谱子可能撞上旧链接。
   ⚠️ **换密钥 = 立刻作废所有已发出的链接**，属于"轮换凭据"，别当普通配置改着玩。

   ⚠️ **票据在 URL 查询串里**（`/view?t=…`）⇒ **会进 Nginx access log**。日志按凭据对待：
   只给运维账号可读，保留期照 §12.5 的节奏；**别把带 `t=` 的 URL 贴进群、工单、聊天记录**。
   应用已在 `/view` 响应上打 **`Referrer-Policy: no-referrer`**，防止票据随 Referer 漏给第三方站点；
   **别再在 Nginx 层覆盖成宽口径**，若统一加安全头，要保证不把这一条冲掉。
5. **建上传目录，并把属主交给服务账号**（**手册原先漏了这一步**，2026-09-24 补）：

   ```bash
   sudo mkdir -p /data/band/uploads && sudo chown -R band:band /data/band/uploads
   ```

   **为什么不能靠"程序自己会建"**：应用启动时确实会建这个目录（`FileStorage.java:40` 的 `Files.createDirectories`），
   但**它对"已经存在的目录"不校验可写性**——目录若由 `root` / `ubuntu` 建成（755），
   **启动一切正常、只有上传时才炸**：`Files.copy` 抛 `AccessDeniedException`，
   被压成一句「文件写入失败」（`FileStorage.java:64`，**不记日志、不带路径**），界面上完全看不出是权限问题。
   ⚠️ **与「先建 `/opt/band/logs`」那条是同一类坑**（现见 `docs/16` §16.4 症状 S2）：**"程序会自己建" ≠ "建对了"**。
   📌 **这条不是推测**——**2026-09-25 线上就是这么炸的**（属主 root），完整复盘见 `docs/16` 案例 **C1**。
6. **配 systemd**（开机自启 + 崩溃自动重启；**不用 Docker**）：

```ini
# /etc/systemd/system/band.service
[Unit]
Description=ForBand 乐团管理系统
After=network.target mysql.service

[Service]
User=band
WorkingDirectory=/opt/band
# application-local.yml 放在同目录，密码不进命令行（ps 看不到）
# 2026-10-23 换到 2C2G 后调整为 512m 上限 + 192m Metaspace（见 §12.6「换机切流」）
ExecStart=/usr/bin/java -Xms256m -Xmx512m -XX:MaxMetaspaceSize=192m -jar /opt/band/band.jar --spring.profiles.active=prod,local
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

   `systemctl daemon-reload && systemctl enable --now band` → `systemctl status band` 确认在跑。
7. **配 Nginx 反代**（`SECURITY.md` §12.4 的要求都在里面：真实 IP 转发、静态资源、限流留白）：

```nginx
# /etc/nginx/conf.d/band.conf
server {
    listen 80;
    server_name _;                      # 用 IP 访问，不配域名
    client_max_body_size 60m;           # 录音/照片上传，留足余量

    gzip on;                            # 压缩首屏那几份资源（2026-09-30 补，交接单 #131）
    gzip_types text/css application/javascript image/svg+xml;
    gzip_min_length 1024;
    # brotli 更小，但要装 ngx_brotli 模块；没装就用 gzip，别为它引额外依赖

    location / { proxy_pass http://127.0.0.1:8080;
                 proxy_set_header Host $host;
                 proxy_set_header X-Real-IP $remote_addr;   # 登录设备列表要显示真实 IP
                 proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; }

    location /.well-known/acme-challenge/ { root /var/www/certbot; }   # 给 certbot webroot 用
}
```

   **压缩为什么两层都开**：应用侧已在 `application.yml` 打开 `server.compression`（`enabled: true`，
   mime 列了 css/js/html/json，`min-response-size: 1024`）——**在 jar 这层开是为了不依赖服务器有没有配 Nginx**；
   Nginx 这层再补 `gzip` 与之不冲突（已压过的响应不会二次压）。
   实测效果（本机 `curl`，2026-09-30）：`bootstrap.min.css` **232,411 → 31,125**、`band.css` **117,262 → 42,913**、
   `app.js` **121,852 → 43,210** 字节（三份合计 **471KB → 117KB，约 −75%**）。
   📌 **这组数是 2026-09-30 当时的 `app.js` 实测**；此后脚本已拆成 `band-*.js` **8 个模块**，
   总量与单文件大小都已改变。**别再直接引用旧数字**——要报数就当场重测
   （`curl -sI` 看 `Content-Length`，或 `gzip -c <file> | wc -c`）。
   ⚠️ 静态资源还应配缓存（`location` 里加 `expires` / `Cache-Control`）——压缩只减**体积**，减不了**每次重拉**。

   > **📌 2026-10-19 修订（PWA 上线前必读，详见 `19` §19.8）**：上面原建议的 **`expires 30d` 不能再照抄**。
   > 本站静态资源文件名**没有内容指纹**（永远叫 `/band.css`、`/band-core.js`），而 PWA 的 service worker 用
   > **stale-while-revalidate**：先给缓存、同时后台拉新的。若 HTTP 层把旧文件缓存 30 天，后台拉到的仍是旧的，
   > **样式/脚本就永远更新不了**。正确分工是：**HTTP 层短缓存，SW 的 Cache Storage 才是缓存层**。
   >
   > **必须 `Cache-Control: no-cache`（或 `max-age=0, must-revalidate`）的路径**：
   > `/service-worker.js`、`/manifest.json`、`/*.html`（含 `offline.html`、`install.html`）。
   > `/icons/*` 用短缓存或 `no-cache`（由 SW 兜底）；`/api/*` 继续**不缓存**。
   > 以后若真要做长期 HTTP 缓存，必须**同时**给文件名加内容指纹并升 SW 版本号，不能只加 `expires`。

8. **签 IP 证书 + 补 443 段**：**严格按 §12.2.1 那 7 步做**（顺序不能反：**先起 80 → 签证书 → 最后才加 443**；
   `--webroot` 而不是 `--nginx`；签完配 deploy hook 重载 Nginx）。
9. **改掉默认管理员密码**（`docs/01` §1.4 的"首次部署"那节）：`AdminSeeder` 的初始密码**上线前必须换成只有管理员知道的强密码**。
10. **跑一遍 §12.7 的检查清单**，每一项都在备注里写上**验证方式**（命令 / 操作 / 截图）。
11. **PWA 缓存头自检**（`19` 上线后每次部署都跑）：
    ```bash
    curl -sI https://<IP>/service-worker.js | grep -iE 'HTTP/|content-type|cache-control'
    curl -sI https://<IP>/manifest.json      | grep -i cache-control
    curl -sI https://<IP>/events.html        | grep -i cache-control
    ```
    期望：SW 返回 `200` + JS 的 `Content-Type`；三者 `cache-control` 均为 `no-cache`（或 `max-age=0`）。
    **任何一项带了长 `max-age`，更新提示就不会触发**——先修头，再谈别的。

### 增量上线：在已有系统的机器上发新版（2026-09-28 首次增量上线实测）

> 上面 1~10 步是**第一天**（全新机器）；机器已经在跑、只是要把新版 jar 换上去，走这一节。
> ⚠️ **顺序绝不能反**，反了会让**旧 jar** 撞**新约束**直接 500。

**顺序（照抄）**：`stop → 换 jar → 跑 sql/schema.sql → start`

1. **停服务**：`sudo systemctl stop band`。
2. **留回滚点**：换 jar 前 `cp /opt/band/band.jar /opt/band/band.jar.bak-<日期>`。
3. **换 jar**：把新包覆盖到 `/opt/band/band.jar`。
4. **跑迁移**：喂 `sql/schema.sql`（脚本从 `#10` 起含**「光重跑补不上」**的迁移——例如
   `leave_request.reason` 收紧为 `NOT NULL`，而拦空理由的 `@NotBlank`**只有新代码有**）。
5. **起服务**：`sudo systemctl start band`。

**为什么必须先换 jar 再跑脚本**：`reason` 收紧成 `NOT NULL` 之后，**旧 jar** 没有 `@NotBlank` 拦截，
一旦写入空理由就会撞新约束直接 **500**。先跑脚本正是这个顺序，所以**绝不能反**。

**回滚口径**：**只回 jar、不回库**。新增的表/列是纯增量、旧代码不用它们；
但 `NOT NULL` 这个收紧会**留在库里**（回 jar 也带着它）。

**迁移跑完的四条判据**：
1. 表数 **+2**（新增 `profile_visit` / `showcase_photo`）；
2. `concert.is_showcase` 列**在**；
3. `leave_request.reason` 的 `IS_NULLABLE=NO`；
4. 该列**残留 `NULL` = 0**。

**新包生效的判据 = 打一条新端点看 401/404**：

```bash
curl -s -o /dev/null -w '%{http_code}' https://<IP>/api/showcase/timeline
```

→ **401 = 新包在**（端点存在、只是没登录）、**404 = 还是旧包**（端点在旧包里根本不存在）。
（与 `AGENTS.md` 那条同源。）

> 📌 **附带事实**：仓库里的 `sql/schema.sql` 是 **CRLF** 换行，本次先 `sed -i 's/\r$//'` 再喂 mysql。
> ⚠️ **必要性未做反例验证**（纯保险，可一并写清或明确不必）——不放心就先转一遍，代价可忽略。

### 换机切流：旧机 → 新机（2026-10-23 实测）

> 旧机到期前把服务整体搬到新机器。**只搬三样：数据库、上传目录、jar**（jar 版本不变）。
> 目标是把停机时间压到几分钟，并且**用可复算的指纹证明"搬全了"**。

**顺序（照抄）**：

1. **冻结点**：旧机 `sudo systemctl stop band`。从这一刻起**两边都不再写**，库与文件是同一时刻的快照。
2. **全库导出**：`sudo mysqldump --single-transaction --routines --databases band | gzip > /tmp/final.sql.gz`
   （`--databases` 让 dump 自带 `CREATE DATABASE` / `USE`，导入时不必手工建库）。
3. **上传目录整包**：`sudo tar -C /data/band -czf /data/uploads.tgz uploads`
   ⚠️ **别写 `/tmp`**：`/tmp` 有 sticky 位，且 Ubuntu 的 `fs.protected_regular=2` 会让 **root 也无法覆盖**
   属主是别人的同名文件（2026-10-23 实际踩到，改用 `/data` 下写包即通）。
4. **记三个指纹**（下文判据表）：数据指纹、上传包 sha256、文件清单指纹。
5. **搬运**：旧机 → 本机 → 新机，每跳 `sha256sum` 比对；**中转不省**——本机留一份副本就是临时回滚点。
6. **新机解包并修属主**：`sudo tar -C /data/band -xzf /tmp/uploads.tgz`，
   再 `sudo chown -R band:band /data/band/uploads`（属主错 = 上传必然失败，见 §12.6 第 5 步）。
7. **新机导库**：`stop → DROP DATABASE IF EXISTS band → gunzip -c /tmp/final.sql.gz | sudo mysql → start`。
8. **对齐**：跑判据表；全对才算切流成功。

**判据表（2026-10-23 实测值，可复算）**：

| 判据 | 怎么算 | 当时的值 |
|---|---|---|
| 数据指纹 | `mysqldump --no-create-info --skip-triggers --skip-comments band \| grep -v "^/\*!" \| sha256sum` | `e550711d…` 新旧一致 |
| 表数 | `information_schema.tables` 里 `table_schema='band'` 计数 | **24** |
| 上传包 | `sha256sum uploads.tgz` | `4b7e196f…` 三处一致 |
| 文件清单 | `find uploads -type f -printf "%P %s\n" \| sort \| sha256sum` | `73e6b270…` 新旧一致，**23 个文件** |
| 服务 | `systemctl is-active band` + `curl -sk https://127.0.0.1/api/health` | `active` + **200** |

> **为什么用"数据指纹"而不是整份 dump 的哈希**：新旧机 MySQL 版本不同（8.0 / 8.4），
> dump 里的版本注释行 `/*!…*/` 会不一样，直接比整份文件会**假报警**。
> 去掉建表语句与版本注释、只比行数据，才是"内容是否一致"的判据。

**两条与用户侧有关的硬事实**（切流后必须通知）：

- **旧 APK 写死了旧地址**，装旧包的人登录/上传都会失败——必须发新包（versionCode 递增）。
- **登录态与 Service Worker 按"协议 + 主机 + 端口"隔离**：换 IP 后**所有人要重新登录**，
  用过「添加到主屏幕」的人要**重新添加一次**。

**关于旧机 302：本次决定不做（2026-10-23 用户拍板）。**
理由：旧网址本来就是测试地址，且已提前通知团员换网址。旧机应用停掉后旧网址返回 **502**，属预期。
> ⚠️ 若将来再切一次、且**不能**让用户换地址，则旧机 nginx 应改成
> `return 302 https://<新IP>$request_uri;`（**用 302 不用 301**，避免浏览器永久缓存旧跳转）。

**回滚口径**：旧机应用 `sudo systemctl enable --now band` 即可恢复（数据和 jar 都还在）。
⚠️ 若新机**已经产生新数据**（有人登录/上传），必须先把新机库 dump 回旧机再切，否则丢数据。

## 12.7 上线检查清单

照 §12.6 手册做完一遍后，逐条用下面这些**判据**核。**"做过没"不写在这里**——
状态的权威是 `交接单.md`（`work_log.md` 里有 2026-09-23 首次上线逐条走完的记录）；
**本节只回答"怎么算通过"**，所以将来换服务器时可以直接照它重跑。

| 项 | 怎么验证（判据） |
|---|---|
| 服务能开机自启 | `sudo reboot` 后**从外网**访问 `https://<IP>` 返 `200` |
| **重启服务器后数据还在** | 重启后能正常登录，`member` 表行数不变 |
| 备份任务跑过，**且成功恢复过一次** | `/var/backups/band/` 有当日两份非空文件；**恢复到临时库 `band_drill` 后行数与真库一致**（演练制度见 §12.5 硬要求 1） |
| **上传真的成功过一次** | 传一张照片 + 一段音频（mp3 或 m4a）→ **都成功**；随后 `ls -l /data/band/uploads/` 能看到刚落下的新文件。⚠️ **别只测一个类型**——三类（音频 / 图片 / 谱子 PDF）走的是同一段落盘代码，但权限/磁盘问题只在真写的时候暴露 |
| **上传目录的属主是服务账号，且真写得进去** | `ls -ld /data/band/uploads` → 属主是 `band`；再 `sudo -u band touch /data/band/uploads/probe && echo OK` → **必须打印 OK**。⭐ **这一条才是"能写"的判据**：只 `ls` 看不出来，目录属主不对时**启动与其它功能全都正常** |
| **上传目录 = 备份目录** | `application-local.yml` 里的 `band.storage.dir` 与备份脚本里出现的目录路径**逐字相同**（拿 §12.6 第 4 步那一行核对） |
| SSH 密钥登录生效、密码登录已禁 | `sudo sshd -T \| grep -i password` → `no`。⚠️ **必须读「生效值」**；`sshd_config.d/` 是**先到先得**（覆盖要写 `00-`），见 `SECURITY.md` F1 |
| 防火墙只开必要端口 | 腾讯云控制台防火墙仅放行 `22 / 80 / 443` |
| MySQL 未暴露公网 | `sudo ss -lntp \| grep 3306` → `127.0.0.1:3306` |
| 日志轮转生效 | `/opt/band/logs/{app,access}.log` 在写；`logback-spring.xml` 按天切分 + `maxHistory=30` |
| 证书签发与自动续期跑通至少一次 | `--staging` 一次通过 + `certbot renew --dry-run` 成功 + deploy hook（`nginx -s reload`）已配（见 §12.2.1 第 7 步）。⏳ **留一个自然复核点**：下一个续期窗口（≤6 天）看一眼证书日期确实被刷过 |
| 续期失败有告警 | `/opt/band/cert.sh` 挂在**同一个**每日 timer 上；**把阈值临时调大后会真收到邮件** |
| `SECURITY.md` 的 A~H | 逐节对照。**D（备份 / 留痕）、F（环境加固）在服务器侧核**；A / B / C / E / H 属**代码侧**，由实现方的集成测试覆盖 |
| **首屏资源是压缩传的** | `curl -H 'Accept-Encoding: gzip' -sI https://<IP>/css/bootstrap.min.css \| grep -i content-encoding` → 有 **`gzip`**（Nginx 层生效；直连 `:8080` 同判据，是 `server.compression`）。实测三份合计 **471KB → 117KB（约 −75%）**（见 §12.6 第 7 步，`交接单.md` `#131`） |
