> **这份文档解决什么**：线上（腾讯云轻量）出问题时，**按症状查**——"先跑哪条命令、看到什么说明什么、怎么修"。
>
> **三份文档的分工，别搞混**（这是本项目"同一件事只放一处"的延伸）：

## 16.1 怎么用这一份

1. **按症状查，不按时间**：先看 §16.4 的症状索引（S1、S2…），找到你那条，照"先跑这条"做。
2. **要完整来龙去脉**的，去 §16.5 案例库（C1、C2…）——索引给的是"最快判据"，案例给的是"为什么会这样、为什么以前查不出来"。
3. 手上的问题解决之后，**回头把它写成一条 S + 一条 C**（哪怕只写三行）。

## 16.2 怎么连上服务器

| 事 | 怎么做 / 坑在哪 |
|---|---|
| **登录用户是谁** | ⚠️ **是 `ubuntu`，不是 `root`**——`ssh root@<IP>` 会**一直** `Permission denied`（**不是网络问题**，是用户名不对）。分不清就进控制台点「**登录**」（网页终端）敲 `whoami` |
| 用密钥还是密码 | **密码登录已关**（`SECURITY.md` F1）⇒ **没有私钥就只能走控制台网页终端** |
| ⚠️ **密钥可能不在本机** | 2026-09-25 实测：本机 `~/.ssh/` 里**只剩 `known_hosts`**（`id_ed25519` / `id_rsa` 都没了），Windows 的 `ssh-agent` 服务是 `Stopped/Disabled` ⇒ `ssh ubuntu@<IP>` 报 `Permission denied (publickey)` |
| ⚠️ **两种原因的报错一模一样** | **"用户名拼错"** 与 **"本机没有私钥"** 都报 `Permission denied (publickey)`——**光看那行字分不出来**。判据：`ls -l ~/.ssh/`（看不到 `id_ed25519` / `id_rsa` 就是**没钥**） |
| ⭐ **兜底：控制台网页终端** | 腾讯云控制台 → 轻量应用服务器 → 实例 → 右上角「登录」。**不需要密钥**。进去先 `whoami` |
| ⚠️⚠️ **网页终端会吞中文** | VNC 粘贴**静默丢掉非 ASCII 字符**：实测敲 `grep 上传目录` 到服务器上变成**没有参数的 `grep`**（只打印用法）。⇒ **给远程终端的命令一律纯 ASCII**，中文参数换成英文/路径片段（`grep uploads`、`grep FileStorage`） |
| 控制台「重置密码」 | 要**重启实例**才生效 |
| 找服务器 IP | 控制台实例列表；⚠️ **别把 IP 写进仓库**（本仓库全篇用 `<IP>` 占位，因为仓库是公开的） |
| **恢复密钥登录** | 本机 `ssh-keygen -t ed25519 -f ~/.ssh/for_band -N ""` → 从网页终端把 `.pub` 追加进 `~/.ssh/authorized_keys`（`chmod 700 ~/.ssh`、`chmod 600 ~/.ssh/authorized_keys`）→ `ssh -i ~/.ssh/for_band ubuntu@<IP>`。<br>⚠️ **恢复完请在 `docs/12` 里记一句"钥放在哪个路径"**——这次丢了之所以一点线索都没有，就是因为**从来没记过** |

## 16.3 排查工具箱（常用判据命令）

| 命令 | 看到什么 = 说明什么 |
|---|---|
| `sudo journalctl -u band -n 100` | 服务日志。**看堆栈第一行**（尾部那些 `Suppressed:` 是伴随异常，不是根因） |
| `sudo systemctl status band` | 起没起、退出码。`203/EXEC` = 脚本缺 `#!/bin/bash`；`1/FAILURE` 的真因在 `journalctl` |
| `sudo journalctl -u band \| grep uploads` | 应用启动时打的那行**真实落盘目录**（⚠️ **别 grep 中文**，见 §16.2 的"吞中文"那条） |
| `ls -ld <目录>` | 属主与权限。⚠️ **只 `ls` 只能告诉你"属主是谁"，不能告诉你"你能不能写"** |
| ⭐ `sudo -u band touch <目录>/probe` | **以服务账号身份真写一个文件**——"能不能写"的**唯一**判据（2026-09-25 那次故障就靠它一句话定位）。记得删掉探针：`sudo rm -f <目录>/probe` |
| `df -h` | 磁盘满没满 |
| `sudo nginx -t` + `/var/log/nginx/error.log` | Nginx 配置是否正确 / 403 与 502 的真因 |

## 16.4 症状索引

| 症状号 | 症状 | 先跑这条 | 常见结论 |
|---|---|---|---|
| **S1** | 上传文件报「文件写入失败」（**其它功能都正常**） | `ls -ld /data/band/uploads` + `sudo -u band touch /data/band/uploads/probe` | **目录属主不对**（`sudo chown -R band:band`）或磁盘满。→ 案例 **C1** |
| **S2** | 服务起不来 / systemd 显示 `status=1/FAILURE` | `sudo journalctl -u band -n 50` | 多半是 `/opt/band/logs` 不存在（logback 用的是相对路径）⇒ `mkdir -p` + `chown`；`203/EXEC` ⇒ 脚本缺 shebang |
| **S3** | 站点外部打不开、但服务器本机 `curl` 正常 | **先查腾讯云控制台的防火墙** | 控制台的防火墙与系统防火墙**是两套**，80/443 要在**控制台**放行（最容易漏的一步） |
| **S4** | Nginx 回 403 | `/var/log/nginx/error.log` | 多半是"目录里没有 `index` 指的那份首页文件"（Ubuntu 欢迎页叫 `index.nginx-debian.html`，不叫 `index.html`） |
| **S5** | 证书签不出来 / 续期失败 | `certbot --version` | 版本 < 5.4 **不认 `--ip-address`** ⇒ 要用 **snap** 装；staging 与正式是**两套账号**，换正式前先 `certbot delete --cert-name <IP>` |
| **S6** | 备份任务没跑 / 不知道成没成 | `cat /opt/band/backup-status.json` | 时间戳 > 48h ⇒ 后台会标红（机制见 `docs/12` §12.5） |
| **S7** | 忘了管理员密码 | — | 走应急重置脚本（**无任何远程入口**，只能 SSH 上机器跑）；形态见 `SECURITY.md` F7 + `交接单` `#13` |
| **S8** | ssh 连不上（`Permission denied (publickey)`） | `ls -l ~/.ssh/` | ⚠️ **"用户名错"与"没私钥"报错一样**；本机没钥就走控制台网页终端（见 §16.2） |

## 16.5 案例库

### C1 · 上传全部失败，报「文件写入失败」（2026-09-25）

**症状**：管理员在线上传一个 5MB 的 mp3 → 报「文件写入失败」。
**关键事实**：**其它功能全正常**（能登录、能读、能改、能签到）——这一点最容易把人带偏成"应用有 bug"。

**判据（三条就够）**：

```
sudo journalctl -u band | grep uploads          # 拿到真实落盘目录
sudo ls -ld /data/band/uploads                  # 看属主
sudo -u band touch /data/band/uploads/probe     # 决定性一测
```

实测输出：

```
drwxr-xr-x 2 root root 4096 Sep 23 17:54 /data/band/uploads
touch: cannot touch '/data/band/uploads/probe': Permission denied
```

**真因**：**上传目录的属主是 `root`**（部署时用 `sudo mkdir` 建的），而应用以 **`band`** 账号运行
⇒ `band` 对这个目录**没有写权限** ⇒ 上传时 `Files.copy` 被内核拒绝 ⇒ 报成「文件写入失败」。

**修法**：`sudo chown -R band:band /data/band/uploads`
（**不用重启应用**：`Files.copy` 每次上传都现开目标路径，没有缓存的目录句柄。）

**为什么以前查不出来（这一节比修法值钱）**——两层"静默"叠在一起：

1. 应用启动只用 `Files.createDirectories(dir)`，而它**对已经存在的目录不校验可写性**
   ⇒ 目录存在就"成功"，于是**启动正常、`/api/health` 正常、其它功能全正常**，
   症状被推迟到"**第一次真正写文件**"的那一刻；
2. 异常在 `FileStorage` 里被压成一句「文件写入失败」、**且统一异常处理器对这类业务异常一个字都不打**
   ⇒ 界面和日志里都**看不到"权限"两个字**，排查被迫从"看日志"退化成"上服务器反推"。

⇒ **两道门里任何一道单独存在，这个故障都藏不住**；叠起来才变成"一个能正常启动、别的功能全好、却写不了文件的系统"。
**`交接单` `#47` 要修的就是第二层**（抛错时 `log.error` 打出**落盘目录 + 目标文件名 + 完整异常**）。

**顺带排除的两条**：落盘目录 = 备份目录（实测启动日志里那行是 `/data/band/uploads`，**与备份脚本备的是同一个**，
所以"录音没进备份"这个担心不成立）；角色 / 体积 / 格式 / Nginx（报错是**中文、由 Java 抛出** ⇒ 请求已经到达应用，
一步就排除了反代那一层）。

**哪一步本可以拦住它**：① 部署时建完目录就 `chown`（`docs/12` §12.6 第 5 步现在有了，2026-09-25 之前没有）；
② 启动时做一次"真写一个探针文件"的自检；③ 抛错时留住原始异常并打日志。

**六段式复盘**：见 `debug_log.md`（2026-09-24 那条，2026-09-25 补全根因）。
