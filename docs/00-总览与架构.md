# 00 · 总览与架构

## 0.1 项目是什么

给学校**民族管弦乐团**（约几十人）做的管理系统。全团团员登录使用。

核心用途：看排练与声部课安排、签到、查自己的出勤、上传练习录音、看曲目与谱子、回顾演出。
管理层维护名册、安排活动、统计考勤、管理曲目与演出档案。

## 0.2 架构

```
        ┌──────────────────┐
        │   后端 API 服务    │   Spring Boot + MySQL
        │   唯一数据源       │   所有业务逻辑与权限都在这一层
        └─────────┬────────┘
                  │  REST + Bearer Token
        ┌─────────┴─────────┐
        │                   │
   ┌────▼─────┐       ┌─────▼──────┐
   │  网页端   │       │  安卓 App   │
   │ 所有设备  │       │  安卓团员   │
   └──────────┘       └────────────┘
```

### 两条必须守住的架构约束

1. **两个客户端吃同一套接口，后端不为任何客户端做特化。**
   一旦某个接口为了 App 开特例，前后端分离就白做了。
2. **权限判定集中在 `PermissionService` 一处。**
   绝不散落成 `if (role == ADMIN)`——角色定义还会改（见 0.6 暂定项），散着写必然漏改。

## 0.3 技术栈

| 层 | 选择 | 说明 |
|---|---|---|
| 语言 | Java 17 (LTS) | |
| 框架 | Spring Boot 3.2.x | **不追最新版**——教程与搜索结果最多，卡住时能搜到答案 |
| 数据库 | MySQL 8.0 | |
| 持久层 | MyBatis-Plus | 国内 JD 出现率高、SQL 显式可见。理由与被否掉的 JPA 见 `DECISIONS.md` D2 |
| 鉴权 | 手写拦截器 + BCrypt | 期 1 不引 Spring Security。见 `DECISIONS.md` D6 |
| 网页端 | 原生 JS + Bootstrap 5（**自托管**） | 不引构建链；第三方文件随仓库走。见 `DECISIONS.md` D7 |
| 安卓端 | Kotlin + Android SDK + Retrofit | 期 2 做 |
| 部署 | `jar` + systemd + Nginx + certbot | **全程 HTTPS**（用 IP 地址证书过渡，免域名免备案）。见 `DECISIONS.md` D19 |

**认证方式**：`Authorization: Bearer <token>`，token 是**服务端存储的不透明随机串**（不是 JWT）。
理由见 `DECISIONS.md` D4 / D5。

## 0.4 分期

**不压硬日期**——以「能上线、被真人用起来」作为每期的完成标志。

| 期 | 内容 | 完成标志 |
|---|---|---|
| **期 0** | 打通链路：Spring Boot 本机跑起来 + 连上本机 MySQL + 写读一条数据 + `/api/health` | 浏览器能打开本机服务，数据能落库再读出 |
| **期 1** | 后端核心 + 网页端：登录、团员与声部、排练与声部课、签到、考勤、请假审批 | **团里真的有人用它签到了一次** |
| **期 2** | 安卓 App：登录 + 看安排 + 签到（功能刻意少于网页端） | App 用同一账号看到同一份数据；同时当移动平台开发课作业 |
| **期 3** | 曲目库 + 谱务 + 排练曲目关联 | 曲目可挂音频与谱子，排练能关联曲目 |
| **期 4** | 演出档案 + 演出曲目单 + 演出回顾 | |
| **期 5** | 练习录音（上传 / 播放 / 声部长点评） | |
| **期 6** | 历届成员展示 | |

> **排序原则**：按"最快产生真实价值"排，**不按技术依赖排**。
> 网页端先做是因为它覆盖所有人（含 iPhone / 鸿蒙）、开发最快，而且**它逼着你把接口定稳**——
> 之后 App 接一套已经稳定的接口，比两个客户端同时改轻松得多。
>
> **请假审批流排在期 1 的后半段**：它是"申请单 + 审批 + 状态机 + 两个界面"，会明显拉长工期。
> 先把签到跑起来让团员真用，再做请假。

## 0.6 暂定项汇总（**实现时不许当既定事实**）

这些条目是**当前按最简单方案实现、但已知将来会改**的。每一条都附了替补方案，
条件明朗后一次性拿出来讨论。

| # | 暂定内容 | 现方案 | 将来可能的改动 | 改动影响面 |
|---|---|---|---|---|
| T1 | **指挥的权限** | 不能管账号，只管排练与曲目 | 用户明说会改 | `PermissionService`（已集中，改动小） |
| T2 | **休团期间是否计入出勤分母** | 算（休团者仍算应到） | 要精确则需加 `member` 休团区间记录 | 考勤统计 |
| T3 | **谱子 / 音频附件是否全团公开** | 公开（登录即可下载） | 若要收紧，改的是**权限模型**不是界面 | `02-权限模型` + 文件鉴权 |
| T4 | **跨声部 / 声部内私下合练** | 期 1 不实现（排练=全团，分声部走声部课） | 将来 `event` 要支持"指定部分声部" | `04` 的 `event` 表 |
| T5 | **录音时长上限** | 3 分钟 | 可能放宽 | `08` |
| T6 | **节目单导出** | 要做（可打印 HTML） | 有时单独做海报，可能不需要 | `07` |
| T7 | **历届成员页是否公开** | 公开只读页（不需登录） | 可能改为仅登录可见 | `09` |
| T8 | **账号操作权限** | 全部收归管理员（团长不建号/不改角色/不重置密码） | 若团长日常建号需求变强，可能下放 | `02` 权限矩阵 |

**另有一条已记录的变更点（不是暂定，是确定会加）**：
用户明确说"排练=全团只是暂定，之后肯定会有更改——有时候有声部内私下的合练"。
`event` 表设计上预留，将来加回"跨声部合练"时需重新引入声部关联。

## 0.7 与作者其它项目的联动

本项目与作者的 CS 基础重学计划（操作系统 + 计算机网络）**互为锚点**：
HTTP 报文与状态码、TCP 连接管理、进程与线程、文件描述符、崩溃一致性——都是那个计划里的主题。
安卓端又与移动平台开发课重合。

**一个项目喂三个目标：课程作业 + 团里实用 + 求职作品。**
