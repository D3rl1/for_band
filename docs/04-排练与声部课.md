# 04 · 排练与声部课

## 4.1 这个板块解决什么

安排乐团的日常活动：**排练**（全团）、**声部课**（单声部）、**彩排**（演出前的走台），
并让团员看到自己该看到的那部分。

---

## 4.2 核心概念：三类活动，**不是一种活动的三个属性**

| 类型 | `kind` | 谁安排 | 面向谁 |
|---|---|---|---|
| **排练** | `REHEARSAL` | 团长 / 指挥 / 管理员 | **全团** |
| **声部课** | `SECTION_CLASS` | **声部长**（团长可改，须留痕） | **单个声部** |
| **彩排 / 走台** | `DRESS_REHEARSAL` | 团长 / 指挥 / 管理员 | 全团 |

> **这三者是不同的东西，不是"排练"身上的一个属性。**
> 设计初期曾把"分声部"当成排练的一个属性（`scope = 指定声部`），是错的——
> 用户明确指出"**排练和声部课是两方面**"：排练由团长安排，声部课由声部长安排，
> 且声部长**不能**安排排练。

---

## 4.3 数据模型

### `event`（统一活动表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `kind` | varchar | `REHEARSAL` / `SECTION_CLASS` / `DRESS_REHEARSAL` |
| `title` | varchar(64) | 标题（如"周三例行排练"） |
| `date` | date | 日期 |
| `start_time` | time | 开始时间 |
| `end_time` | time | 结束时间（**签到窗口靠它算**） |
| `location` | varchar(64) NULL | 地点 |
| `section_id` | bigint NULL | **仅 `SECTION_CLASS` 有值**（单声部）；排练与彩排为 NULL |
| `content` | text NULL | 内容备注（期 1 用自由文本；期 3 升级为关联曲目，见 §4.5） |
| `batch_id` | varchar(36) NULL | 批量生成的批次标识，见 §4.4 |
| `status` | varchar | `NORMAL` / `CANCELED` |
| `created_by` | bigint | 创建人 |
| `created_at` / `updated_at` | datetime | |
| `updated_by` | bigint | 最后修改人（**H2 留痕靠它**） |

索引：`idx_date`、`idx_kind`、`idx_section_id`、`idx_batch_id`

> **为什么三类活动共用一张表**：字段差异极小（都只要时间 / 地点 / 状态，只有 `section_id`
> 是声部课独有），不值得拆表；而**拆表会让"某人出席率"这个统计变成两次 UNION**。
> 一张表则签到表只连一个外键，幂等唯一索引也完整。取舍理由见 `DECISIONS.md` D8。

## 4.4 业务规则与边界

### 取消（`CANCELED`）—— 四条可验收行为

**取消 ≠ 删除。** 记录保留、状态置 `CANCELED`。理由：删掉之后，"那周本来有活动后来取消了"
这件事就查不到了，而这类信息恰恰是纠纷的来源。

1. **前端：该条在列表里做暗色处理 + 标注「已取消」**
2. **不再允许签到**
3. **已产生的签到记录保留不删**，但**统计时整场排除**（分子分母都不计）
4. **该场不再产生任何新的考勤录入**

### 批量创建（因为"大部分固定、偶尔加排"）

提供**两个入口**：

| 入口 | 用途 | 参数 |
|---|---|---|
| **批量生成** | 一次生成一整段固定排练 | 星期几 + 开始/结束时间 + 起止日期 + 地点 + 面向（排练 or 声部课） |
| **单次创建** | 临时加排 | 单场完整信息 |

- **不做复杂的 RRULE 重复规则**：跳过节假日等由管理员事后单独取消 / 改期即可
- 同一批生成的场次**共享 `batch_id`**，便于界面上成组显示，也为将来的"批量改期"留口子
- **期 1 的修改是逐个改**（不做批量改期），但界面要能一眼看出"这 20 场是一个批次"

**时间校验（两个入口都要有，不是只管批量）**：

- **`start_time < end_time`**，否则拒绝；
- **单场活动不跨天**——`start_time`/`end_time` 都是 `time`（无日期），而签到窗口 = `end + 2h`，
  跨午夜会算到第二天去。民乐团没有跨天场景，直接禁掉最省事。
- 见 `13-数据模型总表.md` 不变式 12。

> 这两条**必须在服务端校验**（前端拦不住直接打接口的请求）。
> 实现时容易只在"批量生成"里拦、忘了"单次创建"这条路径——两条都要。

### 可见性（**越权防护的一部分，必须真的加过滤**）

| 角色 | 能看到 |
|---|---|
| 团员 | **「全团活动」+「本声部的声部课」**；其他声部的声部课**不可见** |
| 声部长 | 全部 |
| 指挥 / 团长 / 管理员 | 全部 |

> 注意：**不能只隐藏按钮，要在查询层就过滤掉**。

### 历史可见性

**团员可以看全部（历史 + 未来）。** 便于回顾"上周练了什么"、"我那几次是不是没去"。

### 内容填写权限与留痕（H2）

| 对象 | 谁写 | 谁可改 |
|---|---|---|
| 排练 / 彩排的 `content` | 团长 / 指挥 / 管理员 | 同上 |
| 声部课的 `content` | **声部长**（本声部） | 声部长 + **团长可改** |

**团长改了声部课的内容要留痕**（用户明确要求："要标注一下团长修改了的痕迹，
不然声部长完全不知情也不好"）：

- 记录 `updated_by` + `updated_at`
- **当 `updated_by ≠ created_by` 时，界面显式标注「已被 XXX 修改于 …」**，声部长一眼可见

> 完整的逐次修改历史（改了什么、改了哪几个字段）由 `11-日志与留痕.md` 提供，期 1 不做。

## 4.5 分两期实现（解耦 B 组与 C 组）

| 期 | 做法 |
|---|---|
| **期 1** | `content` 就是一段**自由文本**——"今天练《金蛇狂舞》前两段、加练打击乐"。**够用，且不阻塞期 1** |
| **期 3** | 新增 `event_piece(event_id, piece_id, order_no, note)`，使"这次练了哪些曲"可点开、可统计、可回顾 |

> 这样排的好处：**曲目库（`06`）不用为了活动而提前做**，两条线解耦。

## 4.6 接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/events` | 登录 | 活动列表（分页）。**按 §4.4 可见性过滤**。支持 `?from=&to=&kind=` |
| GET | `/api/events/{id}` | 登录 | 单个活动（同样过滤） |
| POST | `/api/events` | 见 §4.4 | 创建单场 |
| POST | `/api/events/batch` | 见 §4.4 | 批量生成 |
| PUT | `/api/events/{id}` | 见 §4.4 | 修改（**声部课被团长改时写留痕**） |
| POST | `/api/events/{id}/cancel` | 见 §4.4 | 取消（**不物理删除**） |

`POST /api/events` 的权限判定：
- `kind = SECTION_CLASS` → 声部长（限本声部）或管理员
- `kind = REHEARSAL` / `DRESS_REHEARSAL` → 团长 / 指挥 / 管理员
