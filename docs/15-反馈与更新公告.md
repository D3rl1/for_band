# 15 · 反馈与更新公告

## 15.1 这个板块解决什么

**两件小事，都是"让系统用起来更像一个正经产品"：**

1. **反馈**：团员遇到 bug 或觉得哪里别扭时，**有个地方说**——而不是发微信给你、或者干脆忍着。
   入口放在页面**右上角**（用户点名），提交后进自己的库，你在管理端看。
2. **更新公告**：你每次修完 bug / 更新完功能，团员**进入系统就能看到"本次改了什么"**——
   像其他 App 的 "what's new"。消除的是"咦怎么变了"和"我之前提的问题修了没"这两类来回问。

> ### ✅ 这两件事都**不依赖**通知渠道（重要，先看这条）
>
> `docs/00` 的暂定项 **T12** 写着"通知渠道未定，`notification_log` 只留表、不实现发送端"，
> U-1（新设备登录告警）因此一直卡着。**本板块与它无关**：
> - **反馈**是信息**进来**（团员 → 你），落自己的库，不需要往外发；
> - **更新公告**是**进系统时看到**（页内展示），不是手机推送。
>
> **所以不要因为"通知渠道还没定"就搁置这个板块**——那两条路互不相干。
> （哪天 T12 定了渠道，这两件事也能顺势升级：反馈可以顺推一条给你，公告可以顺推给团员。
> 那时候要动的是"发送端"，本板块的表与文案**不用改**。）

## 15.2 数据模型

**两张表，定义在 `13-数据模型总表.md` 的 ㉑ `feedback` 与 ㉒ `release_note`**
（`13` 是全库唯一权威，**表结构改动一律先改那里**）。这里只写**为什么这么设计**：

| 决定 | 理由 |
|---|---|
| `feedback` **不设幂等** | 连点两次就是两条反馈，属正常行为，**不该去重**。注意这与"踢会话幂等"恰好相反——那条是**同一个动作重试**，这条是**两个不同的诉求** |
| `feedback` 存 `page_path` | 定位问题的第一线索。"在活动详情页点了签到没反应"比"签到坏了"有用得多 |
| `feedback` 存 `user_agent` 原文 | 展示时按 `01` §1.4 那套**粗解析**成"设备"，与"登录设备"复用同一套规则（认不出来就说认不出来） |
| `release_note` 正文**纯文本 + 换行** | `SECURITY.md` C3 要求输出转义；走 `textContent` 最安全，也避免为一个公告栏引 md 渲染库 |
| `release_note` **发布后不可改不可删** | 团员读过的历史要稳定。要改就**再发一条**（与 `11` 对操作日志的立场一致） |

## 15.3 接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/feedback` | 登录（**荣誉团员除外**） | 提交反馈。入参 `{content, pagePath}`；**UA 由服务端从请求头取**，不信客户端传 |
| GET | `/api/admin/feedback` | 管理员 | 反馈列表（分页；`?status=` 可筛 `OPEN`/`HANDLED`） |
| PUT | `/api/admin/feedback/{id}` | 管理员 | 标记已处理 + 备注。入参 `{status, adminNote}` |
| GET | `/api/release-notes/latest` | 登录 | **最新一条**公告（给弹层用）。**一条都没有时返回 `data: null`** |
| GET | `/api/release-notes` | 登录 | 公告历史（分页，按 `published_at` 倒序） |
| POST | `/api/admin/release-notes` | 管理员 | 发布一条公告。入参 `{title, content}` |

**错误码**（沿用 `10` §10.5，**不新增码**）：

| 情形 | 码 |
|---|---|
| 反馈正文为空 / 超 1000 字 | `10001`（422） |
| 公告标题或正文为空 | `10001`（422） |
| 未登录 | `20002`（401） |
| 荣誉团员提反馈、非管理员调管理端 | `30001`（403） |

**排序**：两处列表都按 `id` 倒序（`10` §10.4 的默认排序）。公告历史若想按发布时间，
用 `published_at` 倒序——但**发布即按当前时间写**，所以两者一致，直接用 `id` 倒序即可。

## 15.4 反馈的规则与边界

### 谁能提

**所有登录角色，唯一例外是荣誉团员**——按 `02` §2.3 末尾的防腐条款"新功能默认不给荣誉团员"。
（他们只读，报 bug 也不该由他们承担；真有问题，在团的人会报。）

### 表单

- **正文**（多行文本框）：**必填**，1 ~ 1000 字。前后端都要校验（后端是真闸门）。
- **页面路径**：**前端自动带当前页**（如 `/event-detail.html?id=12`），用户**看不见、改不了**。
- **设备**：**服务端从 `User-Agent` 请求头取**，与登录时记录设备同源。
- 提交成功 → 提示"已收到，谢谢" → 关闭表单。**不显示"工单号"之类**——40 人的团不需要。

### 不做的事（**明确写出来，免得实现者自己加**）

- **不做频率限制**。40 人内部工具，连点两条是正常行为；加限流只会烦到真人。
- **不做匿名**。团里都是熟人，实名反而让"这是我遇到的"更可信，也避免拿反馈当发泄口。
- **不做截图上传**。要传图就直接发群里；为它引一套文件上传不划算。
- **不做"回复团员"**。处理结果只记 `admin_note`，**不给团员推回去**——
  推回去就需要通知渠道（T12）。真需要沟通直接线下/群里说。

### 管理端

- 列表：**提交人 / 时间 / 页面 / 设备 / 正文（截断） / 状态**。
- 默认按 id 倒序（新的在上）。
- 操作：**标已处理 + 备注**。已处理的条目**不再出现在默认视图**（`?status=OPEN` 是默认），
  避免堆积成一堆"看过了但要一直滚过去"的条目。
- **「处理反馈」不进 `11` §11.3 的操作日志**：`feedback` 表自带 `handled_by` / `handled_at`，
  进操作日志是同一件事记两遍。

## 15.5 更新公告的规则与边界

### 谁能发布 / 谁能看

- **发布：仅管理员**（属"系统层"，与 `02` §2.3 一致）。
- **看：所有登录角色，含荣誉团员**。
  ⚠️ 这是对防腐条款"新功能默认不给荣誉团员"的**有意例外**，理由：**公告是纯只读信息**，
  而荣誉团员的定位正是"只读的过去"；不给他们会让"进系统会看到更新"这件事在新老角色间不一致，
  反而制造两类体验。**这条例外必须留在 `02` §2.3 的荣誉团员节里**，别只写在这里。

### 写与发

- 表单：**标题**（≤64 字）+ **正文**（纯文本，多行）。
- **一次手写一条 = 一次发布**。发布即写 `published_at`。
- **不从 `work_log.md` 自动生成**：`work_log` 是开发向的（写的是"改了哪个类、补了哪条测试"），
  给团员看的是**人话**（"签到加了确认，不会再手滑点错"）。两者受众不同，**不共用一份文本**。
- **发布后不可改、不可删**——要改就再发一条。

### 弹层（"进系统时看到本次更新"）

| 项 | 口径 |
|---|---|
| **触发时机** | **登录成功那一次**，且**欢迎过渡播完之后**（见下方"三者顺序"）|
| **弹什么** | **最新的一条**公告（`GET /api/release-notes/latest`）|
| **弹几次** | **每个版本一次**。"版本" = 公告的 `id`：`latest.id` **大于**本机记过的 id 才弹 |
| **已读记在哪** | **`localStorage` 的 `band_seen_release`**（存 id）。**这是设备级、不是账号级**——理由见下 |
| **首次使用** | 本机**没有任何记录时也要弹**（视为"有未读"）。理由：上线第一条公告（"系统上线了"）**正是要给所有人看的**，那时人人都是"首次" |
| **没有公告** | **不弹、不占位、不出空层**（`latest` 为 `null` 时直接跳过）|
| **内容形态** | 标题 + 正文（`textContent` + 保留换行的 CSS，**不解析 HTML / markdown**）|
| **按钮** | 「知道了」（关掉并记已读）；若还有更早的公告，另给一个「查看全部更新」→ `updates.html` |
| **可跳过** | 点任意处 / Esc 都能关（与欢迎过渡同一套规矩：**绝不能不让人关**）|
| **`prefers-reduced-motion`** | 不播入场动画，直接显示（与欢迎过渡一致）|
| **z-index** | **取 120**——高于欢迎过渡黑幕（`.wel` = 90），低于 toast（2000）与 oneko（最大整数）。**这里给出书面值**，别让实现者自己拍（个人栏那次就因为"docs 无书面值"留了个待办）|

**为什么"已读"是设备级而不是账号级**：账号级要在 `member` 加一列、或新开一张已读表，
而换来的收益只是"换台设备不再看到一次"。对一条**更新说明**来说，换设备再看到一次**无害甚至合理**
（用户本来就可能在不同设备上看）。符合本项目"规模到了再升层、不提前设计"的一贯口径。
—— **代价要写清楚**：清浏览器数据 / 换设备 / 换浏览器会**再弹一次**。这是**已知的、可接受的**。

### ⚠️ 三者顺序（**必须写死，别让实现者自己排**）

登录成功那一次，页面上**有三个东西想同时动**：欢迎过渡（全黑遮罩飞头像）、本弹层、oneko 猫。
`14` §14.6.4 已经记过一次同类事故——"**一只猫从欢迎过渡的黑幕上跑过去**"，原因是**猫加载太早**。

**顺序（固定）：**

```
登录成功 → 欢迎过渡播完（或用户跳过）
        → 有未读公告 → 弹「本次更新」
        → 公告关掉之后 → 才加载 oneko
```

- **公告弹层可以在欢迎过渡之后出现**，但**oneko 必须等公告关掉**——它的 `z-index` 是最大整数，
  不等就会被它压过去（和当初那只猫一模一样的坑）。
- **没有未读公告时**：欢迎过渡播完 → 直接加载 oneko，中间的公告环节**整个跳过**（不留空档、不留空白帧）。
