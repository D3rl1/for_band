# 15 · 问题讨论与更新公告

## 15.1 这个板块解决什么

**两件事，都是"让信息不再单向"：**

1. **问题讨论**：团员遇到 bug 或觉得哪里别扭时，**在系统里公开提**；
   所有人都能看见这个问题、下面的回帖、以及它**处理到哪一步**。
   不再是"提交进一个只有管理员能看的信箱，然后没有下文"。
2. **更新公告**：管理员修完 bug / 更新完功能，团员**进入系统就能看到"本次改了什么"**——
   像其他 App 的 "what's new"。

> ### ✅ 这两件事都**不依赖**通知渠道（重要，先看这条）
>
> `docs/00` 的暂定项 **T12** 写着"通知渠道未定，`notification_log` 只留表、不实现发送端"，
> U-1（新设备登录告警）因此一直卡着。**本板块与它无关**：
> - **问题讨论**是"**在系统里公开**"：状态和回帖就摆在问题下面，团员自己回来看，不需要往外推送；
> - **更新公告**是**进系统时看到**（页内展示），不是手机推送。
>
> **所以不要因为"通知渠道还没定"就搁置这个板块**——两条路互不相干。
> 真到了"必须主动告诉某个人"的程度（例如 @ 我），再看 T12。

### 和旧「反馈信箱」的关系（2026-10-26）

**公开栏取代旧反馈信箱，不并存。** 旧数据只把 `status='OPEN'`（待处理）的那批迁进公开栏，
其余保持私密、只进管理端的「历史反馈」只读归档（见 §15.10）。

**为什么不是"两个入口都留着"**：同一个功能给两个入口，用户不知道该点哪个，
写规格的人也迟早会维护出两套行为。旧入口在本次一并退役（前端浮层、`openFeedback`、相关 CSS、
`POST /api/feedback`、`PUT /api/admin/feedback/{id}`），**不留第二个"提问题"的地方**。

## 15.2 数据模型

**三张新表 + 一张旧表归档，定义在 `13-数据模型总表.md`**
（`13` 是全库唯一权威，**表结构改动一律先改那里**）：

| 编号 | 表 | 一句话 |
|---|---|---|
| ㉗ | `issue` | 问题主表：标题 / 正文 / 设备 / 状态 / 迁移来源 |
| ㉘ | `issue_comment` | 回帖与**系统状态时间线**（`USER` / `SYSTEM`） |
| ㉙ | `issue_reaction` | 「我也遇到」+1，`(issue_id, member_id)` 一人一条 |
| ㉑ | `feedback` | **归档**：不再产生新行；`status` 增加 `MIGRATED` |
| ㉒ | `release_note` | 更新公告（本次不改） |

这里只写**为什么这么设计**：

| 决定 | 理由 |
|---|---|
| **不设缓存计数列**（回帖数 / +1 数读时 `COUNT`） | 团级数据量（几十人、几百条），读时数一下就够了；加缓存列反而要维护"什么时候加、什么时候减"，是自找的一致性负担 |
| `issue.updated_at` **只在回帖 / 改状态时更新**，编辑与 +1 **不更新** | 列表排序和导航红点只该反映"**讨论或状态真的动了**"；有人点了个 +1、或作者改了个错别字，不该把旧帖顶成新动态 |
| 状态变更写一条 `kind='SYSTEM'` 回帖，**不另建历史表** | 公开栏要的就是"改没改、什么时候改的、为什么"；系统回帖本身就是时间线，再开一张表是同一件事记两遍 |
| `issue.source_feedback_id` **唯一** | 迁移脚本可能被重跑；唯一键让"同一条旧反馈只能迁一次"由数据库兜底 |
| `issue_comment` **扁平、不嵌套** | 团内讨论不需要楼中楼；扁平时间线更好读，也少一层权限判断 |
| `feedback.status` 增加 `MIGRATED` | 迁走的那批要能一眼认出来；`MIGRATED` **只由迁移写入**，新反馈不再产生 |
| 所有用户内容**纯文本** | `SECURITY.md` C3：前端一律 `textContent` + `pre-wrap`，**不解析 HTML / Markdown** |

**外键顺序**（`13` §13.2 建表顺序）：`㉗ issue → member, feedback`；
`㉘ issue_comment → issue, member`；`㉙ issue_reaction → issue, member`。

## 15.3 接口清单

> 本节 10 条 `/api/issues*` 已于 **#227** 落地。

### 15.3.1 问题讨论

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/issues` | 登录（**含荣誉团员**） | 列表分页：`?page=&size=&status=&mine=1`。默认 `updated_at DESC, id DESC`。返回 `{list,total,page,size}` |
| GET | `/api/issues/{id}` | 登录（含荣誉团员） | 详情 + **全部回帖按 `created_at ASC, id ASC`**（团级数据量，不分页）+ `reactionCount` / `reactedByMe` / `canEdit` |
| POST | `/api/issues` | 登录，**荣誉团员除外** | 发问题：`{title, content, deviceInfo, pagePath?}`；**`User-Agent` 由服务端从请求头取** |
| PUT | `/api/issues/{id}` | **作者本人**，荣誉团员除外 | 改标题 / 正文 / 设备：`{title, content, deviceInfo}`；写 `edited_at`，**不更新 `updated_at`** |
| POST | `/api/issues/{id}/comments` | 登录，荣誉团员除外 | 回帖：`{content}`；**更新 `updated_at`** |
| PUT | `/api/issues/{id}/comments/{commentId}` | **作者本人**，且 `kind='USER'` | 改回帖：`{content}`；写 `edited_at`，不更新 `updated_at` |
| PUT | `/api/issues/{id}/status` | **仅管理员** | `{status, reason?}`。同状态 = 成功空操作；变状态 = 更新 + 写系统回帖；`REJECTED` **必填 `reason`** |
| POST | `/api/issues/{id}/reaction` | 登录，荣誉团员除外 | 幂等 +1；**作者点自己 = 成功空操作**（界面也不渲染按钮） |
| DELETE | `/api/issues/{id}/reaction` | 同上 | 幂等取消；返回 `{reactionCount, reactedByMe:false}` |
| GET | `/api/issues/activity` | 登录（含荣誉团员） | `{latestUpdatedAt}`；一条问题都没有时 `data` 里为 `null`。**只给导航红点用** |

**列表项字段**：`id` / `title` / `authorName` / `status` / `commentCount` / `reactionCount` /
`lastActivityAt`（即 `updated_at`）/ `createdAt`。

**详情额外字段**：`content` / `deviceInfo` / `pagePath` /
`statusChangedByName` + `statusChangedAt` / `editedAt` / `canEdit`。
原始 `user_agent` **只在库里留作排查，不下发前端**（用户填的 `deviceInfo` 才是给人看的）。
每条回帖带 `kind` / `memberName`（系统行为 `null`）/ `oldStatus` / `newStatus` / `editedAt` / `canEdit`。

### 15.3.2 旧反馈接口的处理

| 方法 | 路径 | 处理 |
|---|---|---|
| GET | `/api/admin/feedback` | **保留**，改为**只读归档**；`?status=` 支持 `OPEN` / `HANDLED` / `MIGRATED` |

**已随 #227 退役**：`POST /api/feedback`（删路由、删前端入口与浮层）、
`PUT /api/admin/feedback/{id}`（归档页不再有处理操作）。旧行只读，不再产生新的旧反馈。

### 15.3.3 更新公告（不变）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/release-notes/latest` | 登录 | **最新一条**公告（给弹层用）。**一条都没有时返回 `data: null`** |
| GET | `/api/release-notes` | 登录 | 公告历史（分页，按 `published_at` 倒序） |
| POST | `/api/admin/release-notes` | 管理员 | 发布一条公告。入参 `{title, content}` |

### 15.3.4 错误码（沿用 `10` §10.5，**不新增码**）

| 情形 | 码 |
|---|---|
| 标题 / 正文 / 回帖 / 设备 / 理由为空或超长 | `10001`（422），`data.field` 指明字段 |
| 状态值不在四档内；`REJECTED` 没给理由 | `10001`（422） |
| 问题 / 回帖不存在 | `10002`（404） |
| 未登录 | `20002`（401） |
| 非管理员改状态；荣誉团员发帖 / 回帖 / +1 / 编辑 | `30001`（403） |
| 编辑**别人**的问题 / 回帖 | `30002`（403） |
| 编辑系统回帖（`kind='SYSTEM'`） | `30001`（403）——它不属于任何团员 |
| 非管理员看历史反馈归档 | `30001`（403） |

**排序与分页**：列表 `updated_at DESC, id DESC`；回帖时间线 `created_at ASC, id ASC`；
列表默认 `page=1&size=20`，`size` 上限 100（沿用 `10` §10.4）；**回帖不分页**。

## 15.4 问题讨论的规则与边界

### 谁能发 / 谁能看

- **看**：所有登录角色，**含荣誉团员**（只读）。
- **发问题 / 回帖 / +1 / 编辑自己的内容**：所有登录角色，**荣誉团员除外**
  （按 `02` §2.3 防腐条款：这些都是"动作"，不是只读）。
- **改状态**：**仅管理员**。团长、指挥、声部长、团员一律 ❌（2026-10-26 用户拍板）。

### 发问题的表单

- **标题**：必填，trim 后 1 ~ 50 字，**纯文本**。
- **正文**：必填，trim 后 1 ~ 2000 字，多行。
- **运行环境（`deviceInfo`）**：**必填**，1 ~ 100 字，例如「小米 14 / Android 15」。
  表单用**粗粒度 UA 解析**预填（能认出 Android/iOS 与可得品牌型号就填，认不出就留空让用户写），
  **用户可改**；**空着不让提交**。
- **页面路径（`pagePath`）**：前端自动带 `location.pathname + location.search`，**不进表单**、用户看不见。
- **UA 原文**：服务端从 `User-Agent` 请求头取，**不信客户端传**。
- 提交成功 → 提示「已提交，大家都能看到了」→ 关闭表单，列表顶部出现新条目。

### 编辑

- **作者可以改自己发的问题与自己的 `USER` 回帖**；改完在内容旁显示「已编辑」。
- **编辑不更新 `updated_at`**——错别字修正不该把帖子顶成新动态。
- **不允许删除**（没有删除接口，前端也不放删除按钮）。
  真需要撤内容，由管理员改状态并说明，**时间线保留**。

### 回帖

- 1 ~ 1000 字，纯文本；**扁平结构、不嵌套**；不做 @、不做楼中楼。
- 回帖**会更新 `issue.updated_at`**（这是真动态，列表与红点应该动）。
- 系统回帖（`kind='SYSTEM'`）**不可编辑、不可删除**，`member_id` 为 `NULL`。

### 状态（四档）

| 存储值 | 界面文案 | 颜色 |
|---|---|---|
| `PENDING` | 待处理 | 中性：`--surface-2` 底 + 墨色字 |
| `PROCESSING` | 处理中 | 中性：同上 |
| `FIXED` | 已修复 | **绿**：`--accent-weak` 底 + `--accent-ink` 字 |
| `REJECTED` | 不处理 | **朱砂**：中性底 + `--danger` 字 / 描边 |

- 四档**任意方向可改**（含回退：已修复 → 处理中）。讨论栏不是审批流，允许反复；每次变更都留痕。
- **每次真正的状态变更必须写一条 `kind='SYSTEM'` 回帖**（同一事务，见 `13` 不变式 18）：
  `old_status` / `new_status` 记前后值，`content` 写理由；没给理由时写「状态改为「已修复」」。
- **`REJECTED` 必须填理由**（1 ~ 255 字），理由进系统回帖正文。
- **同一个状态 = 成功空操作**：不改库、不写系统回帖、不报错（前端连点两下很正常）。
- 状态标签**红不许表示"做好了"**：成功态只能绿，朱砂只用于「不处理」这种负向终态。

### 「我也遇到」（+1）

- 一人一票，**可取消**；`(issue_id, member_id)` 唯一，重复点一律成功、计数不变。
- **作者自己的 +1 按钮不渲染**；就算直接打接口也**成功空操作**（不落行）。
- **+1 不更新 `updated_at`**：有人点了「我也遇到」不该把帖子顶成新动态。

### 渲染

- 标题、正文、回帖、设备信息、理由一律 **`textContent`**；正文与回帖用 `white-space: pre-wrap`。
- **不解析 HTML / Markdown**（`SECURITY.md` C3）。这是一条硬红线，不是风格偏好。

### 明确不做（免得实现者自己加）

- **不做删除**（问题 / 回帖都不删）。
- **不做截图 / 附件**。要传图直接发群里；为它引一套文件上传不划算。
- **不做 Markdown / 富文本**。
- **不做标签、置顶、指派、@ 提醒、楼中楼**。
- **不做全文搜索**（条目多到翻不动时再说，见 §15.8）。
- **不做匿名**：团里都是熟人，实名让「这是我遇到的」更可信。
- **不做发帖频率限制**：内部工具，连点两条是正常行为；真出刷屏再治理。
- **不做个人通知中心 / 邮件 / 推送**：公开栏自己就是"回推"，见 §15.8 F1。

### 管理端

- 管理员在**详情页**直接改状态（下拉四档）；`REJECTED` 弹理由输入框。
- **没有单独的"问题管理"页**：公开栏本身就有状态筛选，管理员看到的和大家看到的是同一份数据。
- **「改问题状态」不进 `11` §11.3 的操作日志**：`issue.status_changed_by/at` + 系统回帖已经是完整留痕，
  再进操作日志是同一件事记两遍（判断标准与旧反馈一致）。

## 15.5 更新公告的规则与边界

### 谁能发布 / 谁能看

- **发布：仅管理员**（属"系统层"，与 `02` §2.3 一致）。
- **看：所有登录角色，含荣誉团员**。
  ⚠️ 这是对防腐条款"新功能默认不给荣誉团员"的**有意例外**，理由：**公告是纯只读信息**，
  而荣誉团员的定位正是"只读的过去"；不给他们会让"进系统会看到更新"这件事在新老角色间不一致，
  反而制造两类体验。**这条例外必须留在 `02` §2.3 的荣誉团员节里**，别只写在这里。

### 写与发

- 表单：**标题**（≤64 字）+ **正文**（纯文本，多行）。
- **一次手写一条 = 一次发布**。发布即写 `published_at`。
- **不从 `work_log.md` 自动生成**：`work_log` 是开发向的（写的是"改了哪个类、补了哪条测试"），
  给团员看的是**人话**（"签到加了确认，不会再手滑点错"）。两者受众不同，**不共用一份文本**。
- **发布后不可改、不可删**——要改就再发一条。

### 弹层（"进系统时看到本次更新"）

| 项 | 口径 |
|---|---|
| **触发时机** | **登录成功那一次**，且**欢迎过渡播完之后**（见下方"五者顺序"）|
| **弹什么** | **最新的一条**公告（`GET /api/release-notes/latest`）|
| **弹几次** | **每个版本一次**。"版本" = 公告的 `id`：`latest.id` **大于**本机记过的 id 才弹 |
| **已读记在哪** | **`localStorage` 的 `band_seen_release`**（存 id）。**这是设备级、不是账号级**——理由见下 |
| **首次使用** | 本机**没有任何记录时也要弹**（视为"有未读"）。理由：上线第一条公告（"系统上线了"）**正是要给所有人看的**，那时人人都是"首次" |
| **没有公告** | **不弹、不占位、不出空层**（`latest` 为 `null` 时直接跳过）|
| **内容形态** | 标题 + 正文（`textContent` + 保留换行的 CSS，**不解析 HTML / markdown**）|
| **按钮** | 「知道了」（关掉并记已读）；若还有更早的公告，另给一个「查看全部更新」→ `updates.html` |
| **可跳过** | 点任意处 / Esc 都能关（与欢迎过渡同一套规矩：**绝不能不让人关**）|
| **`prefers-reduced-motion`** | 不播入场动画，直接显示（与欢迎过渡一致）|
| **z-index** | **取 120**——高于欢迎过渡黑幕（`.wel` = 90），低于 toast（2000）与 oneko（最大整数）。**这里给出书面值**，别让实现者自己拍（个人栏那次就因为"docs 无书面值"留了个待办）|

**为什么"已读"是设备级而不是账号级**：账号级要在 `member` 加一列、或新开一张已读表，
而换来的收益只是"换台设备不再看到一次"。对一条**更新说明**来说，换设备再看到一次**无害甚至合理**
（用户本来就可能在不同设备上看）。符合本项目"规模到了再升层、不提前设计"的一贯口径。
—— **代价要写清楚**：清浏览器数据 / 换设备 / 换浏览器会**再弹一次**。这是**已知的、可接受的**。

### ⚠️ 五者顺序（**必须写死，别让实现者自己排**）

登录成功那一次，页面上**有五个东西想同时动**：欢迎过渡（全黑遮罩飞头像）、本弹层、
**生日通告弹层**（规格见 `14` §14.6.4「生日通告」）、**上任留言弹层**（`03` §3.5、`14` §14.6.4）、oneko 猫。
`14` §14.6.4 已经记过一次同类事故——"**一只猫从欢迎过渡的黑幕上跑过去**"，原因是**猫加载太早**。

**顺序（固定；2026-09-24 由三者扩为四者，2026-10-01 加上任留言后为五者）：**

```
登录成功 → 欢迎过渡播完（或用户跳过）
        → 有未读公告 → 弹「本次更新」
        → 有今天的寿星 → 弹「生日通告」
        → 新任声部长有未读留言 → 弹「上任留言」
        → 三个弹层都关掉之后 → 才加载 oneko
```

- **三个弹层都排在欢迎过渡之后**，但**oneko 必须等它们都关掉**——它的 `z-index` 是最大整数，
  不等就会被它压过去（和当初那只猫一模一样的坑）。
- **生日通告接在更新公告之后、上任留言接在生日之后**（2026-09-24 / 2026-10-01 加）
  ——**不动上面既有那几步的顺序，新的接在后面**。
- **没有未读公告 / 没有寿星 / 没有待读留言时**：对应那一环**整个跳过**
  （不留空档、不留空白帧、不出空层）。
- **三个弹层各自去重、互不代偿**：公告 `band_seen_release` 存 `id`、生日 `band_seen_birthday` 存**日期**、
  上任留言 `band_seen_section_note` 存 `noteId`。**关掉一个不代表另一个已读**。
- **上任留言不是全团都会弹**：只有"此刻在任 + 该声部最新一条不是自己写的 + 还没读过"三条同时成立
  （判据见 `03` §3.5），才对那位声部长出现。

## 15.10 历史反馈迁移（只迁 `OPEN`）

**用户原话**：「把标记为待处理的反馈加进公开栏，其它的就不公开了」。

### 15.10.1 只迁这些

- `feedback.status = 'OPEN'` → 迁成 `issue`。
- `HANDLED` 与其它旧行 **一律不迁**，只在管理端「历史反馈」里只读展示。
- **不迁 = 不公开。** 旧反馈原本的预期读者只有管理员，不能顺手把全部历史都翻出来。

### 15.10.2 一条旧反馈怎么变成一条问题

| 字段 | 取值 |
|---|---|
| `member_id` / `content` / `page_path` / `user_agent` | **原样保留** |
| `created_at` | **保留原反馈时间**（历史不能被改写成迁移日） |
| `status` | `PENDING`（待处理） |
| `device_info` | `NULL`（旧表单没有这一项） |
| `updated_at` | **迁移时刻**（让迁入的问题出现在列表顶部，而不是沉到旧时间里） |
| `source_feedback_id` | 旧 `feedback.id`（唯一键，保证幂等） |
| `title` | 取正文**首行** trim：≤50 字原样；>50 字取前 **49** 字 + 「…」（**总长不超过 50**）；首行为空 → 「历史反馈 #<旧 id>」 |

每条迁入的问题再写一条系统回帖：`kind='SYSTEM'`、`content='由历史反馈迁入'`。

### 15.10.3 旧行怎么收尾

`feedback.status = 'MIGRATED'`，并在 `admin_note` **追加**（不覆盖）：
`已迁入问题讨论 #<新 issue id>（2026-10-26）`。

### 15.10.4 幂等写法（放 `sql/schema.sql` 末尾）

```sql
-- ① 迁主表：只迁 OPEN，且 source_feedback_id 唯一兜底
INSERT INTO issue
  (member_id, title, content, device_info, user_agent, page_path,
   status, source_feedback_id, created_at, updated_at)
SELECT f.member_id,
       COALESCE(
         NULLIF(
           CASE WHEN CHAR_LENGTH(TRIM(SUBSTRING_INDEX(TRIM(f.content), '\n', 1))) > 50
                THEN CONCAT(LEFT(TRIM(SUBSTRING_INDEX(TRIM(f.content), '\n', 1)), 49), '…')
                ELSE TRIM(SUBSTRING_INDEX(TRIM(f.content), '\n', 1))
           END, ''),
         CONCAT('历史反馈 #', f.id)),
       f.content, NULL, f.user_agent, f.page_path,
       'PENDING', f.id, f.created_at, NOW()
FROM feedback f
WHERE f.status = 'OPEN'
  AND NOT EXISTS (SELECT 1 FROM issue i WHERE i.source_feedback_id = f.id);

-- ② 给迁入的问题补系统回帖（重跑不会重复）
INSERT INTO issue_comment (issue_id, member_id, kind, content, created_at)
SELECT i.id, NULL, 'SYSTEM', '由历史反馈迁入', i.updated_at
FROM issue i
WHERE i.source_feedback_id IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM issue_comment c
    WHERE c.issue_id = i.id AND c.kind = 'SYSTEM' AND c.content = '由历史反馈迁入'
  );

-- ③ 旧行置 MIGRATED，并追加备注
UPDATE feedback f
JOIN issue i ON i.source_feedback_id = f.id
SET f.status = 'MIGRATED',
    f.admin_note = CONCAT(
      COALESCE(f.admin_note, ''),
      CASE WHEN f.admin_note IS NULL OR f.admin_note = '' THEN '' ELSE '\n' END,
      '已迁入问题讨论 #', i.id, '（2026-10-26）'
    )
WHERE f.status = 'OPEN';
```

> **SQL 只是示意**，实现方按 `13` 的字段与 `sql/schema.sql` 现有风格落地；
> 关键是三件事：**只动 `OPEN`**、**`source_feedback_id` 唯一**、**`NOT EXISTS` 可重跑**。

### 15.10.5 发布与核对

**发布顺序**：停服 → 备份数据库 → 换 jar → 跑 `sql/schema.sql` → 起服。

跑之前先预览：

```sql
SELECT COUNT(*) FROM feedback WHERE status = 'OPEN';
```

跑之后核对（两个数必须相等）：

```sql
SELECT COUNT(*) FROM issue WHERE source_feedback_id IS NOT NULL;
SELECT COUNT(*) FROM feedback WHERE status = 'MIGRATED';
```

### 15.10.6 隐私提醒（写给出规格的人自己看）

旧反馈是**按私信预期写的**。用户已经明确同意只公开 `OPEN` 那批；**其它行不得顺手迁**。
迁移脚本上线后不要"再补迁一次"——`MIGRATED` 之外的行是刻意保持私密的。

## 15.11 导航红点（板级未读，不是个人通知）

### 15.11.1 口径

- 红点挂在主导航**「问题讨论」**这一项上。
- **板级**：**任何**问题有了新回帖 / 状态变更（即 `issue.updated_at` 前进了）就亮；
  **不是**"有人回了我"。编辑与 +1 **不亮**。
- 点开 `issues.html` 或 `issue-detail.html` 后熄灭。

### 15.11.2 判定

| 项 | 做法 |
|---|---|
| 服务器端 | `GET /api/issues/activity` → `{latestUpdatedAt}`；没有问题时为 `null` |
| 本机已读 | `localStorage['band_seen_issue_activity']` 存 ISO 字符串（与 `band_seen_release` 同思路，**设备级**） |
| 亮 | `latestUpdatedAt` 非空，且 **大于** 本机存的值（同一 ISO 格式，可直接字符串比较） |
| 灭 | 打开两个问题页之一时，把当前 `latestUpdatedAt` 写入本机 |
| 首次使用 | 本机没有记录 → **视为有未读**（公开栏刚上线时，人人该看到一次） |

### 15.11.3 实现要点

- `band-shell.js` 的 `menuMarkup` 给每行加 `data-dot` 占位；新增 `refreshIssueDot()`，只作用于「问题讨论」那一行。
- **必须在 `renderNav` 的两条路径都调用**：复用分支（`paintNav(cachedMe)` / `paintNav(me)` 之后）
  与首次挂载分支（已有 `refreshReleaseDot()` / `refreshSectionNoteDot()` 的那一处）。
  复用分支漏了刷新，就会出现「回到页面红点不更新」。
- 视觉：复用 `.hact-dot` 的尺寸 / 颜色（7×7、`--cinna`），但**另起 `.ndot`** 挂在导航图标上；
  `.rail .menu a .ic` 补 `position: relative`。
- **不做轮询**：只在页面加载与 `renderNav` 时查一次；用户正在页面上时来新回帖，下一次导航再亮。
- **换人同机可能少一次提示**：设备级 localStorage 的已知代价，团级场景接受（与更新公告一致）。
