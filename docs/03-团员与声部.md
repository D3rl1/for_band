# 03 · 团员与声部

## 3.1 这个板块解决什么

维护"谁是这个团的人、在哪个声部、现在还在不在团"，并让**历史记录不因为人员变动而失真**。

---

## 3.2 数据模型

### `section`（声部）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `name` | varchar(32) | 声部名 |
| `order_no` | int | 显示顺序 |

**初始数据**（山水民族管弦乐团，**7 个声部、平级**）：
打击声部 · 提琴声部 · 胡琴声部 · 吹管声部 · 古扬声部 · 阮声部 · 琵琶声部

> ⚠️ **声部必须是数据（一张表），绝不能写死在代码里。** 各团编制不同、还会调整；
> 写成枚举的话，以后连加一个声部都要改代码。

> ⚠️ **声部是平级的，没有上下级**（表里没有 `parent_id`，不要加）。
> 曾经考虑过"弹拨声部下辖阮声部 / 琵琶声部"的两级结构，**已否掉**——
> 实际使用中直接就是两个平级声部，多设一个上级只是麻烦（用户决定）。
> 因此**"本声部"在权限判定里始终只有一个含义**，不用考虑递归子声部。
> 「古扬声部」同时含古筝与扬琴，两者差异记在 `member.instrument`。

> ⚠️ **2026-09-24：「声部管理」这个功能已删除**（用户决定）。
> 删掉的是**管理界面 + 两个写接口**（`POST /api/admin/sections`、`PUT /api/admin/sections/{id}`；
> 2026-09-25 落地，两个端点已从 §3.3 的接口清单里删掉——**它们不再存在**）——
> 用户原话是它"**形同虚设**"：名为"管理声部"，实际只能增 / 删 / 改名，而**实际运用中很难有合理的用法**。
> **保留的**：`section` 表本身、7 条初始数据（`DataSeeder.java`）、以及 **`GET /api/sections`**
> （名册筛选、团员表单、活动表单的**声部下拉都在用它**，别跟着一起删）。
> ⚠️ **连带后果（要认）**：以后要**加声部 / 改名 / 调顺序**，**只能直接改库**（写一条 SQL，
> 或改 `DataSeeder` 后清库重灌）。这与上面那条"**声部必须是数据、不能写死**"**不冲突**——
> 表还在、数据还在，只是"一次性设置"这个动作从界面挪到了库。
> **旁证**：上一次「4 个声部 → 7 个」实际也是改 `DataSeeder` + 清库重灌做的，**根本没走这个界面**，
> 说明日常确实用不到它。
> **将来若又要加声部**：先想清楚"要不要把这个界面加回来"，别默认它还在。

## 3.4 业务规则与边界

### 谁能改什么（2026-09-23 补 —— 一条容易搞混的边界）

`02` 的 **T8**「账号操作全部收归管理员」管的是**账号级动作**（建号 / 停用 / 改角色 / 改声部 /
重置密码 / 踢下线）——**它管的是"身份与权限"。**

**它不挡"本人自己的资料字段"**。这两类不是一回事：

| 字段 | 谁能写 | 依据 |
|---|---|---|
| `name` / `section_id` / `role` / `status` / `student_no` / `instrument` / `phone` / `note` | **仅管理员** | 身份、编制、以及管理员的工作备注——**改了人就乱了**（用户原话） |
| `avatar` / `intro` / `contact` / `birthday` | **本人 + 管理员**（⚠️ **荣誉团员除外**） | 这是"我自己的资料"，先例是 `alumni_message`（`09` §9.3 的端点权限就是「本人 / 管理员」）；管理员保留写入是为了**帮不会操作的人代填** |

> ⚠️ **`PUT /api/me/profile` 绝不能收 `memberId`**——收了就等于开了水平越权的口子
> （`SECURITY.md` A2 那个高危样板）。要改别人的资料，走管理员的 `PUT /api/admin/members/{id}`。

### `MemberView` 各字段的可见性（**唯一权威表**，2026-09-24 补）

⚠️ **为什么单列一张表**：`intro` / `contact` / `note` 原先**一处可见性都没写**，
`studentNo` 又和 `13` 的说法不一致（代码无条件返回）——散着写就必然漂。
**读侧裁剪只有一个生产点**：`MemberService.toView()`，下表就是它该做的事。

| 字段 | 谁能看 | 备注 |
|---|---|---|
| `id` / `name` / `sectionId` / `sectionName` / `instrument` / `role` / `status` | **全团**（登录即可） | 名册可见性，`02` §2.3 |
| `joinedAt`（入团年份）/ `leftAt` | **全团**（只到年份） | |
| `avatar` / `intro`（简介） | **全团** | "别人的主页"上要显示的就是这两样 |
| `birthday` | **本人 / 管理员**看全值；**别人只到「月-日」、不显示年份** | `13` §13.3。⚠️ **现状是"对外一律 `null`"**（比规格更保守），见 `交接单.md` `#8` |
| `contact`（联系方式） | **仅本人 + 管理员** | **2026-09-24 定**：它是自由文本（大家会写微信号 / QQ），与 `phone` 同级甚至更敏感 → **别人的主页上不出现** |
| `phone`（手机号） | **管理员 / 团长 / 指挥** | 既有口径，`02` §2.3 |
| `studentNo`（学号） | **本人 + 管理员** | 与 `T17` 同级隐私。⚠️ **现状是代码无条件返回（要改）** |
| `note`（管理员备注） | **仅管理员** | ⚠️ **原先没有任何规定**，现在定死：那是管理员的工作备注 |
| `account` / `activated` / `honoraryUntil` / `lastLoginAt` | **仅管理员** | 账号级信息 |
| 出勤率 / 请假次数 / 统计 | **仅本人**（`02` §2.3） | → **别人的主页上不显示** |

> ⚠️ **这张表是"读侧"口径**，上面「谁能改什么」那张是**写侧**口径——**两张别混**。
> 混起来就重演 T8 那次误用（拿"写侧"的限制去论证"读侧能不能看"）。

### 状态四态

`ACTIVE` 在团 · `PAUSED` 休团 · `LEFT` 退团 · `GRADUATED` 毕业

### 软删除：**绝不物理删团员行**

退团、毕业的人，其考勤、录音、演出历史都还挂着；物理删人会把历史一起切断。
一律用 `status` 标记。

### 状态变更的连带动作（**重要，容易漏**）

| 状态变化 | 必须同时做的事 |
|---|---|
| 任何状态 → 非 `ACTIVE` | ① **禁止登录** ② **立即作废其全部 token** |
| `ACTIVE` → `LEFT` / `GRADUATED` | 写入 `left_at`（**考勤统计靠它划边界**，见下） |
| 回到 `ACTIVE` | 清空 `left_at`（重新计算时按新的区间） |

> 第一条是安全漏洞的修补：不同时作废 token 的话，退团的人拿着 30 天有效期的旧 token
> 照样能看谱子、录音、成员手机号。

### `left_at` 与考勤统计的关系

考勤出勤率按**个人视角**计算：分母 = 该成员**「`joined_at` ~ `left_at`」区间内**的应到场次。

> **为什么不能按"当前在团成员"算应到**：某人退团后，他过去所有场次都不再算应到，
> 但他那时的签到记录还在 → **出勤率会算出超过 100%**。这是设计阶段自审抓出来的问题。
> 详见 `05-签到与考勤.md`。

### 兼声部

**不允许。** 一人一个声部。
好处：表结构最简单，且"本声部"在权限判定里只有一个含义。
兼声部的人归到他主要的那个声部即可。

### 声部长不设冗余字段

**声部长 = `role = SECTION_LEADER` 且 `section_id = X` 的那个人**，由两个字段直接推出。

**"每个声部最多一个声部长"这条约束在应用层校验**（改角色时检查该声部是否已有声部长）。

> 不单独存一个"本声部负责人"字段的理由：**存两处就会有两处不一致的可能**。

### 名单维护权限

**仅管理员**（建号 / 停用 / 改声部与角色）。见 `02-权限模型.md` T8。

### 荣誉团员的授予（2026-09-23）

- **谁能设**：**仅管理员**（与"改角色"同一入口，T8 不变）。
- **能给谁设**：**只有 `status = GRADUATED`（因毕业离团）的人**；退团（`LEFT`）/ 休团（`PAUSED`）**不适用**。
- **必须同时填** `member.honorary_until`（**登录有效期**；界面默认"毕业后 2 年"、可改）。
  **不填 = 不可登录**（fail-closed）。**续期**走同一个入口。
- **变更照旧写历史**：`role` 从 `MEMBER` 改成 `HONORARY` 时，**必须写 `member_role_history`**（硬规则不变）。
- ⚠️ **这条规则是双向的**（`13` **不变式 13**）：授予之后，**也不允许把状态改成非 `GRADUATED`**。
  否则 `status` 变成 `ACTIVE` 会让 `01` §1.4 的登录闸门**第一步就放行**，
  `honorary_until` 当场形同虚设（**永久可登录**），而且他会重新进应到名单、**能签到**——
  与 `02` §2.3「签到 ❌」直接冲突。
  要实现上收口有两种做法（**由实现方选，但结果必须满足不变式 13**）：
  ① 改状态时，若该人当前是荣誉团员 → **拒绝**改成非 `GRADUATED`；
  ② 或要求**同一次请求里**把角色降回 `MEMBER` 并清空 `honorary_until`。
- **撤销荣誉团员**：把 `role` 改回 `MEMBER`（状态仍是 `GRADUATED`）→ **必须同时清空 `honorary_until`**
  （`13` 不变式 13：非荣誉团员该列恒为 NULL）。此后他**不能再登录**（`status ≠ ACTIVE` 且不是荣誉团员），
  但只要重新授予就能再回来——**数据一直留着**。

### 管理端「编辑团员」弹窗

**要解决的问题（2026-09-27 用户提出）**：`admin-members.html` 的成员列表**没有任何改角色的入口**——
角色只出现在**建号表单**里。于是「**换届**」（上一届团长毕业、把团长交给下一届）**在界面上做不到**，
只能绕过界面直接调 `PUT /api/admin/members/{id}`（后端其实早就支持，且会自动写操作日志与曾任职务）。

⚠️ **同一个洞还有第二个表现，修的时候别只修一半**：那行的「停用 / 恢复」只在
`ACTIVE ↔ PAUSED` 之间切，**「毕业 / 退团」在界面上根本设不了**。而「授予荣誉团员」按钮
**只对 `status = GRADUATED` 的人显示** → **死循环：造不出毕业，就永远点不到荣誉入口**
（能写 `member.status` 的地方只有三处：`AdminSeeder` 与建号的 `create` 都只会写 `ACTIVE`，
**非 `ACTIVE` 只有 `MemberService.update` 一处能写**——而它的界面入口恰好缺了「状态」这一样）。

**做法**：成员列表每行加一个「**编辑**」按钮 → 弹窗，改 **角色 / 声部 / 状态** 三样。

- **不新增接口**——复用 `PUT /api/admin/members/{id}`（部分更新：**只提交改动过的字段**）。
- **不改造**已有的行内「入团日期」控件与「授予荣誉团员」弹窗，三者并存。
- **权限仍是仅管理员**（`02` 的 **T8 一字不改**）。本次只是**补一个界面入口**，不是下放权限。

| 字段 | 下拉内容 | 规则 |
|---|---|---|
| 角色 | 团员 / 声部长 / 指挥 / 团长（**与建号表单同源**，**不含管理员**） | **不含「荣誉团员」**：它必须配 `honorary_until`，走已有的「授予荣誉团员」入口；见下方 ③ |
| 声部 | 无声部 + `GET /api/sections` 的各声部 | 选「声部长」时**声部必填**，见下方 ① |
| 状态 | 在团 / 休团 / 退团 / 毕业（**四态全给**） | 改成非「在团」时，确认框必须写明：**会立即吊销他的登录态、他不能再登录**（与既有「停用」文案同口径） |

**三条边界（写死，实现者读完不用再拍板）：**

① **选「声部长」而声部为空 = 拒绝。** 现在 `checkSectionLeaderUnique` 在 `sectionId == null` 时
直接返回、等于放行，能造出「**没有声部的声部长**」。拦在**后端**，**前端不要预先判**（两处口径必漂）。

② **「无声部」必须真能清空。** `update` 目前把 `sectionId == null` 当「**未提供**」，
所以弹窗上选「无声部」会**静默失效**。实现方自选途径（如多带一个 `clearSection` 标记），
但**结果必须真能清空**——不许留一个点了没反应的选项。

③ **荣誉团员的角色只能「撤销」。** 当前是荣誉团员的人，角色栏**只给两项**：
「荣誉团员（当前）」与「团员（撤销荣誉）」。选后者即 `role = MEMBER`，后端会自动清 `honorary_until`
（状态保持 `GRADUATED`）。**后端同时要拒绝**把荣誉团员直接改成团长 / 指挥 / 声部长——
否则**绕过有效期校验**，而且会留下一条自相矛盾的记录（**已毕业的人挂着团长头衔**，
`member_role_history` 里还会多一段假任期）。依据 `13` 不变式 13 与本节上面荣誉团员那几条。

**交互**：保存失败时**浮层不关**（让人改完再试，先例＝反馈浮层）；失败提示**直接用后端消息**
（`BAND.must` 已 toast `envelope.message`），前端**不要自己复述**「该声部已有声部长」这类判据；
保存成功后 toast + **重拉列表**（后端可能有连带改动：清 `honorary_until`、写 `left_at`、吊销 token）。

**明确不做「一键移交团长」**：换届 = **两次编辑**（新人 → 团长；老人 → 团员或毕业）。
理由：**`LEADER` 本就不是单例**（`02` §2.2「约 3 个」），过渡期允许并存；
一个有「移交」语义的原子接口会把团长写成单例，与角色模型打架。

> **为什么「毕业」没有自动判定**（用户 2026-09-27 问到，一并记在这里）：
> 系统里**没有学制、年级字段，也没有定时任务**——`status = GRADUATED` 就是**管理员手工设的那一刻**，
> 它不是系统识别出来的事件。设它会连带写 `left_at`（考勤分母靠它划边界）并**立即吊销该人全部 token**。
> 「可以授予荣誉团员」的判据也仅此一条：`status = GRADUATED` 且 `role ≠ HONORARY`。
> **所以顺序是写死的：先设毕业 → 按钮才出现。**
> 「到点提醒谁该毕业了」**本次不做**——要做先得有年级或学制字段，属独立条目。

### 账号唯一性

建号前先查重，重复返回 409。重名示例：两个张伟 → `zhangwei` / `zhangwei2`。

### 上线迁移：现有团员怎么录进来（2026-09-23 定）

**系统是中途上线的**，所以"以前就入团的人，入团时间怎么算"是一道必须回答的题
（用户自己提出来的）。已定：

| 项 | 口径 |
|---|---|
| **老团员的 `joined_at`** | **真实入团日期**——不是上线日、也不是建号日 |
| **精度** | 前端个人栏只显示**年份**（`XXXX 年入团`，见 `14` §14.6.4），所以**精确到年即可**，不必逐个溯源到日 |
| **新团员** | 默认 = 建号当天 |
| **必须能填** | 建号表单要有「入团日期」一栏（默认当天、可改成更早）。⚠️ **现在没有**——`POST /api/admin/members` 的 DTO 里其实有 `joinedAt`，但界面上没这一栏，等于**实际上填不了** |
| **必须能改** | `PUT /api/admin/members/{id}` 要能改它。⚠️ **现在改不了**（`MemberUpdateRequest` 没有这个字段）＝ "填错一次就永久错，只能直接改库"。改它会**动出勤率分母**（不变式 7），所以要么进操作留痕、要么只让管理员改 |
| **上线后要不要补录历史活动** | **要补**。补录必须**成对做**：补一场活动就逐人**代签**补考勤（`05` §5.3）。**只补活动不补考勤 → 出勤率分母凭空变大**（`13` 不变式 14）|
| **补录场次里的"已离团的人"** | **不算**——考勤只服务**现役**的人。补录的历史场次里**不会出现**当年在团、现已毕业/退团的人。**这是刻意的**，写在这里免得后人以为漏了 |

> **为什么 `joined_at` 不是"展示字段"**：它**门控考勤**——应到名单要求
> `joined_at 为空 或 ≤ 该场活动日期`（`05` §5.4）。所以填错**分母就错了**，
> 而不只是"个人栏显示不好看"。这正是"能填能改"被列为硬要求的原因。
