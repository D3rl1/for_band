# 08 · 练习录音与文件存储

## 8.1 这个板块解决什么

团员把自己的练习录音传上来，声部长听本声部的录音并留言指点，团员可以回复追问。

**另外，本文件还承载全项目统一的文件存储设计**（见 §8.5）——
曲目附件、演出照片、练习录音**共用同一套上传与鉴权机制**。

## 8.2 数据模型

### `recording`（练习录音）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `member_id` | bigint | 上传者 |
| `section_id` | bigint | 冗余存一份，**因为可见性按声部判定，查询会高频用到** |
| `piece_id` | bigint NULL | 录的是哪首曲子（可选，方便声部长按曲目挑听） |
| `assignment_id` | bigint NULL | **关联本周作业条目**（2026-10-25 新增）；为空＝未关联，不计入完成度 |
| `title` | varchar(64) NULL | 标题 / 说明 |
| `file_id` | bigint | 关联 `file` |
| `duration_sec` | int | 时长 |
| `size_bytes` | bigint | 文件大小 |
| `uploaded_at` | datetime | **归周依据**（按 `uploaded_at` 落周） |

索引：`idx_member_id`、`idx_section_id`、`idx_piece_id`、`idx_assignment_id`

### `recording_comment`（点评）

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `recording_id` | |
| `author_id` | 留言人 |
| `content` | 文字内容 |
| `created_at` / `updated_at` | |

**结构：平铺按时间，不做父子回复嵌套。**
理由：声部长 ↔ 团员本质是一对一对话，父子结构纯属多余。

### `recording_assignment`（本周录音作业，2026-10-25 新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `week_start` | date | 该周周一（**Asia/Shanghai**），不是“创建时间” |
| `section_id` | bigint | 布置给哪个声部（**按声部布置**，不按人） |
| `title` | varchar(64) | 作业标题，如「单跳基本功」「长弓稳定性」 |
| `piece_id` | bigint NULL | 可选曲目；**基本功类作业为空** |
| `created_by` | bigint | 布置人（`member.id`） |
| `created_at` / `updated_at` | datetime | |

索引：`idx_week_section`（`week_start, section_id`）、`idx_piece_id`。
无外键（沿用全库惯例）。

**为什么标题必填、曲目可选**：打击的「单跳」「长弓」这类基本功练习**不涉及具体曲目**；
若把曲目做成必填，要么逼人乱挂一首曲子，要么这类作业根本建不出来。

- 历史周返回同样的 `sections → members → recordings`，但**不带** `assignments` 完成度、`state` 一律 `null`。

## 8.4 业务规则与边界

### 可见性（**必须在查询层过滤，不能只隐藏按钮**）

| 角色 | 能听谁的录音 |
|---|---|
| 团员 | **仅自己** |
| 声部长 | **本声部成员**的 + 自己的 |
| 指挥 / 团长 / 管理员 | 全部 |

**不是本声部成员上传的录音，对其他声部长一律不可见。**

### 录音管理视图与本周作业（2026-10-25 新增）

这一页（`recordings.html`）**不再整页只给四角色**——它同时是普通团员**唯一的上传入口**。
做法是**同页双视图**：菜单对全员不变，管理员 / 团长 / 指挥 / 声部长多一个「录音管理」，
其余人只有「我的录音 + 录一段」。原「我能听到的全部」文案作废。

#### 周界（唯一口径）

- **Asia/Shanghai，周一 00:00:00 – 周日 23:59:59**；`week_start` 存该周**周一**的日期。
- **录音按 `uploaded_at` 归周**，不看作业创建时间、不看客户端时间。
- 页面上的「本周」＝服务器按上述时区算出来的当前周，不接受前端传“我觉得现在是哪周”。

#### 应录名单（谁该交）

本周应录 = 同时满足：`status = ACTIVE`、非系统账号（`is_system = 0`）、**非指挥**、
`joined_at <= week_start`（**周一前入团**才计入本周）。
**荣誉团员 / 休学 / 退团不计**；`section_id` 为空的（无声部）不计入未交，只可能出现在录音里。
排序：声部按 `section.order_no`，人按 `member.id` 升序（**不假装拼音排序**）。

#### 三态完成度

| 状态 | 判定 |
|---|---|
| **未交** | 本周关联了 0 条作业提交 |
| **部分交** | 本周有 ≥1 条关联提交，但没有把本人当前声部的**全部**作业交齐 |
| **已交** | 本人当前声部的全部作业都有了关联录音 |

- 统计基数是**本人当前声部的作业条目数**；该声部本周无作业时，该声部**不进统计**。
- **有录音但没关联作业**的人：只在名单旁标「传了 N 条 · 未关联作业」，**不自动算已交**。
- 同一作业传两条也算已交（不按条数判），但两条都保留展示。

#### 本周作业的增删改

- **粒度是声部**，条目 = **标题（必填）+ 曲目（可选）**。
- 本周内可增删改；**已有任意录音关联的条目只能改名，不能删**（避免历史统计被悄悄改写）。
- **历史周只读**：不能补布置、不能补改。

#### 无布置周

该声部本周没有作业时，顶部显示「**本周未布置曲目**」，**未交名单整块隐藏**（没有作业就无所谓“没交”）。
本周录音照常展示。若全团所有声部都没布置，页面只显示这句话 + 本周录音。

#### 已知边界：换声部跨周

`recording.section_id` 是**上传时的快照**，本周录音分组用它；应录名单用 `member.section_id`（当前声部）。
因此**换声部的人当周**可能出现「旧声部有他的录音、新声部显示他未交」。
**这是已知边界，不做回溯重算**——录音归属以当时声部为准。

#### 历史周

- 默认折叠；点开才加载（先周列表 + 每周条数，再拉该周明细）。
- 历史周的分组和本周一致（声部 → 人），但**不计算完成度、不出未交名单**：
  用今天的名单反推过去，会产生“当时还没入团的人也被算未交”这类假数据。

### 上传限制

| 项 | 规则 |
|---|---|
| **时长上限** | **页面内录音 8 分钟（480 秒）**，且**只算真正录进去的部分**：**暂停的时间不计入上限、也不计入这条录音的时长**（2026-10-25 由用户拍板，原 3 分钟作废）。⚠️ **只拦这条路**：「选择本机文件」**不受时长限制**，只受 **20MB 体积**限制（服务端本来就解析不了音频时长，见 §8.5） |
| 格式 | `m4a` / `mp3` / `wav`（服务端按文件头判定，见 §8.5） |
| 来源 | **两条路各自独立、各有名字**：① **「页面内录音」**——浏览器直接录；② **「选择本机文件」**——从手机 / 电脑里挑已有的音频。⚠️ **不许做成一个控件**，见下 |
| 关联作业（2026-10-25） | 可选。传了 `assignmentId` 时，**服务端校验它属于本人当前声部且是本周**，否则拒绝；若该作业带曲目，**服务端自动回填 `recording.piece_id`**（旧曲目筛选继续可用）。不传＝未关联，允许，但不计入完成度 |

#### ⚠️ 「选择本机文件」在手机上必须真能挑到文件（2026-09-26）

**症状**：团员在手机上点那个文件选择框，**弹出来的是手机自带的录音机 App**（只能新录一段），
手机里已有的 `.m4a` 一个都挑不到。**服务端其实早就收 m4a**（§8.5 的白名单 + 文件头嗅探都放行），
坏的是前端那一个控件。

**根因**：`<input type="file" accept="audio/*">` 里的 **`audio/*` 是个通配**。
安卓按"谁能**产出**音频"来做意图匹配，**录音机 App 正好声明了这条**，于是它被选中。
⚠️ **不是 `capture` 属性的锅**——本仓从来没写过 `capture`，**加了才会强制**走录音；去掉它并不能解决这个症状
（网上那条最常见的建议在这里对不上，别照抄）。

**两条硬要求**（少一条症状就复现）：

1. **`accept` 必须列「显式扩展名 + 具体 MIME 类型」**，**不得**用 `audio/*` 这类通配：
   `.m4a,.mp3,.wav,audio/mp4,audio/mpeg,audio/x-m4a,audio/wav`；**不得加 `capture`**。
2. **两个入口是分开的、有文字的控件**，各自带一个说人话的标签（「页面内录音」/「选择本机文件」）。
   现状是一个裸的、无标签的文件输入框，和「开始录音」挤在同一行——**规格原来只写了
   "或选择本地文件"六个字，实现出一条谁也注意不到的输入框，就是这个后果**。

**另外（2026-10-25 改口径）**：**挑完文件不再直接上传，先进试听卡**。
原规则「挑完即传」的目的是防"选了没传、却以为传了"；现在这条由**试听卡上唯一的上传按钮**
来保证——用户必须先听过、再按「上传这条」，不会再有第二个上传入口让人猜。
两条路（页面内录音 / 本机文件）**统一先试听再上传**，详见下节「先试听，再决定上传」。

### 页面内录音：节拍器与音质约束（2026-09-26）

#### ⭐ 不变式：录音全程必须听得见节拍器

**这是整个节拍器功能存在的唯一理由，不是"顺带加个节拍器"。**

团员原先的做法是：手机录音机 App 录音 + 另开一个节拍器 App。**录音机一启动就抢走音频焦点，
节拍器 App 当场被系统静音**——于是"跟节拍器录"这件事在手机上根本做不成。

**网页里能做成的原理**：`MediaRecorder` 抓的是麦克风流，**它不会静音页面自己的音频输出**。
所以把节拍器做进这个页面、并让它在**录音进行中一直响**，正是这条路的全部价值。

**验收判据是"正面听到"**：真机上**录着音、耳朵听到节拍声**才算过。
**不接受**"代码里没静音"这种糊弄式通过。

#### 节拍器长什么样

- **控件（2026-10-15 更新，跟代码）**：BPM 手填、**拍号分子 `#m-num` / 分母 `#m-den`**、开始 / 停止、
  **圆弧拍点 `.mt-arc` + 拍点圆点 `#m-dots`**。
- **拍号 = 每小节几拍**（6/8 按**六拍**算、不按两拍大拍）；**重音按拍位点选**：
  **点某一拍的圆点 = 设 / 取消那一拍的重音**（不再只有"首拍重音"一个开关）。
  重音与弱拍靠**音高 + 音量**区分，重拍高、弱拍低。**默认峰值（2026-10-25）重拍 0.90 / 弱拍 0.45**（保持 2:1，音色与包络不变，比原先约 +8.5 dB）；兼容模式 WAV 同比例放大，两种模式同响。
- 录音页的这块面板另带**细分 `#m-sub`**与**TAP 打拍 `#m-tap`**；与独立节拍器页**同一套键、同一套代码**。
- **拍点指示**：一拍一个点，当前拍点亮，**重拍更明显**——别做成一整条进度条。
- **BPM 记在本机**（`localStorage`，键 `band_metronome_bpm`，首次默认 80）。
  ⚠️ **曲目表不加"速度"字段**——2026-09-26 定：手填 + 记住上次就够，**不动数据库**。
- ⚠️ **"录音停"不等于"节拍器停"**：两者**各管各的**——节拍器由用户自己按才停，
  这样停一次录音还能接着录下一条。**不许做成"录音结束自动关节拍器"**。
- **预备拍（起拍）本轮不做**——用户没要，别自作主张加。
- 声音与视觉的具体规矩见 `14` §14.6.6；`prefers-reduced-motion` **只降级视觉、不静音**。
  ⚠️ **节拍器不受全局声音开关 `band_sound` 约束**——那是一条**显式例外**，理由见 `14` §14.6.6。
- **两种音频模式（2026-10-15，跟代码）**：默认「高精度」走 Web Audio
  （`BAND.ensureAudio()` → `BAND.tick()`）；宿主能跑但不出声时切「兼容模式」，
  用 `<audio>` 播 `/sounds/metro-accent.wav` / `metro-weak.wav`（每种 4 个元素轮换，**鸿蒙 NEXT 默认兼容**）。
  ⚠️ 这两个 WAV 是**部署产物、不是用户附件**，**不入 `file` 表**、不参与上传校验。
- **兼容模式计时（2026-10-25）**：`<audio>` 不能预排未来，但定时器要按**绝对时间网格**走（`setTimeout` 链 + `performance.now()`），消掉 `setInterval` 的累计漂移；每次 `play()` 的启动抖动仍在，故提示行仍写「精度略低」。
- **起拍前必须 `await` 音频真正 `running`**：拿不到就**不启动**、按钮保持「开始」，
  失败原因**持久写在提示行**（不弹一下就没）。三类文案：不支持 Web Audio / 初始化失败 /
  被挂起（后者含百度浏览器「锁图标 → 网站设置 → 声音 → 允许」；鸿蒙 NEXT 与 App 内 WebView 各有自己的出路）。
  运行中另提示「听不见先查：媒体音量 / 蓝牙耳机 / 站点声音权限」；`?diag=1` 附 `AudioContext` 状态与 UA。
- ⚠️ **站外因素 JS 感知不到**：内核的站点声音开关、标签页静音、系统媒体音量、蓝牙输出
  都会让声音消失，页面只能给**能照做的路径**。所以**真机验收不能由 `_metro_audio_check.py` 代替**——
  探针只证明"排出去的拍"与"失败时怎么说"，**证明不了耳朵听得到**。

> 📌 **2026-10-07 补记（独立节拍器）**：`metronome.html` 那件「**独立完整版**」已出规格
> （`docs/14` §14.6.4「独立节拍器」）。**与本节这个面板的关系**：
> 本节这面板**只为"录音时听得见"**服务、是录音页的一部分；那件是**练琴用的独立工具页**
> （录音页那套 + 细分拍 / 重音花样 / 更多拍号 / tap tempo），**无表、无接口**。
> 两者**共用同一套 `BAND.tick` / `tickCompat` 与 `band_metronome_*` 键**
> （高精度模式共用全页唯一 `AudioContext`，兼容模式共用 WAV 池），但**互不联动**（关一个不影响另一个）。

#### 外放时录音里带节拍声，**这是预期结果**（2026-10-25 改口径）

团员开节拍器录音，本来就是为了**把节拍声一起录进去**；它不再是需要规避的"脏东西"。

| 怎么放 | 听得见节拍器？ | 录音里有没有节拍声？ |
|---|---|---|
| **外放** | ✓ | ✓ **会录进去——这是目的** |
| **戴耳机** | ✓ | 取决于耳机漏音；若**不想**把节拍声录进去，才需要戴 |

- **节拍声为什么会进录音**：因为下面那条"关掉语音处理"。这是**有意的取舍**——
  开了回声消除虽能压掉外放串进来的节拍声，**但它同时会压平乐器、把弱音尾巴当噪声掐掉**，
  给乐器录音得不偿失。
- **界面不再提示戴耳机**（2026-10-25 删）：只保留「录音中请勿切走应用」。
- **如果确实不想把节拍声录进去**：戴耳机；**有线更稳**——蓝牙麦克风可能切到免提（HFP）通道，把录音降成通话音质。

#### ⚠️ 录音期间页面必须留在前台、屏幕不能熄

浏览器在页面切到后台 / 锁屏时会**挂起音频**，节拍器当场哑掉——
**这是"要听得见"最可能被破坏的地方**，必须当正事处理：

- 界面上写死一句「**录音中请勿切走应用**」；
- 实现侧要做前台可见性守卫：`visibilitychange` 一旦走到后台，**必须明确提示"节拍器已停"**，
  **不许静默**——无声无息地哑掉比报错更坏。

#### 录音质量：必须显式关掉浏览器的语音处理

`getUserMedia` **必须显式传** `echoCancellation: false` / `noiseSuppression: false` / `autoGainControl: false`。

**为什么**：裸写的 `{ audio: true }` 会把这三样**全打开**，而它们是为**语音通话**调的——
自动增益来回压电平、降噪把**乐器的弱音尾巴当噪声掐掉**、回声消除连带压掉一部分乐器。
对一个给乐器录音的系统，**这是缺陷，不是保守**。

（与上面那条配套：关掉回声消除 ⇒ **外放时节拍声会进录音**——对"跟着节拍录"正是目的；只有不想把节拍声录进去时才需要戴耳机。）

#### 录音失败时要说什么（2026-10-11 补）

**现在**：那个 `catch` 不管什么原因都弹一句「拿不到麦克风权限」——**是一句蒙的话**，
把"站内权限被拒"、"系统层没开权限"、"没设备"三种原因说成同一种。

**要求**：按 `getUserMedia` 抛出的 `err.name` 分开说，**口径与措辞照 `docs/18` §18.12**
（那份是手机端麦克风权限的统一说明，本页别再各写一套）。两条要害：

- `NotAllowedError` = **站内权限被拒**（点地址栏图标改允许）；`NotReadableError`（"Could not start audio source"）
  = ⚠️ **系统层没给这个浏览器麦克风权限**（安卓还会**自动收回久未使用 App 的权限**）⇒ 到「设置 → 应用管理」开权限；
- **别把英文原样抛给用户**，给"开系统权限 / 换手机自带浏览器或 Chrome"这种**能照做的指路**。
  （2026-10-11 的真实案例正是系统层这一层没开，用户照着"拿不到麦克风权限"去翻浏览器网站权限是怎么翻都翻不出来的。）

### 保留策略：**绝不自动删除任何人的东西**

### 播放：**一次只能听一个**（2026-09-30 新增）

**用户原话**：「听录音的时候可以**同时按多个录音听，这个不好，一次应该只能听一个**。」

**现状**：`recordings.html` 每条录音各自建一个**原生 `<audio controls>`**，**没有任何互斥逻辑**
（全文件 grep 无 `pause(`）⇒ 浏览器原生允许多个同时播、**声音叠在一起**。

**定**：
- **全局同一时刻最多一个在播**——**播新的时，先把上一个 `pause()` 并 `currentTime = 0`**。
- 这一条**不靠"用户自觉"**：是**代码层**的互斥（浏览器的原生行为不会帮你做）。
- ⚠️ **别用 `pause` 事件做状态正确性**（`14` §14.6.6 那条"过渡必须可取消"的同族）：
  直接持一个"当前正在播的那个"引用，切换时**显式**处理旧的，不要依赖事件回调的时序。

> ⚠️ 本节**以前是空白**——`08` 只写了"不做转码"，**从没有播放器的规格**。
> 所以这条是**新增**，不是修订。

### 录音页三项增强：拖动进度 · 录音暂停 · 先试听再上传（2026-10-25，#226）

**用户原话**：「听录音的时候给个能拖动的时间进度条，拖动进度条就可以听不同时间的录音了。
录音过程中，给个暂停的按钮（因为有人需要中途暂停去换节拍器的速度）录音结束后，要做到能够
自己去听自己的录音，也可以选择是否上传此次录音。」

**三条口径已拍板**（实现时不再改）：

| 问题 | 定 |
|---|---|
| 暂停时节拍器 | **照常走**。录音与节拍器各管各的；暂停 / 继续**不碰节拍器** |
| 时长上限怎么算 | **只算真正录进去的部分（暂停不计）**；上限 **8 分钟 = 480 秒** |
| 本机文件这条路 | **也先试听再上传**；原「挑完即传」作废（见上节） |

**参考实现（冻结样张，非生产代码）**：`design-samples/样张-精装-录音管理.html`
（闸门 `design-samples/check_rec_manage.mjs`，跑一次会生成 `shots-rec-manage/` 的截图）。
样式与状态的**行为**照它抄，但**类名以本文为准**（样张用 `.picks`，生产用 `.rc-picks`）；
样张里的 `__sample.setCap / failUpload` 是演示钩子，**生产不要带**。
desktop_agent 里的 `design-system/乐团系统/demo/` 那份是设计系统母本，两份都**不算生产代码**，以本规格为准。

#### 1) 可拖动进度条（列表卡与试听卡共用同一套逻辑）

- 用**原生 `<input type="range">` 叠在可视轨上**，不自写拖拽：键盘左右键、读屏、触摸都由浏览器负责。
- 触区高 **28px**、可见轨 3–4px、拇指 **14px** 实心 `--accent` + 2px `--surface` 描边；
  `:focus-visible` 用 `--accent-line` 外圈；`touch-action:pan-y`（横拖归滑块，竖滑仍滚页面）。
  手机 390px 下轨道可用宽度 **≥ 180px**（实测 194px）。
- **`input` 事件只重绘**（填充宽度 + 时间文本），**不动 `audio.currentTime`**；
  **`change`**（鼠标松手 / 触摸抬手 / 键盘按键）才跳一次；`pointercancel` 同样复位。
  正在播就接着播，暂停就只挪位置；`ended` 时归零复位。
- `range.max` **只认 `audio.duration`**（有限且 > 0）；**绝不拿列表里的 `durationSec` 当 max**。
  metadata 未到 / `duration` 为 Infinity 时 range 禁用，时间文本仍可用 `durationSec` 兜底显示。
- **手指还按着时，metadata 到达不得把填充画回 0**：重绘函数开头判 `dragging` 直接 return。
- 跳转用**代际令牌**（每次 `change` 递增），过期的 `loadedmetadata` 回调不得再改 `currentTime`。
- 同一时刻只允许一个播放实例（沿用上节「一次只能听一个」），换卡时旧实例 `pause()` + `currentTime=0`。

#### 2) 录音中暂停 / 继续

- 状态机：`idle → recording ⇄ paused → stopping → review`。
- 计时用**累计毫秒**，不用墙钟：`recordedMs + (segmentStart ? now - segmentStart : 0)`；
  **200ms ticker 只读不写**，暂停时 `segmentStart=null` 自然冻结，不需要暂停/重排定时器。
- 到 `480000ms` 自动停止 → 进试听，提示「**已达 8:00 上限，已自动停止**」；**不丢弃这条录音**。
  `onstop` 上报 `min(480, max(1, round(recordedMs/1000)))`；原「超时即丢弃」分支删除。
- 暂停 / 继续**只调用 `recorder.pause()` / `resume()`**；**绝不调用节拍器的启停**。
  暂停中改 BPM 照常生效（走现有 `setBpm() → metroRestart()`）。
- **能力探测与降级**：无 `pause` 方法，或调用后 `recorder.state !== 'paused'` ⇒
  toast「本机浏览器不支持暂停录音，这条只能连续录」+ 禁用按钮，**录音不中断、已录内容不丢**；
  绝不静默失败，也绝不为降级自动停止录音。
- 停止时若处于 `paused`，先 `resume()` 再 `stop()`；异常兜底直接 `stop()`。
- 文案：`正在录…` / `已暂停 · 节拍器照常` / `继续录音…`，状态文本 `aria-live="polite"`；
  暂停时波形与红点**只冻结动画**（`animation-play-state:paused`），点色用 `--ink-3`
  ——**不用朱砂**（朱砂只给警示）。

#### 3) 先试听，再决定上传（页面内录音与本机文件统一）

- 同一时刻只允许一个 `pendingTake = {file, url, seconds, source:'rec'|'file', name}`。
- 停止录音 / 选完本机文件后**不自动上传**，进入**试听卡**：进度条（同 §1）、
  「上传这条」/「重录（文件来源显示『重选』）」/「丢弃」、以及一句「不传就丢掉，不会保存」。
- 标题、曲目、关联作业在**点「上传这条」时**才取值（允许先听、再改标题）。
- **本页只有一个上传入口**：录音页只删 `#updone` 回执与它的 `showUpdone()`；
  `.rc-review` 里的「上传这条」**本页只此一个**；成功后就回列表（列表第一条即回执）。
  ⚠️ **`piece-detail.html` 里的 `#u-send`「上传并挂上」是另一页的挂曲目上传，不要动**
  （录音页本来就没有 `#u-send`，别照字面去全局删）。
- **样式名以生产为准**：入口容器在生产里叫 **`.rc-picks`**；样张演示页写的是 `.picks`，
  照抄样张时要改名。
- **上传中**：`uploading` 状态位 + 按钮禁用 + `aria-busy="true"`（防双击发两次）；
  `sendRecording` 必须 `try/catch/finally`。
- **成功**：`audio.removeAttribute('src'); audio.load()` 之后再 revoke；清 pending、收起试听卡、
  恢复两个入口、清标题、刷新列表。
- **失败**：保留 pending 与秒数、恢复按钮、toast 具体原因，**可直接重试**。
- **待上传期间**：两个入口 `aria-disabled` + `.rc-picks.busy{pointer-events:none;opacity:.55}`，
  提示「先上传或丢弃这条」。
- **objectURL 生命周期**：staging 时创建；「上传成功 / 丢弃 / 重录 / 重选 / `beforeunload`」时 revoke；
  待上传且不在上传中时挂 `beforeunload` 提醒。
- **本机文件预检**：扩展名白名单（m4a / mp3 / wav）+ **≤ 20MB**，不合格立即 toast、**不进入 staging**；
  建 URL 后用临时 `<audio preload="metadata">` 探时长，**4 秒超时或失败则时长留空，不阻断**试听与上传；
  上传时把探测到的秒数作为 `durationSec` 提交（探测失败传 `null`）。
- 本机文件**不受 8 分钟上限**约束（仍只受 20MB）。

#### 已知边界（实现与验收都按这个）

- **手机进程被杀**：待上传内容留不住；`beforeunload` 只覆盖浏览器内跳转 / 关闭。
- **8 分钟仍是前端拦截**：服务端不解析音频、不校验时长（与现状一致），文档不冒充服务端保证。
- **`MediaRecorder.pause()` 的拼接连续性必须真机验**（部分安卓 WebView 可能异常）；
  桌面闸门只能验状态机与计时，**不能代替真机回放**。
- `audio.duration` 为 `Infinity` / `0` 时只禁用进度条，**不许把 fill / 时间画成 `NaN`**。

### ⚠️ 「不能下载」的真实口径（2026-09-23）

用户对荣誉团员的要求是"**能查看、不能下载**"。落地时的**准确含义**是：

- **界面上不提供任何下载入口**（不显示"下载"按钮 / 链接），**且**接口按上面的可见性规则判定（谱子类直接 403）；
- ⚠️ **但这不是技术保证**：文件要能"看/听"，浏览器就必然拿到字节流，**技术上仍可另存**。
- **所以规格里照实这么写**——它是**产品层面的约定，不是 DRM**，别让实现者以为做了防拷贝。
  真要"连另存都不行"，唯一办法是**根本不给访问**（那"查看内容"也就没了）。

### ⭐ 附件的「查看」怎么打开（2026-09-30 新增）**· 这是 bug**

**用户报障**：「**手机上好像没法查看谱子，好像是 url load 错误**」。

**根因**（已定位，`band-media.js` 的 `openFile()`）：

```js
async openFile(fileId) {
  try { window.open(await this.fileBlobUrl(fileId), '_blank'); }
  catch (e) { /* toast 已弹 */ }
}
```

**`window.open` 是在 `await` 之后才调用的 ⇒ 那一刻已经脱离用户手势** ⇒
手机浏览器 / 弹窗拦截器**直接把它拦掉**（返回 `null`，**静默失败**）；代码**不校验返回值**。
iOS 上新标签打开 blob 的 PDF 也常常一片空白。桌面上因为拦截宽松，往往看不出问题。

**定（2026-10-07 实做，2026-10-24 回写）：手机端走「签名 URL」**——不再把 blob 塞进 `iframe` / 新标签。

1. 前端先带 `Authorization` 调 **`GET /api/files/{id}/ticket`**（这条**要鉴权**，可见性判定与
   `GET /api/files/{id}` 完全相同；荣誉团员在这里就 **403**），拿到 `{ view, download, expiresAt }`。
2. `view` / `download` 是**同源相对 URL**：`/api/files/{id}/view?t=<票据>&dl=0|1`，直接给 `<a href>`。
   浏览器用自己的导航 / 下载器去取——**夸克 / 小米 / 微信这些没有内置 PDF 渲染器的壳也能用**。
3. **`/view` 只认票据、不做头部鉴权**（浏览器导航带不了 `Authorization`）。
   **无票 / 伪造 / 跨文件 / 过期一律 401**，**绝不 fallback 成开放静态读**；
   `dl=1` 走 `attachment` + 真文件名（`filename*=UTF-8''…`，ASCII 兜底名另存一份）。
4. 前端按类型分路：**图片 / 音频仍走 blob**（本来就正常，还能在页内播）；**PDF / PPT / Word / 未知类型**
   给「打开」「下载」两个**真链接**。桌面仍可同步开窗再填 blob，但**必须校验 `window.open` 返回 `null`**。

**票据机制（无状态，不新增表）**：

- `ticket = Base64URL(HMAC-SHA256(secret, "file:" + fileId + ":" + epochDay))`，
  **时区 `Asia/Shanghai`**（与数据源 `serverTimezone` 同源）。
- **按"天"分桶**：同一天内票据值**恒定** ⇒ URL 一字不变 ⇒ 浏览器缓存生效、反复打开不重复下载。
  校验接受**今天 / 昨天**两个桶——跨午夜那几分钟也不失效（`expiresAt` 只是给前端看的信息，不是校验依据）。
- **票据不绑用户**（标准签名 URL 模型）：拿到 URL 的人可在窗口内转发。窗口 ≤ 2 天，
  且**取票本身要过 `FileService.requireViewable`**（荣誉团员在那里就被 403）——
  与本节上面「这不是 DRM、是产品层面的约定」是同一口径。
- **`/view` 的响应头**：`Cache-Control: private, max-age=86400, immutable`（文件内容按 id 不可变，
  `private` 防共享代理串号）、`Referrer-Policy: no-referrer`（票据在 URL 里，别随 Referer 漏出去）。
- ⚠️ **密钥 `band.file-ticket.secret` 未配置时**：服务用**本次启动的临时随机密钥**
  （**绝不退回写死的默认值**——那等于人人可伪造）。代价是**重启后旧链接全失效**；
  前端每次打开都重新取票，**能自愈**。生产配置见 `12` §12.6。
- ⚠️ **票据会出现在查询串里** ⇒ 可能进 Nginx access log。日志权限与保留期按 `12` §12.6 管。

> ⚠️ **验收必须包含真机**——旧 blob/iframe 方案在桌面上**复现不出来**（拦截宽松），
> 只在手机上暴露。桌面测通了不等于修好了。

### ⚠️ 两条硬要求

1. **下载必须走后端鉴权接口，严禁暴露公开静态目录。**
   若用 `/uploads/xxx.mp3` 这类**可猜路径**，任何人拿到 URL 就能下载，
   **整个权限模型形同虚设**。这是最容易被忽略、也最致命的一类漏洞。
2. **磁盘文件名随机生成**，不用原始文件名——原始文件名可猜、还可能带路径穿越字符。

### 存储位置

服务器上一律用 `/data/band/uploads/`（**口径唯一**，配置与部署见 `12` §12.6 第 4、5 步），
**不与代码混放、不纳入 git**，随每日备份一并处理（见 `12-部署与备份.md`）。

**两条运行前提**（2026-09-24 补，起因是一次线上真故障：管理员上传 5MB 的 mp3 报「文件写入失败」）：

1. **该目录必须对服务账号（部署手册里是 `band`）可写。**
   ⚠️ **"程序会自己建这个目录"≠"建对了"**：`FileStorage.java:40` 用的是 `Files.createDirectories`，
   **它对"已经存在的目录"不校验可写性**——目录若由 `root` 建成 755，
   **启动与其它功能全部正常，只有上传时才炸**，且报错被压成一句「文件写入失败」
   （`FileStorage.java:64`，**不记日志、不带路径**）。**建目录 + `chown` 是部署步骤**，不是运行时的自愈行为。
2. **它必须与备份脚本备份的那个目录是同一个**（同一条路径、逐字一致）。
   两处写成两个路径**不会报错**：后果是"备份一直显示成功（备的是空目录），
   而录音**从来没进过备份**"——这类"漏了不出声"的坑要靠 §12.7 检查清单核，别靠记性。

### 图片处理

**前端压缩后上传**：canvas 缩到**长边 1920 / 质量 80%**。
服务端仍要校验实际大小，防止绕过前端直接调接口传大图。

### 音频处理

限制格式（`m4a` / `mp3` / `wav`）与时长（页面内录音 **8 分钟，只计实录音、暂停不计**，见 §8.4 的两条路差别）。
服务端**不校验时长**——到点是前端自动停止并进试听，不是"提交后被拒"。
**不做转码**——手机浏览器对这三种格式的播放支持足够，转码是没必要的复杂度。
⚠️ **白名单就是这三种，一个不多**（2026-09-25 对齐）：代码里曾经多收一个 **`mp4`**（`FileTypes.AUDIO_EXT`），
已去掉——`.mp4` 是**视频容器**，收成音频等于让人把一段视频当录音传进来；而我们自己的录音器产出的就是 `.m4a`
（`recordings.html` 里 `new File([blob], 'take-*.m4a')`），不缺这一种。
（**下载侧不校验扩展名**，所以即使库里已有旧文件，也不会因为这次收窄而读不出来。）

#### ⚠️ 这条白名单现在卡着一条功能链（2026-09-26 记）

**别把下面这段读成"白名单要改"——它是条件句，决策还没做。**
但它现在是**整条"页面内录音 + 节拍器"路的生死判据**，不能再当小事挂着：

- 页面内录音能不能用，取决于 **`MediaRecorder.isTypeSupported('audio/mp4')`**。
  这是 `recordings.html` 现在的门槛：**为假就直接禁用录音按钮**，并提示"用手机录音机录好、再选本地文件上传"
  （那条提示的落点正是 §8.4 里刚修的那条路）。
- 而 **Chrome 安卓的 MediaRecorder 默认产 `webm/opus`**，`audio/mp4` 在安卓 Chrome 上**支持与否尚未确认**
  （2026-09-26 查不到确凿结论，**不许按"应该有"实现**，必须真机实测）。
- **若真机实测为假**：安卓上就**没有页面内录音**，节拍器 §8.4 那条不变式在安卓上也就无从谈起
  ⇒ 二选一：**① 把 `webm` 加进白名单**（代价：它违背上一条"一个不多"，且要考虑 **iPhone 上的声部长放不放得出** webm），
  或 **② 接受安卓上没有页面内录音**（那节拍器就只剩"独立练"的用法）。
- 这条与 **交接单 `#9`** 是同一件事——`#9` 已挂三次，**这次由 `#67` 的验收顺带真机实测并把结果回填**。
