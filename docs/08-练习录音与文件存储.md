# 08 · 练习录音与文件存储

## 8.1 这个板块解决什么

团员把自己的练习录音传上来，声部长听本声部的录音并留言指点，团员可以回复追问。

**另外，本文件还承载全项目统一的文件存储设计**（见 §8.5）——
曲目附件、演出照片、练习录音**共用同一套上传与鉴权机制**。

### `recording_comment`（点评）

| 字段 | 说明 |
|---|---|
| `id` | PK |

## 8.4 业务规则与边界

### 可见性（**必须在查询层过滤，不能只隐藏按钮**）

| 角色 | 能听谁的录音 |
|---|---|
| 团员 | **仅自己** |
| 声部长 | **本声部成员**的 + 自己的 |
| 指挥 / 团长 / 管理员 | 全部 |

**不是本声部成员上传的录音，对其他声部长一律不可见。**

### 上传限制

| 项 | 规则 |
|---|---|
| **时长上限** | **3 分钟**（**暂定 T5**） |
| 格式 | `m4a` / `mp3` / `wav` |
| 来源 | 手机浏览器直接录音，或选择本地文件 |

### 保留策略：**绝不自动删除任何人的东西**

**永久保留**，后台显示存储用量，到阈值时提醒管理员。**不自动清理。**

> 理由：作者对"用机制逼人"类的设计一贯反感。"我的录音莫名少了"会直接摧毁使用意愿——
> 尤其被自动删掉的往往正好是记录进步的那一条。**清不清理、什么时候清，控制权留在人手里。**

### 删除权限

**本人 + 本声部长 + 管理员。**

> ⚠️ **反向也要写死：团长 / 指挥不能删任何人的录音。** 他们能"听全部"（见上面的可见性表），
> 但**不删**——删除是不可逆动作，收窄到与录音直接相关的三方。
> 2026-09-23 定（`02` §2.3 矩阵原先给团长 / 指挥 ✅，是未同步的旧值，现已改 ❌）。

### 点评

- **双向**：声部长留言后，团员可以回复追问
- **谁能点评**：**能看见谁的录音，就能在谁下面留言**（声部长的可见范围限本声部）——
  团员"能看见的只有自己"，所以**只能在自己的录音下回复追问，点评不到别人的**
  （`02` §2.3 这一格写作「✅ 仅自己」）
- 理由：团员看不懂点评时若没地方问，就会转去微信——信息又散到系统外去了
- **不做「已点评 / 未点评」标记**：一旦有这个状态，声部长的点评就从"自发帮忙"变成
  **欠账 KPI**，他会开始躲这件事。理由见 `DECISIONS.md` D18

## 8.5 F4 · 统一文件存储设计（**三处共用**）

**曲目附件（`06`）、演出照片（`07`）、练习录音（`08`）共用同一套机制。**
不要为它们各写一套上传逻辑——否则以后改一处必然漏一处。

### `file` 表

| 字段 | 说明 |
|---|---|
| `id` | PK |
| `stored_name` | 磁盘上的文件名（随机生成，**不用原始文件名**） |
| `original_name` | 用户上传时的原始文件名（仅用于下载时显示） |
| `content_type` | 服务端判定的类型（**不信任客户端传来的 MIME**） |
| `size_bytes` | |
| `sha256` | 内容哈希（去重、校验损坏） |
| `owner_id` | 上传者 |
| `created_at` | |

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/files` | multipart 上传 → 校验类型与大小 → 落盘 → 返回 `file_id` |
| GET | `/api/files/{id}` | **必须鉴权**，按该文件所属实体的可见性规则判定后返回流。**荣誉团员**（2026-09-23）：**只能访问属于自己的文件**（自己上传的录音）；**曲目附件（谱子 / 音频）一律 403** |
| GET | `/api/admin/storage` | **仅管理员**（团长的白名单都不含它——这是系统维护数据，不是业务信息） | 存储用量统计。落点：`logs.html` 顶部一行；阈值默认 **2GB**（`band.storage.warn-bytes` 可配）。📌 2026-09-24 补记：代码已实现（`AdminStorageController`），文档漏记。⚠️ **别与"备份状态"搞混**——那是另一件事，见 `12` §12.5 |

### ⚠️ 「不能下载」的真实口径（2026-09-23）

用户对荣誉团员的要求是"**能查看、不能下载**"。落地时的**准确含义**是：

- **界面上不提供任何下载入口**（不显示"下载"按钮 / 链接），**且**接口按上面的可见性规则判定（谱子类直接 403）；
- ⚠️ **但这不是技术保证**：文件要能"看/听"，浏览器就必然拿到字节流，**技术上仍可另存**。
- **所以规格里照实这么写**——它是**产品层面的约定，不是 DRM**，别让实现者以为做了防拷贝。
  真要"连另存都不行"，唯一办法是**根本不给访问**（那"查看内容"也就没了）。

### ⚠️ 两条硬要求

1. **下载必须走后端鉴权接口，严禁暴露公开静态目录。**
   若用 `/uploads/xxx.mp3` 这类**可猜路径**，任何人拿到 URL 就能下载，
   **整个权限模型形同虚设**。这是最容易被忽略、也最致命的一类漏洞。
2. **磁盘文件名随机生成**，不用原始文件名——原始文件名可猜、还可能带路径穿越字符。

### 存储位置

服务器上一律用 `/data/band/uploads/`（**口径唯一**，配置与部署见 `12` §12.6 第 4、5 步），
**不与代码混放、不纳入 git**，随每日备份一并处理（见 `12-部署与备份.md`）。

**两条运行前提**（2026-09-24 补，起因是一次线上真故障：管理员上传 5MB 的 mp3 报「文件写入失败」）：

1. **该目录必须对服务账号（部署手册里是 `band`）可写。**
   ⚠️ **"程序会自己建这个目录"≠"建对了"**：`FileStorage.java:40` 用的是 `Files.createDirectories`，
   **它对"已经存在的目录"不校验可写性**——目录若由 `root` 建成 755，
   **启动与其它功能全部正常，只有上传时才炸**，且报错被压成一句「文件写入失败」
   （`FileStorage.java:64`，**不记日志、不带路径**）。**建目录 + `chown` 是部署步骤**，不是运行时的自愈行为。
2. **它必须与备份脚本备份的那个目录是同一个**（同一条路径、逐字一致）。
   两处写成两个路径**不会报错**：后果是"备份一直显示成功（备的是空目录），
   而录音**从来没进过备份**"——这类"漏了不出声"的坑要靠 §12.7 检查清单核，别靠记性。

### 图片处理

**前端压缩后上传**：canvas 缩到**长边 1920 / 质量 80%**。
服务端仍要校验实际大小，防止绕过前端直接调接口传大图。

### 音频处理

限制格式（`m4a` / `mp3` / `wav`）与时长（录音 3 分钟）。
**不做转码**——手机浏览器对这三种格式的播放支持足够，转码是没必要的复杂度。
⚠️ **白名单就是这三种，一个不多**（2026-09-25 对齐）：代码里曾经多收一个 **`mp4`**（`FileTypes.AUDIO_EXT`），
已去掉——`.mp4` 是**视频容器**，收成音频等于让人把一段视频当录音传进来；而我们自己的录音器产出的就是 `.m4a`
（`recordings.html` 里 `new File([blob], 'take-*.m4a')`），不缺这一种。
（**下载侧不校验扩展名**，所以即使库里已有旧文件，也不会因为这次收窄而读不出来。）

### 配额

**全局用量显示在管理员后台**；到阈值时提醒（**不自动删除任何东西**）。
