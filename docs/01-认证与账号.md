# 01 · 认证与账号

## 1.1 这个板块解决什么

让团员能用管理员发来的账号密码登录，并且在登出、改密码、被停用之后，**旧凭据立即失效**。

---

## 1.2 数据模型

### `user_token`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `token_hash` | varchar(64) UNIQUE | **token 的哈希，不存原文**（与密码同理：库被拖走也拿不到能用的 token） |
| `member_id` | bigint | 所属账号 |
| `issued_at` | datetime | 签发时间 |
| `expires_at` | datetime | 过期时间（签发 + 30 天） |
| `revoked_at` | datetime NULL | 作废时间；非空即失效 |

索引：`idx_member_id`、`idx_token_hash`（UNIQUE）

### `member` 中与认证相关的字段

| 字段 | 说明 |
|---|---|
| `account` | 登录名，**UNIQUE**。由管理员自定（如姓名拼音） |
| `password_hash` | BCrypt 哈希 |
| `initial_password` | **初始密码明文，仅在该用户从未登录过时有值**；首次登录成功后**立即置 NULL** |
| `last_login_at` | 最后登录时间 |
| `is_system` | 管理员系统账号标记，见 §1.4 |
| `status` | 见 `03-团员与声部.md`；**非「在团」时禁止登录** |

## 1.3 接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/auth/login` | 公开 | 入参 `{account, password}` → `{token, expiresAt, member:{id,name,role,sectionName}}` |
| POST | `/api/auth/logout` | 登录 | 作废当前 token |
| GET | `/api/auth/me` | 登录 | 当前登录者信息。**客户端启动时用它判断登录态是否还有效** |
| POST | `/api/auth/password` | 登录 | 入参 `{oldPassword, newPassword}`；成功后**作废该用户全部 token** |
| POST | `/api/admin/members` | 管理员 | 建号。入参 `{name, sectionId, account, role?}` → **返回该人的初始密码** |
| POST | `/api/admin/members/{id}/reset-password` | 管理员 | 重置密码 → 返回新随机密码 |
| GET | `/api/auth/sessions` | 登录 | **我的**有效登录设备列表（设备 / IP 打码 / 登录时间 / 最后活跃 / 是否当前设备） |
| POST | `/api/auth/sessions/{id}/revoke` | 登录 | 踢掉指定一条会话。**必须校验归属——只能踢自己的**，踢别人的返回 403 |
| POST | `/api/auth/sessions/revoke-others` | 登录 | **踢掉其他所有设备**（保留当前这条） |
| POST | `/api/admin/members/{id}/revoke-sessions` | 管理员 | **踢某人下线**（作废其全部 token，但**不动账号状态**） |
| GET | `/api/admin/accounts/export` | 管理员 | 导出：姓名 / 声部 / 账号 / 初始密码（**格式见 `10-接口规范与错误码.md` §导出格式**） |

## 1.4 业务规则与边界

### 账号的创建与分发

1. **管理员建号**，账号名由管理员自定（如姓名拼音）。**不自动生成。**
2. **账号唯一性**：建号前先查重，重复则返回 409 并提示"该账号已存在，请换一个"
   （例：两个张伟 → `zhangwei` / `zhangwei2`）。
3. **初始密码**：系统随机生成，**8 位、字母 + 数字、剔除易混字符**（`0/O`、`1/l/I`），保证不重复。
4. **分发**：管理员导出（姓名 / 声部 / 账号 / 初始密码），线下或群里发给本人。
5. **导出只包含 `initial_password` 非空的账号**；已登录过的账号导出时不再带密码列，该行改为显示"已激活"。
6. **不强制首次登录改密码**（降低摩擦），但登录后可以自行修改。

### 初始密码的存储代价（**已接受的取舍，见 `SECURITY.md` G1**）

`initial_password` 是**明文**，仅在用户从未登录期间存在，首次登录成功后立即置 NULL。
这样做的代价是：**备份文件里也含明文**，所以备份文件本身要当机密保管。

> 被否掉的替代方案：每次导出时重置一批密码（零明文，但会让已经发出去的密码失效）；
> 或建号时只显示一次（零明文，但管理员当时没记下就得重置）。

### token 规则

- **有效期 30 天**（一个排练周期内基本不需要重新登录）
- **服务端可作废**：登出、改密码、账号被停用时立即失效
- **token 失效一律返回 401**，客户端据此跳登录页
- **token 用不透明随机串，不用 JWT**——JWT 无法在服务端作废。理由见 `DECISIONS.md` D4

### 多设备与会话管理

**一个账号可以同时在任意多台设备上登录，不限数量。** 每次登录**单独一行** `user_token`，
设备之间互不影响（登出只作废当前那一条）。

> **为什么不限制设备数**：团员**手机 + 电脑都要看排练表**，这是真实需求；
> 而限制数量既挡不住真正的外借（借的人只用一台），又烦到正常用户。
> 业界主流也不是"限制台数"，而是「**设备可见 + 可单独踢**」——
> 微信是「同类端互斥、异类共存」，Telegram / GitHub / Google 是「多设备共存 + 会话列表」。

**三个失效出口**（各管一个范围，别搞混）：

| 出口 | 作用范围 |
|---|---|
| 登出 | **仅当前设备** |
| 改密码 | **全部设备** |
| 账号被停用 | **全部设备 + 禁止再登**（且每个请求都复核，见 `AuthInterceptor`） |

**会话管理能力**（接口见 §1.3）：

- **看**：`GET /api/auth/sessions` —— 显示每台设备的**设备（UA 粗解析）/ IP（打码）/ 登录时间 / 最后活跃**，
  并标出**哪条是当前设备**。这就是"我在哪儿登录过"。
- **踢**：踢单个 ／ **踢掉其他所有设备（保留当前）**。
- **管理员踢下线**：`POST /api/admin/members/{id}/revoke-sessions` —— 作废某人全部 token，
  **但不改账号状态**。这是比"停用账号"**轻一档**的手段：停用会连带改状态、禁止再登，
  而"踢下线"只是让人重新登一次。
- **找回的逃生口**：怀疑账号被人用过 → **改密码**，一键踢掉所有设备。

**两条实现约定**（细节在 `13-数据模型总表.md` §13.3④）：

- `last_seen_at` **粗粒度更新**（距上次 > 1 小时才写），避免每个请求多一次 UPDATE；
- **过期 / 已撤销的会话行不删**——它们是**登录流水**（谁、何时、从哪个 IP 登过），留着有审计价值；
  会话列表只展示**有效**会话。

**U-1 不做新设备登录告警**（暂定）：新设备登录时通知本人（"如果不是你，请改密码"）是防账号外借
**最有效**的一条，但它**需要通知渠道**——而本项目的 `notification_log` 只留了表、不实现发送端。
要做的话得先把渠道定下来，**否则又变成"只留表不实现"**。

### 禁用登录的条件

**`member.status` 不是「在团」时：① 禁止登录 ② 立即作废其全部 token。**

> **这是补上的一个安全漏洞**：软删除只标记状态、不删数据，若不同时让账号失效，
> 退团的人拿着 30 天有效期的旧 token 照样能看谱子、录音、成员手机号。

### 密码强度

**至少 8 位，不强制大小写 / 符号混合。**

这是刻意的取舍：复杂规则会让团员把密码写在纸上或到处贴，反而更不安全。

### 登录失败的处理（防爆破）

- 按 **「IP + 账号」组合**计数。**不单按账号**——单按账号会被恶意利用：
  故意输错他人账号名，就能把对方的登录拖慢。
- 达到阈值后**延迟响应**（如 3 秒）并继续计数，**不锁死账号**。
  锁死会制造"找管理员解锁"的运维负担，也违背"别用起来烦"的原则。

### 管理员账号是独立的系统账号

- **`member.is_system = true` 的管理员账号不属于任何团员**，不出现在团员名单、不参与考勤与出勤统计
- 用户名与密码一开始就存在且保密，**靠线下代代相传**
- **换届交接不需要任何系统机制**（线下传凭据即可）
- **系统内没有人能修改管理员账号的角色**
- **忘记密码的出路**：服务器上执行应急重置脚本（只在这一件事上使用）

> 详细背景见 `DECISIONS.md` 与 `11-日志与留痕.md`。

### 首次部署：第一个管理员从哪来（**bootstrap**）

上面说了管理员账号"一开始就存在"，但**第一个账号得由系统自己造出来**——否则是个死循环（没有管理员就没法建号）。
机制（**已在实现中，此处收编为规格**，见 `auth/AdminSeeder.java`）：

1. **配置注入**：账号名与密码由配置提供——`band.admin.account` / `band.admin.password`
   （写在 `application-local.yml` 或环境变量，**绝不进仓库、绝不进日志**）。
2. **首启播种**：应用启动时若**库里还没有 `is_system=1` 的行**，就用配置里的账密创建这个账号；
   已存在则**跳过**（幂等，重启不会重复建也不会覆盖改过的密码）。
3. **强制校验**：密码**至少 8 位**；缺配置直接启动失败并明确报错——**不许静默跳过**
   （静默跳过会变成"部署完发现没有管理员，且不知道错在哪"）。
4. **创建后**：`is_system=1`、`role=ADMIN`、`status=ACTIVE`、`joined_at=当天`；
   按不变式 3 不进名册、不参与考勤。
5. **上线前必做**：把默认密码改成只有管理员知道的强密码，并确认它**没被提交进仓库**。

> 为什么写这一节：这条机制不写下来，换个人实现会各自发明一套（比如直接 SQL 手插明文密码），
> 而且上线时会想不到"第一个管理员"这个必须先解决的问题。

### 日志

**绝不打印密码与 token 原文**，包括错误日志的异常信息里也不能带
（堆栈常会把入参打出来，要检查）。
